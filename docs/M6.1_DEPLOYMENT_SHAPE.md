# M6.1: choosing the deployment shape from measurements

## 0. Why this step exists

`docs/OPERATIONS.md` names an AWS shape - ECS Fargate behind an ALB, RDS PostgreSQL,
CloudFront in front - and says so honestly: "The AWS part is not implemented; everything
about AWS below is an operational contract to be implemented and verified". That contract
was written before a single number had been measured.

Two of its resources are billed continuously and cannot be scaled to zero. An ALB is
charged per hour from creation to deletion, and a VPC-attached compute path that needs to
reach a model API needs a NAT gateway, also charged per hour. A demo nobody is using would
therefore cost tens of dollars a month, which defeats the requirement this stage was given:
start on demand, shut down after fifteen minutes of idleness.

M6's acceptance line in `docs/DEVELOPMENT_PLAN.md` is "Terraform, one-command start/stop",
accepted on creation, login, streaming, archiving, teardown and rollback. It does not ask
for a particular architecture. So the architecture is a decision this project has to make
and defend, and this step makes it from measurements rather than from preference.

### 0.1 An ordering that is recorded rather than hidden

The shape 1 and shape 3 measurements in section 2 were run before this card was written,
as exploratory work directed by the developer. That is the wrong order by this repository's
own rule, and writing the card afterwards to match the results would be worse. The card
below therefore states the decision rule and the acceptance thresholds, the measurements
that already existed are reported as they came out, and the one measurement the rule still
needs - EC2 restart time - was run after this card was written. Which numbers came before
and after is marked in section 3.

## 1. Change card

- **Stage and step**: M6.1
- **Type**: feature, in the sense of a decision plus the read-only tooling that supports it
- **The specific problem**: no deployment shape has been chosen, and the one the operations
  contract assumes has a monthly floor that the on-demand requirement forbids
- **The single theme of this change**: choosing the shape, and adding a read-only AWS
  inventory. Nothing is deployed.
- **Control variables this change does not touch**: the application, the database schema,
  the migrations, the agent, the guard, the evaluation harness, the benchmark subject, the
  local start/stop scripts, and every baseline.
- **Explicitly out of scope**, each its own later step:
  - Terraform modules and state layout
  - The start and stop entry points
  - HTTPS and the entry URL
  - The idle shutdown timer
  - Archiving on stop
- **Expected benefit**: an idle cost under 1 USD per month and a restart short enough to
  begin a live demonstration in front of someone, both measured before any of it is built.
- **Possible cost**: the cheapest candidate on this list is also the least like a
  production topology, because it puts PostgreSQL on the application instance. If it wins,
  saying so plainly is part of the deliverable rather than something for an interviewer to
  discover.

### 1.1 The candidates

| | Shape | Idle behaviour |
|---|---|---|
| 1 | Destroy when idle | every resource deleted; the next start creates them again |
| 2 | Stop when idle | the instance is stopped; its disk survives |
| 3 | Scale to zero | resources exist permanently at zero capacity |

Shape 2 was not in the original list. It was added after shapes 1 and 3 were measured,
because their numbers made the gap it fills visible.

### 1.2 The constraint chain that removes shape 3

Shape 3 needs compute that can be billed at zero while idle. On AWS that means Lambda.
Once the requirement includes streaming output to the browser, Lambda forces a chain of
consequences, each of which was checked rather than assumed:

1. Python on Lambda cannot stream natively. It needs the Lambda Web Adapter or a custom
   runtime, and the response must leave through a function URL or through API Gateway
   ([response streaming](https://docs.aws.amazon.com/lambda/latest/dg/configuration-response-streaming.html)).
2. **Function URLs do not support response streaming inside a VPC.** Documented, same page.
3. Aurora lives in a VPC. Reaching it from outside one means the RDS Data API. Its
   SQLAlchemy dialect is still on SQLAlchemy 1.x
   ([sqlalchemy-aurora-data-api](https://pypi.org/project/sqlalchemy-aurora-data-api/)),
   while `src/retail_support_agent/store.py` is SQLAlchemy 2.0 and gets its idempotency
   from PostgreSQL's `INSERT ... ON CONFLICT`. Replacing that layer would put M1's and M2's
   guarantees back in question to save a few dollars a month.
4. Attaching the Lambda to the VPC instead keeps psycopg, but a VPC-attached Lambda has no
   IPv4 egress. Calling the model API then needs a NAT gateway, billed per hour, which is
   both more expensive than the whole demo and not scale-to-zero.
5. Aurora DSQL avoids the VPC and works with ordinary SQLAlchemy, but supports neither
   foreign keys nor sequences. `src/retail_support_agent/db.py` declares fourteen foreign
   keys with cascade rules and uses integer autoincrement primary keys.

Independently of all of that, Gradio would not survive shape 3 either. Version 6.14 splits
one interaction into `POST /queue/join` and a separate `GET /queue/data` event stream
(`routes.py:1432` and `routes.py:1557`), with the state between them held in process
memory. Two requests on Lambda may land on two instances.

Shape 3 therefore costs either a rewrite of the storage layer or a permanent NAT gateway.
Neither is bought by anything M6 is accepted on.

### 1.3 The decision rule, fixed before the remaining measurement

| Condition | Threshold |
|---|---|
| Idle cost | under 1 USD per month, excluding model usage |
| Restart | under 120 seconds from the start command to a page that answers |
| Application change | none required to make the shape work |
| Streaming | supported by the shape without a protocol workaround |
| Teardown | every billed resource removable, and the removal verifiable by inventory |

A shape is eliminated by failing any one of these. Where two survive, the one with fewer
components to build wins, because every component is a thing that has to be written,
tested and explained.

### 1.4 Baseline, task set and protocol

Not applicable in the evaluation sense. No model is called, no task set is run, and no
baseline moves. The reference this step is measured against is the operations contract in
`docs/OPERATIONS.md`, and section 4 records which parts of it this supersedes.

## 2. Implementation and verification

### 2.1 Files

| File | Responsibility |
|---|---|
| `docs/M6.1_DEPLOYMENT_SHAPE.md` | this decision, its measurements and its limits |
| `scripts/aws_inventory.py` | read-only; lists what this project has in AWS and what the account has spent this month |

The inventory is read-only by design. Deleting is Terraform's job, and a script that can
delete is a script that can delete the wrong thing. It finds resources through the
Resource Groups Tagging API, filtered to `Project=RetailSupportAgent`, so the one way it
can be wrong is a resource created without that tag. It also over-reports rather than
under-reports: a terminated instance keeps its tags for a while and goes on appearing
after it has stopped being billed, which is the safe direction for a report whose job is
to answer "is anything left".

The account id is masked in its output, in the header and inside every ARN, because that
output is meant to be pasted into a report.

### 2.2 How the shapes were measured

Four measurements, each of which created real resources, timed them and deleted them. The
scripts are not in this repository. They provision billed infrastructure, they are run
once to settle a decision rather than repeatedly as part of a release, and a script in
`scripts/` that launches instances is a hazard out of proportion to its value. What each
did is recorded here in enough detail to repeat, and anyone checking these numbers should
re-measure rather than trust a cached script.

| Measurement | What it created | Where the number comes from |
|---|---|---|
| Shape 1, database | one `db.t4g.micro`, PostgreSQL 17, 20 GiB gp3 | wall clock from `create-db-instance` to status `available`, then to gone after `delete-db-instance` |
| Shape 3, database | one Aurora Serverless v2 cluster, min 0 max 1 ACU, `SecondsUntilAutoPause=300`, Data API enabled | wall clock to `available`; then the CloudWatch `ServerlessDatabaseCapacity` minimum polled until it reached zero; then Data API `select 1` timed before and after the pause |
| Shape 3, compute | this application's container image in ECR, invoked as a Lambda function at 1769 MB and at 3008 MB | `Init Duration` and `Duration` from Lambda's own REPORT line, cold and warm |
| Shape 2, compute | one `t3.micro`, Amazon Linux 2023, 8 GiB gp3, serving a static page from a systemd unit | wall clock from the API call to the first HTTP reply from the instance, on first boot and on restart |

Every resource carried `Project=RetailSupportAgent` and `Purpose=m6-shape-measurement`,
and every one was deleted at the end of its run. The Lambda measurement used a dummy
model key, since it only ever answered a health route.

### 2.3 Three failures worth keeping

- **Lambda rejected the image.** `docker buildx` writes an OCI manifest by default and
  `CreateFunction` answers "image manifest, config or layer media type ... is not
  supported". Rebuilding with `--provenance=false --sbom=false` leaves a Docker v2
  manifest, which is accepted.
- **A process started from EC2 user data does not survive a stop.** Cloud-init runs user
  data once per instance, not once per boot, so the first restart measurement timed out
  waiting for a reply that could never come. The probe was rewritten as a systemd unit.
- **Git Bash rewrote a block device name.** `/dev/xvda` reached `RunInstances` as
  `C:/Program Files/Git/dev/xvda` and the mapping was rejected. `MSYS_NO_PATHCONV=1` fixes
  it. This is a local-environment hazard rather than an AWS one, and it is recorded because
  it will recur when Terraform is driven from this machine.

### 2.4 Prices

Taken from the AWS Pricing API for `eu-west-1` on 2026-09-09, not from memory. A month is
730 hours.

| Item | Rate | Per month if it simply exists |
|---|---|---|
| gp3 storage | 0.088 USD per GB-month | 0.70 USD for 8 GiB |
| Public IPv4 address | 0.005 USD per hour, in use or idle | 3.65 USD |
| Application Load Balancer | 0.0252 USD per hour, plus capacity units | 18.40 USD |
| NAT gateway | 0.048 USD per hour, plus 0.048 USD per GB | 35.04 USD |

The last two lines are the reason the operations contract's shape was reopened. An ALB
and a NAT gateway together cost about 53 USD a month before anyone opens the page. The
public IPv4 line is why the chosen shape uses a DNS record updated at boot rather than an
Elastic IP: an Elastic IP is charged at the same rate while idle, so reserving one to
avoid a changing address would cost more than the disk.

## 3. Comparison

The template's metric table does not apply here. No model is called and no task set is
run, so task success rate, safety violations and cost per successful task are unchanged by
construction and are not restated. What follows is the comparison this step actually makes.

### 3.1 What each shape measured

Shapes 1 and 3 were measured before this card was written; shape 2 after, as section 0.1
records.

| Measured | Shape 1, destroy when idle | Shape 3, scale to zero | Shape 2, stop when idle |
|---|---|---|---|
| Database ready | 299 s to create `db.t4g.micro` | 471 s to create, then 4.6 s for the first query after a pause | not created; PostgreSQL runs on the instance in demo mode |
| Database gone or idle | 86 s to delete | capacity reached zero after 606 s of idling, with auto-pause set to 300 s | stopped with the instance |
| Compute ready | not measured separately; bounded below by the database | 6815 ms cold at 1769 MB, 6933 ms at 3008 MB, 3.5 ms warm | 15 s from `start-instances` to the first HTTP reply |
| Repeatability | single run | single run | 15 s, 15 s and 14 s over three boots |
| Shutdown | full delete | pause, cluster still exists | 19 s and 33 s to stopped |

The Aurora resume is about 3.5 s net: a warm query on the same cluster took 1.1 s, so
roughly that much of the 4.6 s is the Data API round trip rather than the wake-up. The
Lambda measurement used an image of 966 MB that does not contain Gradio; adding it would
grow both the image and the cold start, since importing Gradio 6.14 alone takes about
2.1 s on this machine and 81 MB on disk.

### 3.2 Against the decision rule in section 1.3

| Condition | Shape 1 | Shape 3 | Shape 2 |
|---|---|---|---|
| Idle cost under 1 USD per month | pass, nothing exists | pass, storage only | pass at 8 GiB, 0.70 USD; see 3.3 |
| Restart under 120 s | **fail**, 299 s for the database alone | pass, about 10 s | pass, 15 s |
| No application change required | pass | **fail**, the storage layer or the network path has to be rebuilt | pass |
| Streaming without a workaround | pass | **fail**, see section 1.2 | pass |
| Teardown verifiable by inventory | pass | pass | pass |

Shape 1 is eliminated on restart time. Shape 3 is eliminated twice over on the two
conditions that cost engineering rather than money. Shape 2 passes every condition and has
the fewest components to build, which section 1.3 makes the tie-break.

### 3.3 The one threshold that is not comfortably met

Idle cost is a function of disk size, and the disk has not been sized yet. At the
`eu-west-1` gp3 rate of 0.088 USD per GB-month, the 1 USD threshold holds up to 11 GiB and
is missed above it. The measurement ran on 8 GiB, which is what the machine already
compared against, but the demo instance also has to hold the application image and a
PostgreSQL data directory.

This is recorded as an open number rather than resolved by choosing a convenient one. If
sizing the disk in the next step requires more than 11 GiB, the threshold is revisited in
the open and re-agreed, not quietly relaxed.

## 4. Failure analysis and conclusion

**PASS. Shape 2 is chosen: one instance, stopped when idle.**

- **What was accepted**: the shape, and `scripts/aws_inventory.py`.
- **What was rejected, and why it is a measurement rather than a preference**: shape 1
  cannot start a database in under five minutes, and shape 3 buys its zero idle cost with
  either a rewrite of `store.py` or a NAT gateway at 35 USD a month.
- **Nothing was deployed.** Every resource created for these measurements was deleted, and
  the inventory was used to confirm it.

### 4.1 What this supersedes

`docs/OPERATIONS.md` describes an ECS Fargate, ALB, RDS and CloudFront target, and says of
itself that it is a contract to be implemented rather than something that works. Sections
"AWS technical target", "Separate base and demo layers" and "Free URL and HTTPS" are
superseded by this decision and will be rewritten in the step that builds the Terraform,
not before. Until then that document stands with this one as its correction; leaving it
untouched while the shape changed underneath it would be worse than either.

### 4.2 The trade-off being made on purpose

In demo mode PostgreSQL runs on the application instance. That is not a production
topology and nobody should be told otherwise. It is a module variable in the Terraform to
come: demo mode points at a container on the instance, production mode points at RDS, and
both are in version control. The reason is cost, and the cost is written down above.

### 4.3 Not verified

- **The application's own start time.** The 15 s measured here is Amazon Linux 2023
  reaching a systemd unit that serves a static file. The real start also pulls or loads a
  container image, starts PostgreSQL, runs migrations and warms the application. The
  budget in section 1.3 leaves about 105 s for all of that, and the step that builds it
  must measure it rather than assume it fits.
- **The disk size**, and therefore the idle cost, as section 3.3 says.
- **HTTPS.** The plan is a certificate obtained on the instance and kept on the volume so
  it survives a stop, with a DNS record updated at boot. None of that has been built or
  timed.
- **The idle shutdown.** Fifteen minutes of idleness has to be defined against this
  application's state, not against CPU: no write in flight, no confirmation pending, no
  open ticket, and the archive completed. That definition is the next step's first job.
- **Whether 15 s survives a larger instance and a real image.** Three boots of one
  `t3.micro` are not a distribution.
- **The Aurora and RDS numbers are single runs.** They were enough to eliminate two shapes
  by wide margins, and they are not precise enough for anything narrower.
