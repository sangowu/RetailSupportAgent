# M0.4 selection experiments: freezing the evaluation stack, smoke results and cost estimates

Status: **the model is selected - `deepseek-v4-pro` (DeepSeek's own endpoint), on cost rather
than best score; holdout 0.600 (24/40), and the harness is now built around it**.
Date: 2026-09-06.

## 1. The evaluation stack is frozen

Upstream's orchestrator, simulated user and evaluators are never rewritten. Only two wiring
changes are made: route litellm to DashScope's OpenAI-compatible endpoint, and replace the NL
assertion judge from upstream's default `gpt-4.1` (no access) with a fixed model the account
can call.

| Role | Model | Endpoint | Why |
|---|---|---|---|
| Agent under test | the 5 candidates in rotation | DashScope | the experiment's subject |
| Simulated user | `qwen3.6-plus-2026-04-02` | DashScope | **outside the candidate pool**, dated snapshot |
| NL assertion judge | `deepseek-v4-flash` | **DeepSeek (separate)** | outside the pool; quota isolated from the account under test |

The judge sits with a separate provider because the account under test is in
free-quota-only mode (section 4): **when the model under test runs out of quota, the judge must
not go down with it**, or it becomes impossible even to judge where the run failed. The
separate endpoint is enabled only when `RSA_JUDGE_BASE_URL`, `RSA_JUDGE_API_KEY` and
`RSA_JUDGE_MODEL` are all present; a half configuration **falls back** to the default judge
rather than sending the wrong key.

**A known risk that must be reported alongside the scores**: `deepseek-v4-flash` and the
candidate `deepseek-v4-pro-0813` belong to the same `deepseek-v4` family. Exact matching does
not catch that relationship, so `EvalStack.warnings()` compares by **family** as well and
writes the warning into every run's manifest. Models from the same family may systematically
favour their own style of output, and any reading of `deepseek-v4-pro-0813`'s score must state
this risk rather than wait for someone else to point it out.

Two rules live in code rather than only in documentation: at construction, `EvalStack` checks
whether the simulated user and the judge **fall inside the candidate pool and raises if they
do**. The reason is self-evaluation bias: letting a candidate score itself invalidates the
comparison. Dated snapshots are chosen over aliases because an alias can be updated silently
on the server, making today's and next week's scores incomparable.

The stack's temperature is fixed at 0.0, matching upstream's default.

## 3. The cost model (recomputed from measurement; previously overestimated by about 2x)

**Upstream's reported `agent_cost` is always 0**: litellm does not know DashScope's or
DeepSeek's prices. Cost has to be computed here, and `scripts/analyze_eval.py` converts token
usage at the price snapshot and records the date the prices were taken.

### 3.1 Three costs previously missed

Upstream's `get_response_usage()` keeps only two fields:

```python
# tau2/utils/llm_utils.py
return {"completion_tokens": usage.completion_tokens, "prompt_tokens": usage.prompt_tokens}
```

`prompt_tokens_details.cached_tokens` and `completion_tokens_details.reasoning_tokens` are
dropped. Fortunately the full response has always been kept in `message.raw_data`, so
**historical results can be reprocessed**. Reprocessing the smoke run gave three facts that
were previously unknown:

| Finding | Measured | Consequence |
|---|---|---|
| DashScope's implicit cache **has been hitting all along** | **93312 of 129262 input tokens (72%)** on the subject side | Cost was **overestimated by about 2x** |
| The simulated user runs in **thinking mode** | **4451 of 4980 output tokens are reasoning (89%)** | A cost never previously counted |
| Judge calls are not in messages | Previously could only be recorded as unknown | Unknown is not zero and needs separate accounting |

Implicit caching is on by default and cannot be disabled, and cache hits are billed at **20%**
of the input price. But `qwen3.8-max`, `qwen3.8-flash` and `deepseek-v4-pro` are documented
**exceptions** whose discount must be looked up in the console, which we cannot access. For
those three models we therefore **give an interval rather than a falsely precise number**, with
the upper bound at full price (overestimate rather than underestimate).

Judge usage is now accounted separately by `JudgeUsageRecorder`, which wraps the evaluation
module's `generate`, and written into each run's `summary.json`.

### 3.2 Cost after recomputation

Measured per-task usage on the agent side: **input 64631 tokens (46656 of them cache hits),
output 2851 tokens**. Input dwarfs output because every turn resends the full policy (6699
characters) and all 16 tool definitions - and it is precisely because that part is a stable
prefix that the cache hit rate reaches 72%.

Single-model cost for the 74-task dev set:

| Model | 74 tasks (new) | 74 tasks (old, no cache) |
|---|---|---|
| `qwen3.7-max-2026-06-08` | **31.8 CNY** | 65.0 CNY |
| `qwen3.8-max` | 31.8 - 65.0 CNY | 65.0 CNY |
| `deepseek-v4-pro-0813` | 29.3 - 62.5 CNY | 62.5 CNY |
| `glm-5.2` | **22.1 CNY** | 44.2 CNY |
| `qwen3.8-flash` | **2.2 - 4.4 CNY** | 4.4 CNY |

The models with intervals are the three whose cache discount is not published: the lower bound
assumes a 20% discount, the upper bound assumes none.

**Still not counted**:

- The simulated user: usage is measured (about 4930 input / 2490 output per task, 89% of the
  output being reasoning tokens), but `qwen3.6-plus`'s prices could not be obtained, so it
  still cannot be converted.
- The table above originally said "based on non-thinking mode", which is **disproven**: DeepSeek
  has thinking on by default at level high, so the historical data always contained reasoning
  tokens. See 9.5.
- Models differ in verbosity and cache hit rate, so extrapolating other models from the
  reference model's usage is necessarily biased.

### 3.3 Judge cost (DeepSeek's own endpoint)

The judge uses DeepSeek's own endpoint, which is **not the same price list** as the identically
named `deepseek-v4-pro-0813` on DashScope; the code keeps them strictly distinct. DeepSeek has
peak and off-peak prices, off-peak being half of peak:

| | Cache hit | Cache miss | Output |
|---|---|---|---|
| `deepseek-v4-flash` peak | 0.10 | 3.0 | 9.0 |
| `deepseek-v4-flash` off-peak | 0.05 | 1.5 | 4.5 |

CNY per million tokens. Peak is Monday to Friday 09:00-12:00 and 14:00-18:00 Beijing time
(= 01:00-04:00 and 06:00-10:00 UTC); everything else, including weekends, is off-peak.
`deepseek_tier()` determines the tier from the call time automatically, and re-judgement
reports state which tier applied.

A typical judgement is about 6k input and 300 output tokens, so **about 0.02 CNY at peak and
0.01 CNY off-peak**. The judge is cheap but not free; the error is treating "not counted" as
"costs nothing".

## 4. An account problem: free-quota-only mode

Probing a model outside the candidate pool returned this server response:

```
403 - Free quota exhausted. To continue accessing the model on a paid basis,
please add funds or disable the "use free tier only" mode in the management console.
```

What it means and what follows:

1. The account is currently in **free-quota-only** mode. The M0.2 report's "total measured cost
   about 0.31 CNY" is a **theoretical figure** converted from the price snapshot; the run most
   likely consumed free quota rather than real credit, and that statement should be corrected
   accordingly.
2. Several models' free quota is already exhausted (for example `qwen3.7-plus-2026-05-26`).
3. **A full-scale experiment may well fail midway when quota runs out**, leaving incomplete and
   incomparable results.

So before a full-scale experiment starts, it must be confirmed whether the quota is sufficient
or whether free-quota-only mode should be turned off in favour of paid usage. That is not a
technical question; the account holder has to decide.

## 5. The judge's real reach (previously overestimated threefold)

Measured from the upstream task files, not copied from documentation:

| Convention | Count |
|---|---|
| **Declares** NL_ASSERTION in `reward_basis` | 112 / 114 |
| **Actually carries assertions and really calls the judge** | **40 / 114** |
| Declares it but has an empty assertion list, automatically scoring 1.0 | 72 |

Only **29** of the 74 dev tasks call the judge, and only **11** of the 40 holdout tasks. The
earlier claim that "112 tasks run DB x NL_ASSERTION" should be corrected accordingly.

On those 40 tasks the judge is still decisive, because upstream treats assertions as all or
nothing:

```python
all_expectations_met = all(result.met for result in nl_assertions_checks)
reward = 1.0 if all_expectations_met else 0.0
```

One jitter on any single assertion takes the whole task from 1.0 to 0.0. Noise is not averaged
out, it is amplified. So a sample has to contain enough tasks with assertions, and `--sample`
therefore stratifies by judge coverage rather than naively truncating to the first N tasks.

## 6. Experiment design: one round decides the model

Per-task cost is converted from the smoke run's measured usage (input 64631 tokens, 46656 of
them cache hits; output 2851 tokens):

| Model | CNY per task |
|---|---|
| `qwen3.7-max-2026-06-08` | 0.430 |
| `qwen3.8-max` | 0.430 - 0.878 |
| `deepseek-v4-pro-0813` | 0.396 - 0.844 |
| `glm-5.2` | 0.298 |
| `qwen3.8-flash` | 0.030 - 0.059 |
| **Five models combined** | **1.58 - 2.51** |

Scale versus cost for running all five candidates on the same tasks (agent side):

| Tasks | Sessions | With cache counted | Old estimate |
|---|---|---|---|
| 4 | 20 | 6.3 - 10.0 CNY | 13.0 CNY |
| **6** | **30** | **9.5 - 15.1 CNY** | 19.5 CNY |
| 8 | 40 | 12.7 - 20.1 CNY | 26.1 CNY |
| **12 (confirmed)** | **60** | **19.0 - 30.1 CNY** | 39.1 CNY |

Caching cuts the budget roughly in half. Since there is only one round and no later stage to
fall back on, there is no reason to keep saving tasks as if another stage were coming:
**12 tasks are confirmed**, raising judge coverage from 2 tasks at 6 to 5 tasks.

**Decision: one round decides the model.** The earlier A->B->C->D four-stage funnel is
cancelled.

| Step | Contents | Sessions | Estimate | Status |
|---|---|---|---|---|
| **A0 judge reliability** | 2 tasks (with assertions) run once plus 3 offline re-judgements | 2 | 1.15 CNY (actual) | **done, see 6.4** |
| **A selection (the only round)** | 5 models x stratified sample of **12 tasks** x 1 trial, thinking high (see 9.5) | 60 | 16 - 32 CNY (actual) | **done, see 7** |
| V independent verification | `qwen3.8-max` x holdout 40 tasks x 1 trial | 40 | 15.74 - 46.94 CNY (actual) | **done, see 8** |

**About 50 - 72 CNY in total.**

That is higher than the previous version's 32-48 CNY because A0's measured usage was much
larger than the first smoke run's: **115805 input tokens per task versus only 64631**. Tasks
with NL assertions have longer conversations, and the first smoke run happened to sample two
short tasks without assertions, so extrapolating from it **underestimates**. The current
estimate is based on tasks with assertions and is conservative, which is the right direction.

Of the 12 tasks, **5** actually call the judge (`2, 3, 4, 16, 19`); the other 7 are DB
comparison only.

### 6.1 Early stopping within the round

One decisive round means there is no later stage to fall back on, but there is also no reason
to finish 12 tasks for an obviously unfit configuration:

```bash
uv run python scripts/run_eval.py --model <M> --sample 12 --early-stop 4
```

Run the first 4 tasks; if the mean reward is at most 0.001 (all zero), stop and skip the
remaining 8. Results are written in segments and merged back into one run by
`results_io.load_simulations()` on read, with `stopped_early` and `completed_task_ids` recorded
in `summary.json`.

Two rules live in code: **an unscored simulation is not counted as 0** (otherwise a model that
simply did not finish would be killed by mistake), and segments **must not lose tasks or change
their order**.

### 6.2 How to write up the conclusion

One round of 12 tasks yields a **screening** conclusion, not a ranking. The report must follow
these conventions:

- Allowed: "X passes on this sample; Y is clearly unfit (all zero on the first 4 tasks, stopped
  early)"
- **Not allowed**: "X beats Y by 3 percentage points" - 12 tasks cannot resolve a few
  percentage points

If first and second place are close, write "the two were not separated on this sample; X was
chosen on cost/latency". This project's selling point is rigorous evaluation, and a wrong
convention costs more than it gains.

### 6.3 Why independent verification is kept

After the model is chosen, run it once on the **40-task holdout**, about 12-17 CNY, for one
model only. That number **did not take part in selection** and is a clean independent
verification. For a project whose selling point is reproducible evaluation, one such line in the
report is worth far more than two extra candidates. The holdout **must not be used for tuning**.

The thinking-mode comparison (`--thinking`) was cancelled along with stage B. If it is ever
done, note that the current estimates were thought to be based on non-thinking mode but were in
fact the server's default thinking+high (see 9.5.1), so they do not underestimate the output
inflation that thinking causes.

### 6.4 A0 judge reliability results (2026-09-06, executed)

The first real execution after switching the judge to `deepseek-v4-flash` on DeepSeek's own
endpoint. **No earlier run had actually called the judge**; this was the first.

Subject `qwen3.7-max-2026-06-08` on dev tasks `2` and `3` (both with NL assertions):

| Metric | Value |
|---|---|
| Mean reward | 1.0000 (2/2) |
| Judge calls | 2, with 11238 input and 308 output tokens |
| Subject cost | 1.1347 CNY |
| Judge cost | 0.0182 CNY |

The same judge then re-judged **the saved traces** offline three times (zero cost on the agent
side):

| Check | Result |
|---|---|
| Tasks where the same judge contradicted itself | **0 / 2** |
| Disagreements with the previous judge (`qwen3.6-plus`) | **0 / 2 assertions** |
| Cost of re-judging | 0.0067 CNY (off-peak) |
| DeepSeek cache hit rate | **99%** (33408/33714) |

**Conclusion: the judge is usable; proceed.**

**But the strength of that conclusion has to be stated**: the sample is **2 assertions**. Zero
disagreement shows "no problem was found", not "the judge is stable" - 2 assertions cannot
measure a jitter rate of a few percent. Real judge-noise data has to wait until round A finishes
(5 tasks with assertions x 5 models = 25 judgements) and those are re-judged.

Two incidental observations:

- `deepseek-v4-flash` thinks as well (505 of its 1005 output tokens are reasoning).
- DeepSeek's cache hit rate is 99% when judging the same content repeatedly, so **re-judging is
  almost free**, which turns "re-judge all historical results after changing judges" from a new
  expense into a matter of a few cents.

**A0 is a new step and the one that should come first.** It costs almost nothing yet answers a
question that must be settled before spending hundreds: whether the judge itself is stable. The
method re-judges **saved traces** - the judge consumes only the conversation plus the
assertions, both of which are in the result file, so re-judging **does not rerun the agent** and
spends only the judge's tokens:

```bash
uv run python scripts/recheck_judge.py --run <directory> --repeat 3
```

It answers two things at once: whether one judge is self-consistent across repeats
(`--repeat`), and how much the old and new judges disagree. **Frequent disagreement does not
mean the new judge is worse, only that the two are not interchangeable** - once the judge
changes, all historical scores have to be re-judged, and old and new must not be mixed.

An honest note about cutting to 6 tasks: **6 tasks can screen, not rank.** They suffice to
eliminate configurations that obviously fail, such as one that cannot even call tools
correctly; but if candidates differ by a few percentage points, no small sample can separate
them, and that has to wait for stage C. Shrinking the scale buys earlier elimination of bad
configurations, not an earlier conclusion.

The stratified sampling rule (for reproducibility): sample by the existing ratio of "with
assertions / without assertions" within that split, following the original order of the frozen
list. No random numbers are involved, different machines necessarily draw the same sample, and
the selected task ids are written into the run manifest.

**The lever bigger than cutting tasks has now been identified**: the 64631 input tokens per
task are 88% of the cost, and most of that is the policy text and the 16 tool definitions
resent every turn. That part is a stable prefix, and DashScope's implicit cache **has been
hitting all along at 72%** (see 3.1). So halving the budget did not come from cutting tasks but
from counting a discount that was already happening and simply not being measured.

Conversely, **do not make any change that breaks the prefix's stability** - putting the policy
text or tool definitions in the middle of the conversation, or varying the system prompt each
turn - because the hit rate would drop and the cost would immediately double.

## 7. Round A results (2026-09-06, executed)

5 candidates x a stratified sample of 12 dev tasks x 1 trial, with `--early-stop 4` and
concurrency 4. (Recorded at the time as non-thinking, in fact the server's default
thinking+high; see 9.5.1.)
**All 5 models completed; none triggered early stopping and none hit a quota 403.**

### 7.1 Scores

| Model | Mean reward | DB | NL | Cost for 12 tasks |
|---|---|---|---|---|
| `qwen3.8-max` | 0.7500 (9/12) | **11/12** | 10/12 | 4.88 - 14.32 CNY |
| `qwen3.7-max-2026-06-08` | 0.7500 (9/12) | 9/12 | **12/12** | 5.61 CNY |
| `glm-5.2` | 0.5833 (7/12) | 9/12 | 9/12 | 2.40 CNY |
| `qwen3.8-flash` | 0.5000 (6/12) | 6/12 | **12/12** | **0.24 - 0.76 CNY** |
| `deepseek-v4-pro-0813` | 0.5000 (6/12) | 7/12 | 10/12 | 3.17 - 8.56 CNY |

All 60 sessions ended normally (`USER_STOP`). Round A cost about **16 - 32 CNY**, below the
25-48 CNY estimate.

### 7.2 Statistical conclusion: this round separated no pair of models

| Model | Pass rate | 95% confidence interval (Wilson, n=12) |
|---|---|---|
| `qwen3.8-max` / `qwen3.7-max` | 0.750 | [0.47, 0.91] |
| `glm-5.2` | 0.583 | [0.32, 0.81] |
| `qwen3.8-flash` / `deepseek-v4-pro-0813` | 0.500 | [0.25, 0.75] |

The same 12 tasks are paired data, so pairwise comparisons use the McNemar exact test:
**all 10 pairs are not significant**, with a minimum p of 0.375 (`qwen3.8-flash` vs
`qwen3.8-max`). The largest gap (0.75 vs 0.50) corresponds to p = 0.453.

**So under the conventions fixed in 6.2, nothing here may be written as "X beats Y".**
A sample of 12 tasks cannot resolve a difference of a few, or even twenty-odd, percentage
points - which is not a surprise but the limitation already stated in 6.2.

### 7.3 Judge noise: 8%, the same order as the gaps between models

Re-judging all 5 runs offline three times (25 task-level judgements, 30 assertions) at zero
cost on the agent side and **0.35 CNY** in total:

| Metric | Result |
|---|---|
| The same judge contradicting itself | **2 / 25 tasks (8%)** |
| Disagreement with the previous judge (`qwen3.6-plus`) | 2 / 30 assertions |

Both disagreements point at the same assertion:

> Agent should tell the user that exchanging the pet bed and office chair saves $4

**This number is critical**: the judge's own 8% jitter is the same order of magnitude as the
already non-significant gaps between models. In other words, even if 12 tasks show a gap, it
cannot be separated from judge jitter. This confirms the earlier insistence that the judge must
be independent and its consistency verified first.

### 7.4 A split more meaningful than the total

The totals cannot be separated, but the DB and NL halves behave very differently - and **DB is
a programmatic comparison that never passes through the judge, the only one of these five
numbers free of judge noise**:

- `qwen3.8-max`: DB **11/12**, NL 10/12 - almost every database operation was right, but twice
  it did not say the right thing. Those two NL failures **reproduced stably across 3
  re-judgements and are not judge noise**.
- `qwen3.7-max` and `qwen3.8-flash`: NL **12/12**, with every failure on the DB side.
- `qwen3.8-flash`'s DB is only 6/12 - **ten times cheaper, but half of its order operations are
  wrong**.

For a retail support agent, **getting the database wrong is worse than saying the wrong
thing**. Cancelling the wrong order or refunding the wrong amount is irreversible; an
incomplete explanation just prompts another question.

### 7.5 Selection recommendation

**`qwen3.8-max` is recommended**, on one argument that holds up: it leads on the **only metric
free of judge noise** (DB 11/12), and that metric is exactly the business correctness this
project claims to guarantee.

Three things must be stated alongside it:

1. **This is not a conclusion that it is the strongest.** It ties with `qwen3.7-max` on the
   total and its gaps with the other three are not statistically significant. It is chosen on
   the DB component, not on the overall ranking.
2. **DB 11/12 vs 9/12 has itself not been significance-tested** - n=12 is not enough there
   either. It is a **directional but unproven** signal.
3. **The cost interval is wide** (4.88 - 14.32 CNY per 12 tasks) because its cache discount is
   not published. The lower bound is comparable to `qwen3.7-max`'s 5.61 CNY, the upper bound is
   more than twice it. If the reality is near the upper bound, `qwen3.7-max` is the safer
   choice.

If cost dominates, `qwen3.8-flash` is 10-20x cheaper and statistically tied on the total - but
its **DB is only 6/12**, half its order operations are wrong, and it is unsuitable as the
subject of a business-correctness claim.

### 7.6 Next step

Per 6.3, run the selected model once on the **40-task holdout** (about 23 CNY) as an
independent verification. The holdout takes no part in selection and must not be used for
tuning.

To move round A's conclusion from "not separated" to "separated", the only way is more sample:
the full 74-task dev set for 2 candidates costs about 70 CNY. That is outside the one-round
plan, and whether to do it is your decision.

## 8. Round V: independent verification on the holdout (2026-09-06, executed)

`qwen3.8-max` x 40 holdout tasks x 1 trial, concurrency 4 (thinking level as described in
9.5.1), with **no early stopping** - verification needs complete numbers and must not be cut
short. The holdout took no part in selection and was not used for any tuning.

| Metric | Value |
|---|---|
| **Mean reward** | **0.8000 (32/40)** |
| 95% confidence interval | [0.65, 0.90] |
| DB | 32/40 |
| NL | **39/39** (task 33 is DB-only with no assertions and is excluded) |
| Termination | all 40 ended normally |
| Duration | 22.8 minutes |
| Subject cost | 15.74 - 46.94 CNY |
| Judge | 11 calls, 0.0882 CNY |

**This 0.80 is the project's first clean independent number**: it comes from a task set that
took no part in selection, was not looked at before the run, and after which nothing was tuned.

### 8.1 But the reason for choosing it did not reproduce on the holdout

The only argument for `qwen3.8-max` was its lead on the DB component (dev 11/12 = 0.92). On the
holdout **DB drops to 32/40 = 0.80**.

More notably, the composition of failures inverted entirely:

| | DB failures | NL failures |
|---|---|---|
| Dev, 12 tasks | 1 | **2** |
| Holdout, 40 tasks | **8** | **0** |

On dev it was "good at the database, incomplete in what it says"; on the holdout it is "says
everything right, gets the database wrong 8 times".

The two sets' confidence intervals overlap (0.92 and 0.80 are not contradictory at n=12 and
n=40), so this **does not overturn** the earlier result, but it does show one thing: **the
directional signal in 7.5 is weaker than it looked**. It was already stated there that "DB 11/12
vs 9/12 has not been significance-tested", and the holdout confirms that reservation was
necessary.

### 8.2 Conclusion

What may go into a report:

- `qwen3.8-max` scores **0.800 (32/40)** on the 40-task tau2-bench Retail holdout, 95% CI
  [0.65, 0.90], with all runs terminating normally.
- The number comes from an independent task set that took no part in selection or tuning and is
  reproducible.
- Every failure is on the DB component (8/8), with **zero NL assertion failures**.

What may not:

- **It may not be called the best of the five candidates.** All 10 pairwise comparisons in round
  A were not significant, and the DB advantage on which it was chosen did not reproduce on the
  holdout.
- 0.800 may not be compared with round A's 0.750 to conclude "better" - the two task sets differ
  in difficulty and in sample size.

### 8.3 Cost correction

The "about 23 CNY for the holdout" in 7.6 was **wrong**: that figure used `qwen3.7-max`'s
prices while the run actually used `qwen3.8-max`, whose cache discount is not published, giving
an actual interval of **15.74 - 46.94 CNY**.

M0.4's total actual spend is about **33 - 80 CNY** (A0 1.15 + round A 16-32 + re-judging 0.35 +
round V 15.74-46.94). The interval is that wide entirely because of the three candidates'
unpublished cache discounts, which is missing price information rather than a problem with the
estimation method.

## 9. The selection decision and the harness (2026-09-06)

**`deepseek-v4-pro` is selected, on DeepSeek's own endpoint. The rest of the harness is built
around it.**

### 9.1 The decision rests on cost, not on "it is the strongest"

This distinction must be stated consistently and never blurred in a report:

| | `deepseek-v4-pro` | `qwen3.8-max` |
|---|---|---|
| Holdout, 40 tasks | **0.600** (24/40) | 0.800 (32/40) |
| 95% CI | [0.45, 0.74] | [0.65, 0.90] |
| DB | 24/40 | 32/40 |
| Cost | **0.079 CNY per task** | 0.419 CNY per task |

McNemar paired test on the same 40 tasks: `qwen3.8-max` wins 12 tasks alone,
`deepseek-v4-pro` wins 4 alone, **p = 0.077 - not significant**, but the closest to significance
of any comparison in this project (the previous minimum was p=0.375).

**This is a real trade-off between cost and business correctness**: about 0.34 CNY saved per
task, at the price of possibly one more wrong order in five. In retail a wrong order is
irreversible, so this is a business judgement rather than a technical conclusion. The choice is
the project owner's; this document's job is to quantify the cost and record it.

### 9.2 The dev 12/12 is an illusion and must be written down

`deepseek-v4-pro` scored **1.000 (12/12)** on the 12 dev tasks and only **0.600** on the
holdout.

Forty percentage points apart. The reasons were stated at the time: the CI at 12 tasks is
already as wide as [0.76, 1.00], and those 12 tasks had been used repeatedly while selecting
among candidates. **A perfect score on a small sample is not capability.** This is the first
time this project observed the phenomenon directly, and it is more persuasive than any
admonition.

### 9.3 Key finding: this model is conservative about writes

All 16 holdout failures are **DB failures** (NL assertions 38/39), and in **11 of them the agent
never issued a single write** - it kept explaining, confirming and confirming again without
acting.

| | Failures with no write ever issued | Writes issued across 40 tasks |
|---|---|---|
| `deepseek-v4-pro` | **11 / 16** | 36 |
| `qwen3.8-max` | 4 / 8 | 54 |

A third fewer writes on the same 40 tasks. This is not random variation but a **behavioural
characteristic**.

The application-side demo reproduces the same phenomenon: on the `return` flow (which carries 5
item ids) it asked "please reply yes" again on the third turn, never issued the write, and the
database stayed untouched, while `cancel` (one order id) needed only three turns. The more
arguments there are, the more likely it is to confirm once more.

**The guard is not at fault** - it correctly held the write; the model itself never issued the
call again. `scripts/demo_flows.py`'s return flow therefore allows one extra turn, with the
reason recorded in a code comment.

**Operational implication**: this model is more likely to do too little than to do the wrong
thing. For irreversible writes, doing too little is safer than doing the wrong thing, but task
completion rates fall - and that is exactly what the 0.600 is made of.

Four rules that live in code rather than documentation:

1. **The application and the evaluation share `Settings.agent_endpoint()`** - if the two hit

2. **Switching the model under test must never change `RSA_OPENAI_BASE_URL`** - that would move

3. **Provider-specific parameters go only to that provider**: `enable_thinking` is a DashScope

4. **`SELECTED_MODEL` and the candidate pool's `deepseek-v4-pro-0813` are two different

### 9.5 Two methodological flaws that must be recorded

**One: the holdout has been used twice** (once for `qwen3.8-max`, once for
`deepseek-v4-pro`). A holdout's value comes from being used once, and using it twice discounts
its independence.

The defensible framing is: **the model was selected on cost first, and the holdout verified it
afterwards** - decide, then verify, not verify then pick. **These two scores must never be
compared to make the selection**, which would invalidate both at once.

**Two: temperature and endpoint were changed together.** Two variables moved at once
(temperature default -> 0.0, DashScope -> DeepSeek's own endpoint), so the dev improvement from
0.500 to 1.000 can only be attributed to one of them or to both together. Separating them would
require running `deepseek-v4-pro-0813` on DashScope at temp=0 again (about 5 CNY), which
**has not been done**.

## 9.5 The thinking configuration (2026-09-06, corrected against DeepSeek's documentation)

Based on <https://api-docs.deepseek.com/guides/thinking_mode> and
<https://api-docs.deepseek.com/api/create-chat-completion> (checked 2026-09-06).

### 9.5.1 Three long-standing deviations that never raised an error

**(1) Every earlier run in fact had thinking on, at level high.**

The code says `ThinkingConfig(enabled=False)`, and sections 5, 7 and 8 of this document say
"non-thinking mode" in several places. Both are wrong: we never sent DeepSeek any thinking
parameter, and DeepSeek **has thinking on by default with `reasoning_effort` defaulting to
`high`**. Measured: 190 of 214 calls on the subject side produced reasoning tokens (median 70).

Impact: rounds A and V remain valid in themselves (they really were measured under
thinking+high), but the "non-thinking" label has to be withdrawn from those sections, or someone
reproducing from the label later would get a different configuration.

**(2) `temperature` has no effect in thinking mode.**

From the documentation: thinking mode does not support `temperature`, `top_p`,
`presence_penalty` or `frequency_penalty`, and "for compatibility with existing software,
setting them does not raise an error but has no effect".

So the "agent temperature defect fixed" recorded in section 9 **does not apply to
deepseek-v4-pro**: the `temperature: 0.0` that was fixed was discarded server-side all along.
It now works as: with DeepSeek and thinking enabled, **no temperature is sent**, so the manifest
does not record a reproducible sampling setting that does not exist. The DashScope candidates
are unaffected and still send it.

**(3) With `tools` present, `reasoning_content` must be sent back, and we were not sending it.**

From the documentation: if a request **carries the `tools` parameter**, the `reasoning_content`
of previous turns should all be returned to the API and will be concatenated into the context.
tau2-bench's agent carries tools every turn, while upstream's `to_litellm_messages()` returns
only `content` and `tool_calls`. The result is that the model never sees its own reasoning from
the previous turn - no error, just worse performance.

Fixed: `evaluation.echo_reasoning_content()` recovers `reasoning_content` from
`AssistantMessage.raw_data` and adds it back to the request body (upstream has always stored it,
it simply never translated it back); the application side does the same in
`agent._assistant_message()`.

**This changes scores**, in an untested direction. Rounds A and V were scored without reasoning
context.

### 9.5.2 The three roles after the configuration was fixed

| Role | Endpoint | Thinking | Level | Temperature |
|---|---|---|---|---|
| Subject `deepseek-v4-pro` | DeepSeek's own | `thinking.type=enabled` | `reasoning_effort=high` | not sent (the server discards it) |

> The table is deliberately left as it was: every number in 9.6 and earlier was measured with

This section originally said that raising the level from the server default to high made the
exam harder, so rounds A and V would not be directly comparable with later runs. **Measurement

The simulated user's reasoning-token distribution across three 24-task runs:

| `20260906T192002Z` | none (server default) | 462 | 589 | 2040 |
| `20260906T204001Z` | `reasoning_effort=high` | 418 | 588 | 1666 |
| `20260906T210443Z` | `reasoning_effort=high` | 456 | 633 | 1929 |

### 9.5.3b The valid values of `reasoning_effort` differ by provider, and a wrong one is a 400 rather than a silent ignore

DashScope's API reference page returns 404, so the valid values could only be obtained from an
error message:

```
'reasoning_effort' must be one of: 'none', 'minimal', 'low', 'medium', 'high', 'xhigh'
```

| Provider | Valid values | Note |
|---|---|---|
| DeepSeek | `low` `high` `max` | `medium`/`xhigh` are mapped onto `high` |
| DashScope | `none` `minimal` `low` `medium` `high` `xhigh` | **no `max`** |

`VALID_EFFORTS` previously used DeepSeek's set globally, so:

- **`--thinking max` against a DashScope endpoint would return 400 and crash a whole evaluation
  round** (a latent defect, now fixed);
- `medium` and `xhigh`, both valid on DashScope, were blocked by our own code.

Validation is now per provider (`DEEPSEEK_EFFORTS` / `DASHSCOPE_EFFORTS`) and raises at send
time, when the target provider is known. `high` is valid on both, so the "standardize on high"
convention holds. `tests/test_deepseek_contract.py` pins it down.

### 9.5.4 The judge now uses protocol-level enforced JSON (measured 2026-09-06)

Upstream calls `json.loads()` on the judge's reply and then reads `result["expectedOutcome"]`,
so a parse failure or a missing key crashes the whole round - which is exactly how
`qwen3.7-flash` crashed once. Rather than asking for JSON in the prompt, require it at the
protocol level.

**Measurement design**: the 11 saved traces of
`20260906T182221Z_deepseek-v4-pro_holdout`, with each of three settings run twice (66 judge
calls in total, spending only judge-side tokens and nothing on the agent side).

| Setting | Parseable | Input tok | Output tok | Assertions flipping between the two passes | Differing from the baseline judgement |
|---|---|---|---|---|---|
| A no `response_format` | 22/22 | 92 596 | 3 270 | **1** | baseline |
| B `json_object` | 22/22 | 92 640 | 3 201 | 0 | 1 (the unstable one from A) |
| C `json_schema` strict | 22/22 | 92 640 | 3 281 | 0 | **0** |

Conclusions:

- None of the three had a parse failure - but 22 samples cannot demonstrate a robustness
  difference, and the earlier crash was caused by **thinking being on** and mixing reasoning into
  `content`, which is separately solved by `enable_thinking=false`.
- **Without `response_format` the judge contradicts itself**: the same judge, the same
  assertion and the same input gave different conclusions across two passes. That is precisely
  the noise most worth eliminating, since the reward is all or nothing and one jitter takes a
  task from full marks to zero.
- `json_schema` was chosen over `json_object`: the latter only guarantees valid JSON, while the
  former also guarantees the keys exist, and upstream is equally intolerant of a missing key.
  Measured, `json_schema`'s judgements match the baseline exactly, at a cost of 11 extra output
  tokens.

**Graded by model capability** (`evaluation.judge_response_format()`): on DashScope, strict
`json_schema` is supported only by the Qwen3.7-Plus/Flash/Max and Qwen3.8-Max/Flash families.
The fallback judge `qwen3.6-plus` is not on that list and falls back to `json_object`; forcing
it would raise. `json_object` mode requires the word "json" to appear in the messages, and
upstream's prompt contains "JSON object", which satisfies it.

End-to-end verification (`recheck_judge.py --repeat 2`): 0 disagreements, 0 self-contradictions,
0.0017 CNY.

The judge's prices are now in `pricing.py` (input 0.1 / output 0.4 / cache 0.01 CNY per million
tokens), but **the source is second-hand reporting** because the official pricing page loads
dynamically via JS and cannot be scraped; they must be checked against the bill before any
external report.

## 9.6 The max thinking level experiment, and a more important finding: run-to-run noise (2026-09-06)

### 9.6.1 Four runs

All on the same stratified sample of 24 dev tasks (identical task sets), subject
`deepseek-v4-pro`.

| Run | Harness | Level | Passed | 95% Wilson |
|---|---|---|---|---|
| `20260906T192002Z` | old | high (simulated user at the server default level) | 18/24 = 0.750 | [0.551, 0.880] |
| `20260906T204001Z` | new (9.5) | high | 12/24 = 0.500 | [0.314, 0.686] |
| `20260906T210443Z` | new | high (**exact repeat**) | 14/24 = 0.583 | [0.388, 0.755] |
| `20260906T205134Z` | new | **max** | 17/24 = 0.708 | [0.508, 0.851] |

Paired McNemar exact tests: **none of the four comparisons is significant**:

| Comparison | Fixed | Broke | p |
|---|---|---|---|
| new high#1 vs old high | 1 | 7 | 0.0703 |
| max vs new high#1 | 7 | 2 | 0.1797 |
| max vs new high#2 | 5 | 2 | 0.4531 |
| max vs old high | 2 | 3 | 1.0000 |
| **new high#2 vs new high#1 (same configuration)** | 4 | 2 | 0.6875 |

### 9.6.2 The noise floor: the same configuration on the same tasks flips 25% of them

The last row is the most valuable output of this experiment. Two runs with **identical
configuration** differ on 6 of 24 tasks (1, 11, 15, 20, 22, 29).

The mechanism is clear: **DeepSeek's thinking mode ignores `temperature`** (9.5.1), so the model
under test cannot be pinned to deterministic behaviour. This is not a fixable defect but this
provider's established behaviour.

The consequences have to be written into every conclusion:

- **Any single 24-task score carries a jitter of plus or minus 2-3 tasks.**
  The apparent "6 tasks lost with the new harness" in 9.6.1 does not survive comparison with the
  repeat run.
- The selection conclusions in sections 7 and 8 are equally affected. `deepseek-v4-pro`'s 0.600
  versus `qwen3.8-max`'s 0.800 on the 40-task holdout with McNemar p=0.077 is also **one run
  each**, with no noise floor underneath. The direction may still hold, but calling it
  "verified" was premature.

### 9.6.3 Is max worth its 13% extra cost: look again with the noisy tasks removed

Aligning the per-task results of the two high runs with max and classifying by stability:

| Category | Tasks | Task ids |
|---|---|---|
| Both high runs pass, max passes | 8 | 0, 10, 13, 14, 24, 25, 28, 30 |
| Both high runs fail, **max passes** (max's unique gain) | **3** | 4, 6, 19 |
| Both high runs pass, **max fails** (max's unique loss) | **2** | 2, 16 |
| Both high runs fail, max fails | 5 | 3, 7, 8, 21, 23 |
| The two high runs contradict each other (noisy tasks) | 6 | 1, 11, 15, 20, 22, 29 |

**On the 18 stable tasks, max nets one extra task.** Its apparent +4 advantage comes mostly from
happening to pass all 6 noisy tasks.

That 6/6 is worth noting: if max were no different from high on these borderline tasks, the
probability of getting all of them is 1/64. But **the set of noisy tasks was defined after
seeing high's results**, so there is selection bias and it cannot serve as a test. It is a
hypothesis to be verified - max may genuinely be better on borderline tasks - not a conclusion.

The cost is certain: output goes from 74 132 to 87 220 tokens (reasoning 50 318 to 62 458,
+24%), which converts to 1.594 -> 1.806 CNY per 24 tasks, **+13%**.

**Conclusion: do not switch to max; the production level stays `high`.**
Netting one task out of 18 stable ones does not justify a permanent 13% cost. Confirming the
"better on borderline tasks" hypothesis would require the 40-task holdout or 3-plus repeats, at
about 6-10 CNY. Whether to spend that is a business judgement.

### 9.6.4 Constraints on later experiment methodology

1. **A single run's result must not be used for ranking.** Any model or configuration comparison
   needs a noise floor underneath it, or a task count large enough for noise to be negligible.
2. Reported scores must always carry Wilson intervals - the four runs' intervals all overlap
   pairwise, which is invisible from the point estimates alone (0.500 / 0.583 / 0.708 / 0.750).
3. `scripts/compare_runs.py` fixes the paired-comparison convention (McNemar exact test plus
   usage and cost) so it is no longer recomputed ad hoc each time. Its numerical correctness is
   pinned by closed-form hand calculations in `tests/test_compare_runs.py`.

## 9.7 Reviewing the cost conventions: caching, per-role costs and Langfuse (2026-09-06)

### 9.7.1 Cached and uncached input are separate, but the two providers report differently

`Price.cost()` always prices the hit and miss portions separately rather than estimating at full
price. The question is **whether upstream reports it**:

| Role | Endpoint | Cache field | Measured |
|---|---|---|---|
| Subject `deepseek-v4-pro` | DeepSeek | `prompt_cache_hit_tokens` + `prompt_tokens_details.cached_tokens` | both returned, hit rate **95%** |
| Simulated user `qwen3.6-plus` | DashScope | `prompt_tokens_details.cached_tokens` | always **`null`** |
| Judge `qwen3.7-flash` | DashScope | as above | 0 during a run (one call per task, no shared prefix); 48% when re-judging offline |

The simulated user's row was previously recorded as a 0% hit rate, which reads as "confirmed no
cache benefit" when in fact the server never reported anything. It now tracks
`cache_unreported` separately, is written explicitly as **unknown** in reports, and is converted
at full price (conservative, overestimating rather than underestimating).

**Why nothing is reported**: Qwen's context-caching documentation states that the **minimum
cacheable length for implicit caching is 1024 tokens**. The simulated user's median input is
only 848 tokens, and measurement shows only 43 of 120 calls (36%) reach the threshold; the rest
never enter the cache at all. So this is not a missed statistic - it simply gets almost no cache
benefit. That also explains why its input is 6% of the subject's while its cost is 68% of it:
95% of the subject's input is billed at 20%, while the simulated user is billed at nearly full
price throughout.

The two cache pricing schemes in the documentation (implicit hit 20%, explicit hit 10%, explicit
creation 125%, explicit TTL 5 minutes, prefix matching over only the last 20 content blocks)
agree with `DASHSCOPE_IMPLICIT_CACHE_RATIO = 0.20` in `pricing.py`, so nothing needs changing.
Explicit caching would gain this project nothing: the simulated user does not reach the
threshold, and the judge's conversation differs per task with no shared prefix.

The judge's zero cache during a run is correct rather than a missed statistic: each task's
conversation differs, so there is no reusable prefix. Only offline re-judging
(`recheck_judge.py --repeat`) repeats the same prompts, and there the hit rate is 48%.

### 9.7.2 Per-role cost: the simulated user is 40% of the total and was previously counted as 0

`qwen3.6-plus-2026-04-02` was never in the price snapshot, so `analyze_eval.py` could only print
"not in the price snapshot, cannot convert" - which in a report has the same effect as counting
it as 0. With prices added, taking `20260906T205134Z` (the max round, 24 tasks) as an example:

| Role | Input tok | Cache hits | Output tok | Of which reasoning | Cost |
|---|---|---|---|---|---|
| Subject deepseek-v4-pro | 1 667 394 | 95% | 87 220 | 62 458 | 1.8059 CNY |
| Simulated user qwen3.6-plus | 101 046 | unknown | 85 173 | 79 805 | **1.2242 CNY** |
| Judge qwen3.7-flash | 42 722 | 0 | 1 092 | 0 | 0.0047 CNY |
| **Total** | | | | | **3.0348 CNY (0.1265 CNY per task)** |

The simulated user's input is only 6% of the subject's while its cost is 68% of it, for two
reasons: its unit price is higher in effect (output 12 CNY/M versus 13.5, but **without a 95%
cache discount**), and **94% of its output is reasoning tokens**, all billed at the output price.

**This changes the earlier per-task cost convention**: the 0.079 CNY per task recorded in section
9 counted only the subject side. All three roles together are 0.1265 CNY per task, about 1.6x.
Relative conclusions across models are unchanged (the evaluation stack's cost is independent of
the model under test and is a common term), but a total budget reported externally must use the

`analyze_eval.py --project N` now projects and itemizes the evaluation stack's cost as well.

### 9.7.3 Langfuse: not wired up, and wiring it up today would show fake numbers

Verified state:

- The `langfuse` package is **not installed**;
- upstream's `tau2/config.py` has `USE_LANGFUSE = False`;
- our own code has never referenced it. The several mentions in the documentation are plans, not
  the current state.

More importantly: upstream enables Langfuse through
`litellm.success_callback = ["langfuse"]`, with cost numbers supplied by litellm's
`completion_cost()`. litellm **does not recognize** DashScope's or DeepSeek's models, and
`get_response_cost()` catches the exception and returns 0.0 - which is exactly why
`agent_cost_reported_by_upstream` is always 0.0.

So turning Langfuse on today would show **0 CNY per call**, landing squarely on the prohibition
`docs/EVALUATION_AND_GATES.md` sets for itself: a missing cost must not be recorded as free when
the price is unverified.

### 9.7.4 Two other things checked but not applicable here

- **`preserve_thinking`** (DashScope): concatenates the assistant's `reasoning_content` into the
  next turn, DashScope's counterpart of DeepSeek's "return reasoning when tools are present".
  **Not enabled**: it affects only the simulated user and the judge (the subject is on
  DeepSeek's side), the simulated user is part of the frozen stack, and the documentation states
  that once enabled the historical `reasoning_content` counts as input tokens and is billed -
  which for a role whose output is 94% reasoning would raise cost significantly.
- **Batch inference**: priced at **50%** of real-time calls, supported by qwen3.6-plus, returned
  within 24 hours. **Not applicable**: an evaluation is a multi-turn conversation where each turn
  depends on the previous result, so it cannot be submitted in batch by nature. The only
  batchable part is offline re-judging, which already costs 0.002 CNY. Batch results also
  **contain no `reasoning_content`**, which conflicts with the judge's explainability
  requirement.

### 9.7.5 One thing that must be done before wiring up Langfuse

Use `litellm.register_model()` (confirmed working in 1.82.6) to register `pricing.py`'s price
snapshot into litellm so `completion_cost()` computes real numbers. Then `agent_cost` and the
Langfuse dashboard both become accurate at once rather than each computing its own answer. Note
DeepSeek's peak/off-peak pricing: litellm's price table is static and a registered price cannot
vary by time of day, so either fix it at the peak price (conservative) or convert separately in
the report.

## 9.8 Replacing the simulated user: glm-5.3-flash (2026-09-07)

### 9.8.1 Motivation and method

The simulated user is about 40% of the three-role cost (9.7.2), which makes it worth pricing
separately. But **cost alone must not decide the choice**: the simulated user sets the exam, and
a worse one makes the agent's score **rise** - measured once on 2026-09-06, turning the
simulated user's thinking off raised the score from 18/24 to 23/24 because it broke composite
tasks into single ones.

So this comparison uses two conventions at once, neither optional:

| Convention | Tool | Role |
|---|---|---|
| Agent score | `scripts/compare_runs.py` | Paired McNemar exact test, **used only to detect a difference** |
| Simulated-user quality | `scripts/review_user_sim.py` | Upstream's `UserOnlyReviewer`, **used to judge whether the direction of that difference is credible** |

The reviewing model is fixed at `qwen3.8-max` across candidates, otherwise the comparison is of
reviewers rather than of simulated users. Everything but the simulated user is identical between
the two runs: the same 24 tasks (`--sample 24`, task sets checked item by item), the same subject
(deepseek-v4-pro, thinking high), the same judge and the same seed.

### 9.8.2 Results

| | Baseline `qwen3.6-plus-2026-04-02` | Candidate `glm-5.3-flash` |
|---|---|---|
| Agent score | 14/24 | **23/24** |
| Of the 9 tasks that really call the judge | 4/9 | 9/9 |
| Simulated-user errors found by review | 3 (1 `critical_hindered` + 2 `minor`) | **0** |
| Simulated-user cost | 1.0929 CNY | **0.1018 CNY** |
| Three-role total | 2.7376 CNY | **2.0278 CNY** (0.0845 CNY per task) |
| Mean duration | 103 s per task | 61 s per task |

McNemar exact test **p = 0.0117** (10 tasks fixed, 1 broken). This is the first paired
comparison in this project to reach significance (the previous ones were
p = 0.070 / 0.180 / 0.453 / 1.000 / 0.688).

Run directories: baseline `20260906T210443Z_deepseek-v4-pro_dev`, candidate
`20260906T230617Z_deepseek-v4-pro_dev`.

### 9.8.3 Root cause: the old simulated user was cutting the exam short

The score difference alone is not an argument, since the noise floor measured in 9.6.2 is 25%.
What settles it is that **the mechanism is checkable**.

Task 15, in each simulated user's own words:

```
qwen3.6-plus (score 0, ends after 3 user turns)
  "Yes, that's correct. Please go ahead with the update and
   process the refund to my PayPal account. Thank you. ###STOP###"

glm-5.3-flash (score 1, 5 user turns)
  "...Please go ahead with that change."      <- waits for the agent to execute
  "Great, that's everything I needed. Thanks for your help!"
  "###STOP###"                                 <- stops only after confirmation
```

qwen put "please go ahead" and `###STOP###` in the same message, so **the agent had no turn in
which to perform the modification**. It is not that the agent could not do it; the exam gave it
no chance to act.

This pattern holds in 9 of the 10 flipped tasks - GLM consistently uses 1-2 more user turns:

| Task | qwen user turns | glm user turns |
|---|---|---|
| 3 | 5 | 5 |
| 4 | 4 | 5 |
| 6 | 7 | 6 |
| 7 | 6 | 6 |
| 8 | 5 | 6 |
| 15 | 3 | 5 |
| 19 | 4 | 5 |
| 21 | 4 | 5 |
| 23 | 4 | 6 |
| 29 | 4 | 5 |

Review independently caught a `critical_hindered` on task 3 as well: qwen read "modify **all**
your pending small tshirt" as "modify only the order that is already small" and said explicitly
"The XXL order can stay exactly as it is", making the task impossible to complete.

### 9.8.4 Why this is not "the exam was made easier"

That is exactly the risk 9.8.1 warns about, so it is ruled out point by point:

1. The reviewing model found **0 `critical_helped`** across GLM's 24 sessions, with all 24
   reviewed and none skipped;
2. On task 22, the only one lost, GLM used 11 user turns and 36 messages and review judged the
   simulated user to have followed its instructions exactly - the failure came from the agent
   changing the default address back, which is the exam working normally;
3. The subject-side cost **rose** (1.6399 -> 1.9207 CNY): sessions got longer, not shorter, and
   going easy would shorten them.

### 9.8.5 A counter-intuitive side finding: the winner thinks less

| | Reasoning tokens per call |
|---|---|
| qwen3.6-plus @ high | 633 (70259 over 111 calls) |
| glm-5.3-flash @ high | **19** (2822 over 145 calls) |

GLM is heavily suppressed at level `high` (single-probe measurement: no parameter 2698, `low` 0,
`high` 151, `max` 2874), yet it did not make qwen's fatal sequencing error.

This overturns a note left before the switch, which worried that `high` would weaken GLM and
that a `max` round would be needed before concluding. **It is not needed**: GLM won with its
thinking depth heavily suppressed, and adding `max` would only widen its margin.

Conclusion: the simulated user's quality bottleneck is not thinking depth but **when it says
stop**. The observation in 9.5.3 that levels barely affect qwen is confirmed here from another
direction: neither model is a good simulated user by virtue of thinking more.

### 9.8.6 The four costs of the switch (all recorded in code)

The switch is not free. Each cost is written into a test rather than remembered:

| Cost | Consequence | Where it is recorded |
|---|---|---|
| **No dated snapshot id** | Zhipu provides no `glm-5.3-flash-2026xxxx` (official documentation checked 2026-09-07). If they swap the model behind the alias, only a re-run would reveal it | `test_frozen_user_simulator_alias_risk_is_recorded` |
| **Loss of the thinking-off control switch** | The GLM-5.3 family forces thinking server-side (400 code 1210), so `--user-no-thinking` is unusable with it | `test_disabling_thinking_fails_at_setup_not_mid_run`; `EvalStack.__post_init__` raises at construction rather than midway through a batch |
| **Temperature is no longer ours to control** | Zhipu fixes temperature at 1.0 in thinking mode and sending 0 has no effect, so nothing is sent | `test_frozen_stack_drops_temperature_on_zhipu` |
| **Same family as the candidate glm-5.2** | With glm-5.2 as the subject, the simulated user is from the same family, and the warning now appears every round | `test_frozen_user_simulator_collides_with_a_candidate_family` (the warning is kept, not silenced) |

Also, **changing the simulated user makes every earlier score incomparable**. The old model is
therefore kept as `evaluation.PREVIOUS_USER_SIMULATOR` with its prices retained in `pricing.py`:
reproducing a historical conclusion just passes `user_model=PREVIOUS_USER_SIMULATOR`, which
routes back to DashScope automatically.

### 9.8.7 A real bug fixed along the way

`EvalStack.__post_init__` previously used `RSA_USER_MODEL` to **unconditionally override** an
explicitly passed `user_model`. It never surfaced because before the switch nobody needed to
specify the simulated user explicitly. Afterwards that path became essential (for reproducing
history) and the problem appeared: following the error message's own advice and passing
`user_model=...` was silently overridden by the environment variable.

The precedence is now **explicit argument > environment variable > frozen default**, consistent
with the judge.

### 9.8.8 Not yet verified

- Only one run each on the 24-task dev split. The 25% noise floor still applies; this time the
  p-value and the mechanism evidence are both solid enough, but before a holdout re-check the
  23/24 must not be read as the agent's real level - **it measures the exam under the new
  simulated user, not an improved agent**.
- Whether GLM would be better still at level `max` is untested (by the reasoning in 9.8.5 it
  should not be needed, but untested is untested).
- The GLM simulated user has never been run on the full 114-task set.


## 9.9 Independent verification on a clean evaluation stack (2026-09-07)

### 9.9.1 Why a re-run was necessary

One of M0.5's acceptance conditions is that independent verification is complete and **the
conclusion suffices to support the model selection**. Reviewing the existing evidence showed it
does not: the whole selection rests on two holdout runs, and **those two used different judges**:

| Run | Subject | Score | Judge | Simulated user | Judge JSON |
|---|---|---|---|---|---|
| `20260906T165340Z` | qwen3.8-max | 32/40 (0.800) | `deepseek-v4-flash` | qwen3.6-plus | none |
| `20260906T182221Z` | deepseek-v4-pro | 24/40 (0.600) | `qwen3.7-flash` | qwen3.6-plus | none |

0.800 versus 0.600 is not a gap between models but **two numbers measured with two different
rulers**.

And this is not limited to those two runs: round A's 12-task comparison of all 5 candidates was
judged entirely by `deepseek-v4-flash`, while every `deepseek-v4-pro` round was judged entirely
by `qwen3.7-flash` - **the model that was selected has never been measured with the same ruler
as its competitors.**

Add two defects fixed only recently: both runs used the old simulated user that cuts
conversations short (9.8), and neither judge had a `response_format` (9.5.4). So the selection
evidence fails on three independent points.

### 9.9.2 Results

The same 40 holdout tasks and the same subject model, with only the evaluation stack changed:

| | Old stack (09-06) | New stack (09-07) |
|---|---|---|
| Perfect scores | 24/40 = 0.600 | **35/40 = 0.875** |
| Fixed | - | 14 tasks |
| Broken | - | 3 tasks |
| Of the 11 tasks needing the judge | 5/11 | 9/11 |
| Cost per task | 0.1279 CNY | **0.0806 CNY** |

**McNemar exact test p = 0.0127; the difference is significant.**

Run directory `20260907T080504Z_deepseek-v4-pro_holdout`. The three-role cost totals 3.2241 CNY
(subject 3.0312 + simulated user 0.1898 + judge 0.0031, DeepSeek off-peak).

### 9.9.4 Effect on the selection conclusion

The earlier statement was "deepseek-v4-pro is 5x cheaper, at the price of possibly one more
wrong order in five" (0.600 against qwen3.8-max's 0.800). It is now **0.875 against 0.800**: the
cost advantage is unchanged, and the "worse quality" price does not hold on a clean stack.

But **that must not be written as a conclusion**: qwen3.8-max's 0.800 was measured on the dirty
stack, and comparing it directly with a clean-stack 0.875 is the "two rulers" problem criticized
at the start of this section.

The decision is **not to re-measure qwen3.8-max**: at 0.3877 CNY per task against 0.0806, it is
4.8x more expensive, in an entirely different range, and better quality would not change the
selection. The selection convention is therefore recorded explicitly as:

> **A cost decision.** deepseek-v4-pro costs 0.0806 CNY per task and scores 0.875 on the holdout
> with a clean evaluation stack. No other candidate has been measured on the same stack, and
> **this project does not claim to have made a cross-model quality comparison.** All of round A's
> cross-model numbers are void because the judges were inconsistent.

### 9.9.5 A by-product: protection against lost tasks

Halfway through this run, the judge model's server-side quota ran out and **5 tasks never
started**. The problem is not the fault itself but what happened afterwards:

upstream **dropped those 5 tasks from the denominator**, and `avg_reward` displayed **0.886**;
the real score once they were filled in is **0.875**.

**Losing tasks raises no error and makes the score look better.** That is far more dangerous than
an outright crash, because nothing but reading the logs would reveal it.

Three layers of protection were added (see `tests/test_incomplete_run_guard.py`):

| Layer | Location | Behaviour |
|---|---|---|
| Detect | `run_eval.summarize(sims, expected)` | Reconcile completed sessions against the expected count |
| Record | `summary.json` | Write `incomplete` / `expected_count` / `unscored_task_ids` |
| Refuse | `analyze_eval.py` | On a gap, **do not report a mean score** unless `--allow-incomplete` is passed explicitly |

One deliberate trade-off: `avg_reward` itself **keeps its convention**. Replacing the denominator
with `expected` would count unrun tasks as 0, which is equally fabricated. The right response is
to refuse to treat the number as a score, not to substitute a different wrong one.

The companion `scripts/resume_run.py` resumes the missing tasks and merges them back into the
original directory. It checks only the parts **resolved from the environment** (the simulated
user, the judge, the judge's JSON format and the three endpoints); run parameters are copied
from the manifest, so checking them would be comparing a thing with itself. A stack mismatch is
refused: resumed tasks must run on the same stack as the original round, or merging them back
produces a mixture of two stacks, which is exactly the problem in 9.9.1.

`results_io.load_simulations` was correspondingly changed to deduplicate by `task_id#trial`,
with a scored record overriding an unscored one; different trials are still kept separately so a
multi-trial repeat experiment is not mistaken for a resume.
