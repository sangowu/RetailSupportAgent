# M0.4 选型实验：评测栈冻结、冒烟结果与成本估算

状态：**选型已定——`deepseek-v4-pro`（DeepSeek 官方端点），依据是成本而非最优成绩；保留集 0.600（24/40），harness 已围绕它定型**。日期：2026-09-06。

## 1. 评测栈已冻结

上游的编排器、模拟用户与评分器一律不重写，只做两件接线工作：把 litellm 路由指向
DashScope 的 OpenAI 兼容端点；把 NL 断言评判模型从上游默认的 `gpt-4.1`（无访问权限）
换成账户内可用的固定模型。

| 角色 | 模型 | 端点 | 为什么是它 |
|---|---|---|---|
| 被测 Agent | 5 个候选模型轮换 | DashScope | 实验对象 |
| 模拟用户 | `qwen3.6-plus-2026-04-02` | DashScope | **候选池外**，带日期快照 |
| NL 断言评判 | `deepseek-v4-flash` | **DeepSeek（独立）** | 候选池外；额度与被测账户隔离 |

判官放在独立服务商上，是因为被测账户处于「仅免费额度」模式（见第 4 节）：
**被测模型额度耗尽时，判官不应跟着一起挂掉**，否则连"跑到哪里失败的"都判不出来。
`RSA_JUDGE_BASE_URL` / `RSA_JUDGE_API_KEY` / `RSA_JUDGE_MODEL` 三项齐全才启用独立端点，
只配一半会**退回**默认判官而不是拿错误的 Key 去请求。

**已知风险（必须随成绩一起报告）**：`deepseek-v4-flash` 与候选模型
`deepseek-v4-pro-0813` 同属 `deepseek-v4` 家族。精确匹配拦不住这种同源关系，
所以 `EvalStack.warnings()` 按**家族**另做一次比对，把这条警告写进每次运行的
manifest。同源模型可能系统性偏爱自家风格的输出——解读 `deepseek-v4-pro-0813`
的成绩时必须注明此风险，不能等别人来指出。

两条纪律写进了代码而不只是文档：`EvalStack` 在构造时会检查模拟用户与评判模型
**是否落在候选池里，是则直接抛错**。理由是自评偏袒——让候选模型给自己打分，
比较结论就不成立了。选带日期的快照而非别名，是因为别名可能在服务端被悄悄更新，
导致今天和下周的成绩不可比。

评测栈温度固定 0.0，与上游默认一致。

```python
# tau2/evaluator/evaluator_nl_assertions.py
if not nl_assertions:
    return RewardInfo(reward=1.0, ..., info={"note": "No nl_assertions to evaluate"})
```

因此本次冒烟验证的是：任务加载、工具调用、模拟用户、DB 比对、结果落盘。
**判官链路从未被执行过**，此前"NL 评判正常"的说法应按此更正。
`scripts/run_eval.py --pilot` 已改为只挑真正带断言的题（现为 dev 的 `2`、`3`），
并加了回归测试钉住"开发集前两题不带断言"这个事实。

原始轨迹保存在运行目录下（未入库，体积约 100KB/题）；`summary.json` 已入库，
报告里的每个数字都能回溯到具体运行。

## 3. 成本模型（已按实测重算，此前高估约一倍）

**上游报的 `agent_cost` 恒为 0**——litellm 不知道 DashScope 与 DeepSeek 的价格。
成本必须自己算，`scripts/analyze_eval.py` 按 token 用量乘价格快照折算，并注明取价日期。

### 3.1 此前漏掉的三笔账

上游的 `get_response_usage()` 只保留两个字段：

```python
# tau2/utils/llm_utils.py
return {"completion_tokens": usage.completion_tokens, "prompt_tokens": usage.prompt_tokens}
```

`prompt_tokens_details.cached_tokens` 与 `completion_tokens_details.reasoning_tokens`
被直接丢掉。所幸完整响应一直存在 `message.raw_data` 里，**历史结果可以回溯**。
回溯冒烟那次运行，拿到三个此前不知道的事实：

| 发现 | 实测 | 后果 |
|---|---|---|
| DashScope 隐式缓存**一直在命中** | 被测侧 129262 输入 tok 中 **93312 命中（72%）** | 成本被**高估约一倍** |
| 模拟用户跑在**思考模式** | 输出 4980 tok 中 **4451 是 reasoning（89%）** | 一笔从未计入的支出 |
| 判官调用不在 messages 里 | 此前只能写"未知" | 未知≠零，需单独记账 |

隐式缓存默认开启且无法关闭，命中部分按输入价的 **20%** 计费。
但 `qwen3.8-max`、`qwen3.8-flash`、`deepseek-v4-pro` 是文档明确列出的**例外**，
折扣需查控制台——我们拿不到，因此对这三个模型**只给区间，不给假装精确的数字**，
且上界按全价计（宁可高估，不可低估）。

判官用量现由 `JudgeUsageRecorder` 包住评判模块的 `generate` 单独记账，
写进每次运行的 `summary.json`。

### 3.2 重算后的成本

实测每题用量（被测 Agent 侧）：**输入 64631 tok（其中 46656 命中缓存），输出 2851 tok**。
输入远大于输出，因为每轮都要重发完整政策（6699 字符）与全部 16 个工具定义——
也正因为这部分是稳定前缀，缓存命中率才有 72%。

跑完开发集 74 题的单模型成本：

| 模型 | 74 题（新） | 74 题（旧，未计缓存） |
|---|---|---|
| `qwen3.7-max-2026-06-08` | **31.8 元** | 65.0 元 |
| `qwen3.8-max` | 31.8 – 65.0 元 | 65.0 元 |
| `deepseek-v4-pro-0813` | 29.3 – 62.5 元 | 62.5 元 |
| `glm-5.2` | **22.1 元** | 44.2 元 |
| `qwen3.8-flash` | **2.2 – 4.4 元** | 4.4 元 |

区间的模型是缓存折扣未公开的那三个：下界按 20% 折扣估，上界按无折扣估。

**仍未计入的部分**：

- 模拟用户：用量已实测（每题约 4930 输入 / 2490 输出，其中 89% 是推理 token），
  但 `qwen3.6-plus` 单价未取得，仍无法折算。
- 上表原写"基于非思考模式"，**已证伪**：DeepSeek 默认开思考、默认 high，
  既往数据实际都含推理 token。详见 §9.5。
- 不同模型话多话少、缓存命中率不同，用参照模型的用量推算其他模型必然有偏差。

### 3.3 判官成本（DeepSeek 独立端点）

判官走 DeepSeek 官方端点，与 DashScope 上同名的 `deepseek-v4-pro-0813`
**不是一套价格**，代码里两者严格区分。DeepSeek 有峰谷价，谷时是峰时的一半：

| | 缓存命中 | 缓存未命中 | 输出 |
|---|---|---|---|
| `deepseek-v4-flash` 高峰 | 0.10 | 3.0 | 9.0 |
| `deepseek-v4-flash` 空闲 | 0.05 | 1.5 | 4.5 |

单位元/百万 token。高峰＝北京时间周一至周五 9:00–12:00、14:00–18:00
（＝UTC 01:00–04:00、06:00–10:00），其余时段与周末为空闲。
`deepseek_tier()` 按调用时刻自动判定，复判报告里会注明用的哪一档。

一次典型判定约 6k 输入、300 输出 → **高峰约 0.02 元，空闲约 0.01 元**。
判官便宜，但不是零；错在把"统计不到"当成"不花钱"。

## 4. 账户问题：处于「仅使用免费额度」模式

探测候选池外模型时拿到这条服务端响应：

```
403 - Free quota exhausted. To continue accessing the model on a paid basis,
please add funds or disable the "use free tier only" mode in the management console.
```

含义与影响：

1. 账户当前是**只用免费额度**的模式。M0.2 报告里那句"本次实测总成本约 0.31 元"
   是按价格快照折算的**理论值**，实际很可能消耗的是免费额度而非真实扣费——
   该说法应按此更正。
2. 已有若干模型的免费额度耗尽（如 `qwen3.7-plus-2026-05-26`）。
3. **全量实验很可能在跑到一半时因额度耗尽而失败**，留下不完整、不可比的结果。

因此全量实验开跑前必须先确认：额度是否够，或者是否要关掉「仅免费额度」模式改为付费。
这不是技术问题，需要账户持有人决定。

## 5. 判官的真实影响面（此前被高估了三倍）

从上游任务文件实测，不是从文档抄的：

| 口径 | 数量 |
|---|---|
| `reward_basis` 里**声明** NL_ASSERTION | 112 / 114 |
| **实际带断言、真的会调判官** | **40 / 114** |
| 声明了但断言列表为空 → 自动记 1.0 | 72 |

开发集 74 题里只有 **29 题**会调判官，保留集 40 题里只有 **11 题**。
此前"112 题走 DB × NL_ASSERTION"的说法应按此更正。

但在那 40 题上，判官依然是决定性的，因为上游对断言是**全有全无**：

```python
all_expectations_met = all(result.met for result in nl_assertions_checks)
reward = 1.0 if all_expectations_met else 0.0
```

判官在任意一条断言上抖一下，整题直接从 1.0 掉到 0.0。噪声不会被平均掉，只会被放大。
所以样本里必须保证有足够的带断言题，`--sample` 因此按判官覆盖比例分层抽取，
而不是朴素截断前 N 题。

## 6. 实验设计：一轮定模型

单题成本按冒烟实测用量（输入 64631 tok，其中 46656 命中缓存；输出 2851 tok）折算：

| 模型 | 元/题 |
|---|---|
| `qwen3.7-max-2026-06-08` | 0.430 |
| `qwen3.8-max` | 0.430 – 0.878 |
| `deepseek-v4-pro-0813` | 0.396 – 0.844 |
| `glm-5.2` | 0.298 |
| `qwen3.8-flash` | 0.030 – 0.059 |
| **五模型合计** | **1.58 – 2.51** |

五个候选跑同一批题的规模—成本对照（Agent 侧）：

| 题数 | 会话数 | 计入缓存后 | 旧估算 |
|---|---|---|---|
| 4 | 20 | 6.3 – 10.0 元 | 13.0 元 |
| **6** | **30** | **9.5 – 15.1 元** | 19.5 元 |
| 8 | 40 | 12.7 – 20.1 元 | 26.1 元 |
| **12（已确认）** | **60** | **19.0 – 30.1 元** | 39.1 元 |

缓存把预算砍掉约一半。既然只跑一轮、没有后续档位兜底，
就不该再按「还有下一档」的思路省题——**已确认取 12 题**，
判官覆盖从 6 题时的 2 题提升到 5 题。

**决策：一轮定模型。** 原来的 A→B→C→D 四档漏斗已取消。

| 步骤 | 内容 | 会话数 | 估算 | 状态 |
|---|---|---|---|---|
| **A0 判官可信度** | 2 题（带断言）跑一次 + 离线复判 ×3 | 2 | 1.15 元（实际） | **已完成，见 6.4** |
| **A 选型（唯一一轮）** | 5 模型 × 分层抽样 **12 题** × 1 次，思考 high（见 §9.5） | 60 | 16 – 32 元（实际） | **已完成，见 7** |
| V 独立验证 | `qwen3.8-max` × 保留集 40 题 × 1 次 | 40 | 15.74 – 46.94 元（实际） | **已完成，见 8** |

**合计约 50 – 72 元。**

比上一版（32–48 元）高，原因是 A0 实测出的用量比首次冒烟大得多：
**每题输入 115805 tok，而首次冒烟只有 64631**。带 NL 断言的题对话更长——
首次冒烟抽到的恰好是两道不带断言的短题，用它推算全局会**低估**。
现在的估算基于带断言的题，偏保守，这个方向是对的。

12 题里有 **5 题**会真正调用判官（`2, 3, 4, 16, 19`），其余 7 题只考 DB 比对。

### 6.1 轮内提前终止

一轮定模型意味着没有后续档位兜底，但也没必要给一个明显不合格的配置把 12 题跑完：

```bash
uv run python scripts/run_eval.py --model <M> --sample 12 --early-stop 4
```

先跑前 4 题，平均奖励 ≤ 0.001（即全零）就掐掉，剩下 8 题不跑。分段落盘，
读取时由 `results_io.load_simulations()` 合并回一次运行，
`summary.json` 里记 `stopped_early` 与 `completed_task_ids`。

两条纪律写进了代码：**未评分的模拟不算作 0 分**（否则会误杀一个其实没跑完的模型），
以及分段**不得丢题或改顺序**。

### 6.2 结论怎么写

一轮 12 题得出的是**筛选结论**，不是排名结论。报告口径必须是：

- 可以写：「X 在本样本上通过，Y 明显不合格（前 4 题全零，已提前终止）」
- **不可以写**：「X 比 Y 强 3 个百分点」——12 题分不出几个百分点的差距

若第一名与第二名差距很小，就写成「二者在本样本上未区分开，选 X 基于成本/延迟」。
这个项目的卖点是评测严谨，口径错了反而扣分。

### 6.3 为什么保留独立验证

选定模型后在**保留集 40 题**上跑一次，约 12–17 元，只跑一个模型。
这个数字**没有参与选型**，是干净的独立验证——对一个以「可复现评测」为卖点的项目，
报告里有这么一行的分量，比多跑两个候选大得多。保留集**不得用于调参**。

思考模式（`--thinking`）的比较已随 B 档一并取消。若将来要做，
注意：现有估算原以为基于非思考模式，实为服务端默认的 thinking+high（见 §9.5.1），
所以估算并未低估思考带来的输出膨胀。

### 6.4 A0 判官可信度结果（2026-09-06，已执行）

判官换成 `deepseek-v4-flash`（DeepSeek 独立端点）后的第一次真实执行。
**此前所有运行都没有真正调用过判官**，这是第一次。

被测 `qwen3.7-max-2026-06-08` 跑 dev 的 `2`、`3` 两题（均带 NL 断言）：

| 指标 | 值 |
|---|---|
| 平均奖励 | 1.0000（2/2） |
| 判官调用 | 2 次，输入 11238 tok，输出 308 tok |
| 被测成本 | 1.1347 元 |
| 判官成本 | 0.0182 元 |

随后用同一判官对**已保存的轨迹**离线复判 3 轮（Agent 侧零成本）：

| 检查项 | 结果 |
|---|---|
| 同一判官自相矛盾的题数 | **0 / 2** |
| 与原判官（`qwen3.6-plus`）分歧 | **0 / 2 条断言** |
| 复判花费 | 0.0067 元（空闲时段） |
| DeepSeek 缓存命中率 | **99%**（33408/33714） |

**结论：判官可用，可以往下走。**

**但这个结论的强度必须说清楚**：样本只有 **2 条断言**。零分歧证明的是
「没发现问题」，不是「判官很稳」——2 条断言不足以测出百分之几的抖动率。
真正的判官噪声数据要等 A 轮跑完（5 题带断言 × 5 模型 = 25 次判定）再回头复判。

顺带两个观察：

- `deepseek-v4-flash` 自己也在思考（1005 输出 tok 里 505 是 reasoning）。
- 重复判定同样内容时 DeepSeek 缓存命中率 99%，所以**复判几乎不要钱**——
  这让「换判官后整体重判历史结果」从"要重新花一笔"变成"几分钱的事"。

**A0 是新增的一步，也是最该先做的一步。** 它几乎不花钱，却能回答一个
在花掉后面几百元之前必须先确认的问题：判官本身稳不稳。做法是对**已保存的轨迹**
重新判定——判官只吃"对话 + 断言"，两者都在结果文件里，所以复判**不重跑 Agent**，
只花判官那一侧的 token：

```bash
uv run python scripts/recheck_judge.py --run <目录名> --repeat 3
```

它同时回答两件事：同一判官多轮之间自不自洽（`--repeat`），以及新旧判官之间
分歧多少。**分歧多不代表新判官更差，只代表两者不可互换**——一旦换判官，
历史成绩必须整体重判，不能新旧混用。

关于压到 6 题的诚实说明：**6 题只能做筛选，不能做排名。** 它足以淘汰
"连工具都调不对"这类明显不合格的配置；但候选之间若只差几个百分点，
任何小样本都区分不出来，那要留到阶段 C。缩小规模买的是"早点淘汰废配置"，
不是"早点得出结论"。

分层抽样规则（保证可复现）：按该划分"带断言 / 不带断言"的原有比例取，
落在冻结清单的原始顺序上——不引入随机数，不同机器抽出的样本必然一致，
选中的题号写进运行 manifest。

**那个"比砍题数更大的杠杆"已经查清了**：每题输入 64631 tok 占成本的 88%，
其中绝大部分是每轮重发的政策文本与 16 个工具定义。这部分是稳定前缀，
DashScope 的隐式缓存**一直在命中，命中率 72%**（见 3.1）。所以预算减半不是靠砍题，
是靠把本来就发生了、却没被统计的折扣算进来。

反过来说，**别做任何会打断前缀稳定性的改动**——比如把政策文本或工具定义
放到对话中间、或每轮变动系统提示——那会让命中率掉下来，成本立刻翻倍。

## 7. A 轮结果（2026-09-06，已执行）

5 个候选 × 开发集分层抽样 12 题 × 1 次，`--early-stop 4`，并发 4。
（当时记作"非思考"，实为服务端默认的 thinking+high，见 §9.5.1）
**5 个模型全部跑完，无一触发提前终止，无一遇到额度 403。**

| 模型 | 平均奖励 | DB | NL | 12 题成本 |
|---|---|---|---|---|
| `qwen3.8-max` | 0.7500 (9/12) | **11/12** | 10/12 | 4.88 – 14.32 元 |
| `qwen3.7-max-2026-06-08` | 0.7500 (9/12) | 9/12 | **12/12** | 5.61 元 |
| `glm-5.2` | 0.5833 (7/12) | 9/12 | 9/12 | 2.40 元 |
| `qwen3.8-flash` | 0.5000 (6/12) | 6/12 | **12/12** | **0.24 – 0.76 元** |
| `deepseek-v4-pro-0813` | 0.5000 (6/12) | 7/12 | 10/12 | 3.17 – 8.56 元 |

全部 60 个会话均正常结束（`USER_STOP`）。A 轮实际花费约 **16 – 32 元**，
低于 25–48 元的估算。

### 7.2 统计结论：这一轮没有区分出任何一对模型

| 模型 | 通过率 | 95% 置信区间（Wilson, n=12） |
|---|---|---|
| `qwen3.8-max` / `qwen3.7-max` | 0.750 | [0.47, 0.91] |
| `glm-5.2` | 0.583 | [0.32, 0.81] |
| `qwen3.8-flash` / `deepseek-v4-pro-0813` | 0.500 | [0.25, 0.75] |

同一批 12 题是配对数据，用 McNemar 精确检验做两两比较，**10 对全部不显著**，
最小 p = 0.375（`qwen3.8-flash` vs `qwen3.8-max`）。最大的那个差距
（0.75 vs 0.50）对应 p = 0.453。

**所以按 6.2 预先约定的口径，这里不能写"X 比 Y 强"。**
12 题的样本量本就分不出几个百分点乃至二十几个百分点的差距——
这不是意外，是 6.2 里已经写明的限制。

### 7.3 判官噪声：8%，与模型间差距同量级

对全部 5 次运行离线复判 3 轮（25 个题级判定、30 条断言），Agent 侧零成本，
合计花费 **0.35 元**：

| 指标 | 结果 |
|---|---|
| 同一判官自相矛盾 | **2 / 25 题（8%）** |
| 与原判官（`qwen3.6-plus`）分歧 | 2 / 30 条断言 |

两次分歧指向同一条断言：

> Agent should tell the user that exchanging the pet bed and office chair saves $4

**这个数字很关键**：判官自身 8% 的抖动，与模型之间那些本就不显著的差距是同一量级。
换句话说，即使 12 题跑出了差距，也无法排除是判官抖出来的。
这印证了当初坚持"判官必须独立、必须先验一致性"的判断。

### 7.4 一个比总分更有意义的分化

总分区分不开，但 DB 与 NL 两半的表现明显不同——**DB 是程序化比对，不经过判官，
是这五个数字里唯一不含判官噪声的**：

- `qwen3.8-max`：DB **11/12**，NL 10/12 → 该做的数据库操作几乎都做对了，
  但有两次"没说对话"。这两次 NL 失败经 3 轮复判**稳定复现，不是判官噪声**。
- `qwen3.7-max` 与 `qwen3.8-flash`：NL **12/12**，全部失败都出在 DB。
- `qwen3.8-flash` 的 DB 只有 6/12——**便宜十倍，但一半的订单操作是错的**。

对一个零售客服 Agent，**写错数据库比说错话严重**。取消错订单、退错款是不可逆的；
话说得不够全，用户还会再问一句。

### 7.5 选型建议

**建议 `qwen3.8-max`**，理由只有一条经得起推敲：它在**唯一不含判官噪声的指标**
（DB 11/12）上领先，而这个指标对应的正是本项目声称要保证的业务正确性。

必须同时说明的三件事：

1. **这不是"它最强"的结论**。总分上它与 `qwen3.7-max` 打平，与其余三个的差距
   统计上不显著。选它是基于 DB 这一分项，不是基于总分排名。
2. **DB 11/12 vs 9/12 本身也没做显著性检验**——n=12 同样不够。这是一个
   **有方向性但未被证实**的信号。
3. **成本区间很宽**（4.88 – 14.32 元/12 题），因为它的缓存折扣未公开。
   下界与 `qwen3.7-max` 的 5.61 元相当，上界则是它的两倍多。若实际接近上界，
   `qwen3.7-max` 是更稳妥的选择。

若优先考虑成本，`qwen3.8-flash` 便宜 10–20 倍且总分统计上打平——
但 **DB 只有 6/12**，一半的订单操作出错，不适合作为业务正确性的主张对象。

保留集不参与选型，也不得用于调参。

## 9. 选型决定与 harness 定型（2026-09-06）

**选定 `deepseek-v4-pro`，走 DeepSeek 官方端点。后续 harness 围绕它搭建。**

### 9.1 决定依据是成本，不是"它最强"

这个区别必须一直说清楚，报告里也不许含糊：

| | `deepseek-v4-pro` | `qwen3.8-max` |
|---|---|---|
| 保留集 40 题 | **0.600**（24/40） | 0.800（32/40） |
| 95% CI | [0.45, 0.74] | [0.65, 0.90] |
| DB | 24/40 | 32/40 |
| 成本 | **0.079 元/题** | 0.419 元/题 |

McNemar 配对检验（同一批 40 题）：`qwen3.8-max` 独赢 12 题，`deepseek-v4-pro` 独赢 4 题，
**p = 0.077——未达显著**，但这是本项目所有比较里最接近显著的一次（此前最小 p=0.375）。

**这是成本与业务正确性的真实权衡**：每题省约 0.34 元，代价是每 5 单可能多错 1 单。
零售场景里错单不可逆，这笔账属于业务判断，不是技术结论。选择由项目所有者做出，
本文档负责把代价量化并留痕。

### 9.2 开发集 12/12 是假象，必须记下来

`deepseek-v4-pro` 在开发集 12 题上拿了 **1.000（12/12）**，保留集只有 **0.600**。

差 40 个百分点。原因是当时就写明的两条：12 题的 CI 本就宽到 [0.76, 1.00]；
且那 12 题是所有候选选型时反复用过的题。**小样本上的满分不是实力。**
这是本项目第一次直接观测到这个现象，比任何说教都有说服力。

### 9.3 关键发现：这个模型在写操作上偏保守

保留集 16 个失败**全部是 DB 失败**（NL 断言 38/39），其中 **11 题 Agent 一次写操作都没调**——
它一直在解释、确认、再确认，就是不动手。

| | 失败题中"从未调写" | 40 题共发起写操作 |
|---|---|---|
| `deepseek-v4-pro` | **11 / 16** | 36 次 |
| `qwen3.8-max` | 4 / 8 | 54 次 |

同样 40 道题，写操作次数少了三分之一。这不是随机波动，是**行为特征**。

应用侧 demo 复现了同一现象：`return` 流程（要带 5 个商品 ID）第三轮它又问了一遍
"请回复是"，写操作始终没发出，DB 纹丝不动；而 `cancel`（只带一个订单号）三轮就够。
参数越多越倾向于再确认一次。

**护栏没有问题**——它正确地扣住了写操作；是模型自己没有再次发起调用。
`scripts/demo_flows.py` 的退货流程因此多给一轮，并在代码注释里写明了原因。

**运营含义**：这个模型更可能"少做"而不是"做错"。对不可逆的写操作，
少做比做错安全，但任务完成率会下降——0.600 这个数字的构成正是如此。

### 9.4 harness 定型

| 项 | 值 | 位置 |
|---|---|---|
| 生产模型 | `deepseek-v4-pro` | `config.SELECTED_MODEL` |
| 端点 | DeepSeek 官方 | `RSA_AGENT_BASE_URL` / `RSA_AGENT_API_KEY` |
| 温度 | **0.0** | `llm.ModelConfig` / `evaluation.AGENT_TEMPERATURE` |
| 思考 | 关闭 | `ThinkingConfig(enabled=False)` |
| 模拟用户 | `qwen3.6-plus-2026-04-02` @ DashScope | **不变**，冻结栈 |
| NL 判官 | `qwen3.7-flash-2026-07-15` @ DashScope，**强制关思考** | `RSA_JUDGE_*` |

四条写进代码而非文档的纪律：

1. **应用与评测共用 `Settings.agent_endpoint()`**——两边打到不同服务商，
   评测成绩对线上就没有解释力。`tests/test_harness_wiring.py` 钉死。
2. **切换被测模型绝不能改 `RSA_OPENAI_BASE_URL`**——那会把模拟用户一起改掉。
3. **服务商专有参数只发给它自己**：`enable_thinking` 是 DashScope 扩展，
   不发给 DeepSeek。
4. **`SELECTED_MODEL` 与候选池里的 `deepseek-v4-pro-0813` 是两个东西**：
   后者是 DashScope 上的同款，价格是前者的 3~5 倍，名字混用会按错的价目表折算。

### 9.5 两处必须留痕的方法学瑕疵

**一、保留集已被使用两次**（`qwen3.8-max` 一次、`deepseek-v4-pro` 一次）。
保留集的价值来自只用一次，用两次其独立性即打折扣。

站得住的口径是：**模型基于成本选定在先，保留集验证在后**——先定后验，不是先验后挑。
**绝不能拿这两个分数比高低来选型**，那会让两个数字同时失效。

**二、温度与端点的混淆未分离**。这次同时改了两个变量（温度默认→0.0、
DashScope→DeepSeek 官方），所以开发集 0.500→1.000 的提升只能归因于"两者之一或共同作用"。
要分离需让 `deepseek-v4-pro-0813` 在 DashScope 上以 temp=0 再跑一次（约 5 元），**尚未执行**。

## 9.5 思考配置定型（2026-09-06，据 DeepSeek 官方文档修正）

依据 <https://api-docs.deepseek.com/zh-cn/guides/thinking_mode> 与
<https://api-docs.deepseek.com/zh-cn/api/create-chat-completion>（2026-09-06 查阅）。

### 9.5.1 三条一直存在、但从不报错的偏差

**（1）此前所有运行其实都开着思考，且档位是 high。**

代码里写的是 `ThinkingConfig(enabled=False)`，本文档 §5/§7/§8 多处写"非思考模式"。
两者都是错的：我们从未向 DeepSeek 下发过任何思考参数，而 DeepSeek
**默认开启思考、`reasoning_effort` 默认 `high`**。实测被测侧 214 次调用中
190 次产生了推理 token（中位数 70）。

影响面：A 轮与 V 轮的成绩本身有效（它们确实是在 thinking+high 下测得的），
但"非思考"这个标签必须从上述章节撤掉——否则日后有人照着标签复现，会得到不同配置。

**（2）思考模式下 `temperature` 不生效。**

原文：「思考模式不支持 `temperature`、`top_p`、`presence_penalty`、`frequency_penalty` 参数」，
且「为了兼容已有软件，设置参数不会报错，但也不会生效」。

所以 §9 里记的"agent 温度缺陷已修复"对 **deepseek-v4-pro 无效**——修好的那个
`temperature: 0.0` 从头到尾都被服务端丢弃。现在改为：DeepSeek + 思考开启时**不发**温度，
免得 manifest 记下一个不存在的"可复现采样设置"。DashScope 侧候选模型不受影响，照发。

**（3）带 `tools` 时 `reasoning_content` 必须回传，我们没回传。**

原文：「若请求**携带 `tools` 参数**：历史轮次的 `reasoning_content` 均应回传给 API，
并会被拼接进上下文。」τ²-bench 的 Agent 每轮都带 tools，而上游
`to_litellm_messages()` 只回传 `content` 与 `tool_calls`。
结果是模型每一轮都看不到自己上一轮的推理——不报错，只是变笨。

已修：`evaluation.echo_reasoning_content()` 从 `AssistantMessage.raw_data`
里把 `reasoning_content` 取回来补进请求体（上游一直存着，只是没翻译回去）；
应用侧 `agent._assistant_message()` 同样补上。

**这条会改变成绩**，方向未测。A/V 两轮的分数是在"没有推理上下文"的条件下取得的。

### 9.5.2 定型后的三个角色

| 角色 | 端点 | 思考 | 档位 | 温度 |
|---|---|---|---|---|
| 被测 `deepseek-v4-pro` | DeepSeek 官方 | `thinking.type=enabled` | `reasoning_effort=high` | 不下发（服务端会丢弃） |
| 模拟用户 `qwen3.6-plus-2026-04-02` | DashScope | `enable_thinking=true` | `reasoning_effort=high` | 0.0 |
| NL 判官 `qwen3.7-flash-2026-07-15` | DashScope | `enable_thinking=false` | — | 0.0 |

> **2026-09-07 更新**：模拟用户已换成 `glm-5.3-flash`（智谱 open.bigmodel.cn），
> 方言是**顶层** `thinking={"type":"enabled"}` + 顶层 `reasoning_effort=high`，
> 温度不下发（服务端固定 1.0）。理由与四项代价见 §9.8。
> 上表保留原样是**故意的**——§9.6 及更早的全部数字都是在旧模拟用户下测的。

档位取值只允许 `low / high / max`：DeepSeek 会把 `medium`、`xhigh` 都映射成 `high`，
写它们会让 manifest 记录的档位与真实生效的档位对不上。由 `llm.VALID_EFFORTS` 强制。

### 9.5.3 模拟用户下发了显式档位——但**实测证明它几乎没有效果**（2026-09-06 更正）

原先此处写的是「把档位从服务端默认提到 high，等于把考卷改难，A/V 两轮成绩与
此后的运行不可直接比较」。**这个说法已被实测推翻**，保留原文以便追溯。

三轮 24 题运行里模拟用户的推理 token 分布：

| 运行 | 下发的档位 | 中位数 | 均值 | 最大 |
|---|---|---|---|---|
| `20260906T192002Z` | 不下发（服务端默认） | 462 | 589 | 2040 |
| `20260906T204001Z` | `reasoning_effort=high` | 418 | 588 | 1666 |
| `20260906T210443Z` | `reasoning_effort=high` | 456 | 633 | 1929 |

三者分布无差别。单点对照实测（同一提示词、逐档位）也一样：

| 档位 | qwen3.6-plus 推理 tok | qwen3.7-flash 推理 tok |
|---|---|---|
| 不设参数 | 1344 | 1181 |
| low | 1293 | 1112 |
| medium | 1493 | 1240 |
| high | 1263 | 999 |
| xhigh | 1558 | 1166 |
| **thinking_budget=256** | **256** | **256** |

**`reasoning_effort` 在这两个模型上是个软提示，效果落在噪声里；
`thinking_budget` 才是硬约束（设 256 就精确停在 256）。**

结论修正：
- 模拟用户的行为**没有改变**，所以旧运行与新运行在这一维度上**仍然可比**。
  §9.6 里"新 harness 掉了 6 题"的表象因此更明确地归因于运行间噪声。
- 想真正钉住模拟用户的思考深度，只能用 `thinking_budget`，不能用 `reasoning_effort`。
  但那会改变冻结栈行为（实测 A/B 已证明模拟用户思考量直接决定考卷难度），
  **本步不做**，留作显式待决项。

### 9.5.3b `reasoning_effort` 的合法取值两家不同，发错会 400（不是静默忽略）

DashScope 的 API 参考页 404，取值只能从错误信息里拿到：

```
'reasoning_effort' must be one of: 'none', 'minimal', 'low', 'medium', 'high', 'xhigh'
```

| 服务商 | 合法取值 | 备注 |
|---|---|---|
| DeepSeek | `low` `high` `max` | `medium`/`xhigh` 被映射成 `high` |
| DashScope | `none` `minimal` `low` `medium` `high` `xhigh` | **没有 `max`** |

此前 `VALID_EFFORTS` 用的是 DeepSeek 那套并全局套用，于是：
- **`--thinking max` 打到 DashScope 端点会直接 400，把整轮评测跑崩**（潜在缺陷，已修）；
- `medium`/`xhigh` 这两个 DashScope 合法值被我们自己拦掉了。

现改为按服务商分别校验（`DEEPSEEK_EFFORTS` / `DASHSCOPE_EFFORTS`），
在下发时（那时才知道打到哪家）抛错。`high` 是两家都合法的取值，
所以「统一 high」这个口径成立。由 `tests/test_deepseek_contract.py` 钉死。

### 9.5.4 判官改用协议层强制 JSON（2026-09-06 已实测）

上游拿到判官回复后直接 `json.loads()`，再按键取 `result["expectedOutcome"]`——
解析失败和缺键都会把整轮跑崩，`qwen3.7-flash` 就因此崩过一次。
与其在提示词里求它输出 JSON，不如在协议层要求。

**实测设计**：用 `20260906T182221Z_deepseek-v4-pro_holdout` 的 11 条已保存轨迹，
三种设置各跑 2 遍（共 66 次判官调用，只花判官侧 token，Agent 侧零成本）。

| 设置 | 可解析 | 输入 tok | 输出 tok | 两遍间翻转的断言 | 与基线判定不同 |
|---|---|---|---|---|---|
| A 不设 `response_format` | 22/22 | 92 596 | 3 270 | **1** | 基线 |
| B `json_object` | 22/22 | 92 640 | 3 201 | 0 | 1（即 A 不稳的那条） |
| C `json_schema` strict | 22/22 | 92 640 | 3 281 | 0 | **0** |

结论：
- 三种都没出现解析失败——但 22 个样本证明不了鲁棒性差异，之前那次崩溃的成因是
  **思考开着**把推理混进了 `content`，那一条已由 `enable_thinking=false` 单独解决。
- **不设 `response_format` 会自相矛盾**：同一判官、同一条断言、同样输入，两遍给出不同结论。
  这正是最该消除的噪声——奖励是全有全无，判官抖一下整题就从满分掉到零分。
- 选 `json_schema` 而不是 `json_object`：后者只保证是合法 JSON，前者还保证键存在，
  而上游对缺键同样零容错。实测 `json_schema` 的判定与基线完全一致，代价是输出多 11 tok。

**按模型能力分档**（`evaluation.judge_response_format()`）：`json_schema` 严格模式
DashScope 侧只支持 Qwen3.7-Plus/Flash/Max 与 Qwen3.8-Max/Flash 系列，
兜底判官 `qwen3.6-plus` 不在名单内，退回 `json_object`——强上会直接报错。
`json_object` 模式要求消息里出现 "json" 字样，上游提示词含 "JSON object"，满足。

全链路验证（`recheck_judge.py --repeat 2`）：0 分歧、0 自相矛盾、0.0017 元。

判官单价已补进 `pricing.py`（输入 0.1 / 输出 0.4 / 缓存 0.01 元每百万 token），
但**来源是二手报道**，官方定价页 JS 动态加载抓不到；对外报告前需按账单核对。

## 9.6 思考档位 max 实验，以及一个更重要的发现：运行间噪声（2026-09-06）

### 9.6.1 四次运行

全部 dev 分层抽样 24 题（题集完全相同），被测 `deepseek-v4-pro`。

| 运行 | harness | 档位 | 通过 | 95% Wilson |
|---|---|---|---|---|
| `20260906T192002Z` | 旧 | high（模拟用户跑服务端默认档位） | 18/24 = 0.750 | [0.551, 0.880] |
| `20260906T204001Z` | 新（§9.5） | high | 12/24 = 0.500 | [0.314, 0.686] |
| `20260906T210443Z` | 新 | high（**原样重复**） | 14/24 = 0.583 | [0.388, 0.755] |
| `20260906T205134Z` | 新 | **max** | 17/24 = 0.708 | [0.508, 0.851] |

配对 McNemar 精确检验，**四组比较没有一组显著**：

| 比较 | 修好 | 弄坏 | p |
|---|---|---|---|
| 新 high#1 vs 旧 high | 1 | 7 | 0.0703 |
| max vs 新 high#1 | 7 | 2 | 0.1797 |
| max vs 新 high#2 | 5 | 2 | 0.4531 |
| max vs 旧 high | 2 | 3 | 1.0000 |
| **新 high#2 vs 新 high#1（同配置）** | 4 | 2 | 0.6875 |

### 9.6.2 噪声底：同一配置、同一批题，25% 的题会翻转

最后一行才是本次实验最有价值的产出。两次**配置完全相同**的运行，
6/24 题结果不同（题号 1、11、15、20、22、29）。

机制清楚：**DeepSeek 思考模式忽略 `temperature`**（§9.5.1），
我们无法把被测模型钉成确定性的。这不是可以修的缺陷，是这个服务商的既定行为。

后果必须写进所有结论：
- **任何单轮 24 题的成绩，本身带 ±2~3 题的抖动。**
  §9.6.1 里那个"新 harness 掉了 6 题"的表象，与重复轮一对比就站不住了。
- §7/§8 的选型结论同样受影响。保留集 40 题上 `deepseek-v4-pro` 0.600
  vs `qwen3.8-max` 0.800、McNemar p=0.077——那也是**各跑一轮**的结果，
  没有噪声底垫在下面。结论方向可能仍然成立，但"已验证"这个说法当时给早了。

### 9.6.3 max 到底值不值那 13% 成本：把噪声题剔掉再看

把两轮 high 的逐题结果与 max 对齐，按稳定性分类：

| 类别 | 题数 | 题号 |
|---|---|---|
| 两轮 high 都过，max 也过 | 8 | 0, 10, 13, 14, 24, 25, 28, 30 |
| 两轮 high 都没过，**max 过**（max 独有收益） | **3** | 4, 6, 19 |
| 两轮 high 都过，**max 没过**（max 独有损失） | **2** | 2, 16 |
| 两轮 high 都没过，max 也没过 | 5 | 3, 7, 8, 21, 23 |
| high 两轮自相矛盾（噪声题） | 6 | 1, 11, 15, 20, 22, 29 |

**在 18 道稳定题上，max 净赚 1 题。** 表面上那 +4 的优势，
主要来自 max 恰好通过了全部 6 道噪声题。

那 6/6 值得记一笔：若 max 在这些边缘题上与 high 无异，全中的概率是 1/64。
但**噪声题这个集合是看了 high 的结果之后才划出来的**，存在选择偏倚，
不能当成检验。它是一个待验证的假设——max 可能确实在边缘题上更强——不是结论。

成本代价是确定的：输出 74 132 → 87 220 tok（推理 50 318 → 62 458，+24%），
折算 1.594 → 1.806 元 / 24 题，**+13%**。

**结论：暂不切 max，生产档位保持 `high`。**
在 18 道稳定题上净赚 1 题，撑不起 13% 的常态成本；而那个"边缘题更强"的假设
要证实，需要保留集 40 题或 3 轮以上重复，约 6~10 元。这笔钱该不该花是业务判断。

### 9.6.4 对后续实验方法的约束

1. **单轮结果不得直接用于排名。**任何模型/配置比较至少要有噪声底垫底，
   或者把题量放大到噪声可忽略的规模。
2. 报告成绩必须同时给 Wilson 区间——四轮的区间两两重叠，
   这件事只看点估计（0.500 / 0.583 / 0.708 / 0.750）是看不出来的。
3. `scripts/compare_runs.py` 固定了配对比较口径（McNemar 精确检验 + 用量成本），
   不再每次临时算。它的数值正确性由 `tests/test_compare_runs.py` 用手算封闭解钉死。

## 9.7 成本口径复核：缓存、分角色、Langfuse（2026-09-06）

### 9.7.1 缓存与非缓存：分开的，但两家服务商的报法不同

`Price.cost()` 始终把命中部分与未命中部分分开计价，不是按全价估。
问题在于**上游报不报**：

| 角色 | 端点 | 缓存字段 | 实测 |
|---|---|---|---|
| 被测 `deepseek-v4-pro` | DeepSeek | `prompt_cache_hit_tokens` + `prompt_tokens_details.cached_tokens` | 都返回，命中率 **95%** |
| 模拟用户 `qwen3.6-plus` | DashScope | `prompt_tokens_details.cached_tokens` | 恒为 **`null`** |
| 判官 `qwen3.7-flash` | DashScope | 同上 | 运行中为 0（每题一次调用，无共享前缀）；离线复判重复判定时命中 48% |

模拟用户那一行此前被记成「命中率 0%」，读起来像"确认没有缓存收益"，
实际是"服务端根本没报"。已改为分别统计 `cache_unreported`，
报告里明确写成**未知**，并按全价折算（偏保守，宁可高估）。

**为什么没报**：千问上下文缓存文档写明隐式缓存的**最小缓存长度是 1024 token**。
模拟用户的输入中位数只有 848 tok，实测 120 次调用里只有 43 次（36%）够到门槛，
其余根本不进入缓存。所以这不是统计漏了，是它本来就基本吃不到缓存——
这也解释了为什么它输入只占被测的 6%、成本却是被测的 68%：
被测有 95% 的输入按 20% 计价，模拟用户几乎全按全价。

另外文档给出的两种缓存计价（隐式命中 20%、显式命中 10%、显式创建 125%、
显式有效期 5 分钟、前缀匹配只看最近 20 个 content 块）与 `pricing.py` 里
`DASHSCOPE_IMPLICIT_CACHE_RATIO = 0.20` 一致，无需改动。
显式缓存对本项目没有收益：模拟用户够不到门槛，判官每题对话都不同、无共享前缀。

判官运行中缓存为 0 是正确的，不是漏统计：每道题的对话都不同，没有可复用前缀。
离线复判（`recheck_judge.py --repeat`）才会重复同样的提示词，那时命中 48%。

### 9.7.2 分角色成本：模拟用户占 40%，此前按 0 记

`qwen3.6-plus-2026-04-02` 一直不在价格快照里，`analyze_eval.py` 只能输出
「不在价格快照里，无法折算」——在报告里的实际效果就是按 0 记。补价后：

以 `20260906T205134Z`（max 轮，24 题）为例：

| 角色 | 输入 tok | 缓存命中 | 输出 tok | 其中推理 | 成本 |
|---|---|---|---|---|---|
| 被测 deepseek-v4-pro | 1 667 394 | 95% | 87 220 | 62 458 | 1.8059 元 |
| 模拟用户 qwen3.6-plus | 101 046 | 未知 | 85 173 | 79 805 | **1.2242 元** |
| 判官 qwen3.7-flash | 42 722 | 0 | 1 092 | 0 | 0.0047 元 |
| **合计** | | | | | **3.0348 元（每题 0.1265 元）** |

模拟用户输入只有被测的 6%，成本却是被测的 68%——原因有两个：
它的单价更贵（输出 12 元/M vs 13.5，但**没有 95% 的缓存折扣**），
且 **94% 的输出是推理 token**，全按输出价计费。

**这改变了此前的每题成本口径**：§9 里记的 0.079 元/题只算了被测一侧。
三角色全算是 0.1265 元/题，约 1.6 倍。跨模型比较的相对结论不变
（评测栈成本与被测模型无关，是共同项），但对外报总预算时必须用后者。

`analyze_eval.py --project N` 现在会把评测栈成本一并推算并单列。
「缺价不等于免费」由 `tests/test_cost_accounting.py` 钉死：
`role_cost()` 对未知模型返回 `None` 而不是 0，合计遇到 `None` 只输出下界并注明。

### 9.7.3 Langfuse：**没接，而且现在接上会显示假数字**

现状核实：
- `langfuse` 包**未安装**；
- 上游 `tau2/config.py` 里 `USE_LANGFUSE = False`；
- 我们自己的代码从未引用过它。文档多处提到它，全是计划，不是现状。

更要紧的是：上游启用 Langfuse 的方式是
`litellm.success_callback = ["langfuse"]`，成本数字由 litellm 的
`completion_cost()` 提供。而 litellm **不认识** DashScope 与 DeepSeek 的型号，
`get_response_cost()` 捕获异常后直接 `return 0.0`——
这正是每次运行 `agent_cost_reported_by_upstream` 恒为 0.0 的原因。

所以今天直接打开 Langfuse，看到的会是**每次调用成本 0 元**，
恰好落进 `docs/EVALUATION_AND_GATES.md` 自己写下的禁令：
「未核验价格时不能把缺失成本记为免费」。

### 9.7.4 其余查证过、但本项目用不上的两项

- **`preserve_thinking`**（DashScope）：把 assistant 的 `reasoning_content` 拼进下一轮，
  是 DeepSeek「带 tools 时回传推理」的 DashScope 对应物。**未启用**：
  它只影响模拟用户与判官（被测已在 DeepSeek 侧），而模拟用户是冻结栈，
  且文档写明「启用后历史 `reasoning_content` 会计入输入 Token 并计费」——
  对一个 94% 输出都是推理的角色，这会显著推高成本。
- **Batch 批量推理**：价格是实时调用的 **50%**，qwen3.6-plus 支持，24 小时内返回。
  **用不上**：评测是多轮对话，每一轮都依赖上一轮的结果，天然无法批量提交；
  唯一能批的是离线复判，而那本来就只要 0.002 元。
  且批量结果**不含 `reasoning_content`**，与判官的可解释性要求冲突。

### 9.7.5 接入 Langfuse 前必须先做的一步

用 `litellm.register_model()`（1.82.6 已确认可用）
把 `pricing.py` 的价格快照注册进 litellm，让 `completion_cost()` 算出真实数字。
这样 `agent_cost` 与 Langfuse 面板会同时变准，而不是各算各的。
注意 DeepSeek 的峰谷价：litellm 的价格表是静态的，
注册进去的单价无法随时段变化，要么固定按峰时价（保守），要么在报告里另行折算。

## 9.8 更换模拟用户：glm-5.3-flash（2026-09-07）

### 9.8.1 起因与方法

模拟用户占三角色总成本约 40%（§9.7.2），值得单独比价。但**成本不能单独决定选型**：
模拟用户是出考题的，它变差会让 Agent 分数**上升**——2026-09-06 已实测过一次，
关掉模拟用户思考后分数从 18/24 涨到 23/24，原因是它把复合任务拆成了单任务。

所以这次对比同时看两个口径，缺一不可：

| 口径 | 工具 | 作用 |
|---|---|---|
| Agent 分数 | `scripts/compare_runs.py` | 配对 McNemar 精确检验，**只用来发现差异** |
| 模拟用户质量 | `scripts/review_user_sim.py` | 上游 `UserOnlyReviewer`，**用来判断差异的方向是否可信** |

审查模型跨候选固定为 `qwen3.8-max`，否则比的是审查模型而不是模拟用户。
两轮除模拟用户外全部相同：同 24 题（`--sample 24`，题目集逐一核对一致）、
同被测（deepseek-v4-pro，thinking high）、同判官、同 seed。

### 9.8.2 结果

| | 基线 `qwen3.6-plus-2026-04-02` | 对比 `glm-5.3-flash` |
|---|---|---|
| Agent 得分 | 14/24 | **23/24** |
| 其中真正调判官的 9 题 | 4/9 | 9/9 |
| 审查发现的模拟用户错误 | 3（1 `critical_hindered` + 2 `minor`） | **0** |
| 模拟用户成本 | 1.0929 元 | **0.1018 元** |
| 三角色合计 | 2.7376 元 | **2.0278 元**（0.0845 元/题） |
| 平均时长 | 103 秒/题 | 61 秒/题 |

McNemar 精确检验 **p = 0.0117**（修好 10 题，弄坏 1 题）。这是本项目做过的
所有配对比较里第一个达到显著的（此前依次为 p = 0.070 / 0.180 / 0.453 / 1.000 / 0.688）。

运行目录：基线 `20260906T210443Z_deepseek-v4-pro_dev`，
对比 `20260906T230617Z_deepseek-v4-pro_dev`。

### 9.8.3 根因：旧模拟用户在提前掐断考试

分数差本身不构成理由——§9.6.2 测得的噪声底是 25%。真正定案的是**机制可核对**。

题 15，两边模拟用户的原话：

```
qwen3.6-plus（0 分，3 个用户轮就结束）
  "Yes, that's correct. Please go ahead with the update and
   process the refund to my PayPal account. Thank you. ###STOP###"

glm-5.3-flash（1 分，5 个用户轮）
  "...Please go ahead with that change."      <- 等 Agent 执行
  "Great, that's everything I needed. Thanks for your help!"
  "###STOP###"                                 <- 确认后才停
```

qwen 把「请你去改」和 `###STOP###` 写进了同一条消息，**Agent 根本没有回合
执行那次修改**。不是 Agent 不会做，是考试没给它动手的机会。

这个模式在 10 道翻盘题里有 9 道成立——GLM 的用户轮数一律多 1~2 轮：

| 题 | qwen 用户轮 | glm 用户轮 |
|---|---|---|
| 3 | 5 | 5 |
| 4 | 4 | 5 |
| 6 | 7 | 6 |
| 7 | 6 | 6 |
| 8 | 5 | 6 |
| 15 | 3 | 5 |
| 19 | 4 | 5 |
| 21 | 4 | 5 |
| 23 | 4 | 6 |
| 29 | 4 | 5 |

审查另外独立抓到题 3 的 `critical_hindered`：qwen 把
「modify **all** your pending small tshirt」读成「只改已经是 small 的那单」，
明确说 "The XXL order can stay exactly as it is"，直接让任务不可能完成。

### 9.8.4 为什么这不是「考卷被改简单了」

这正是 §9.8.1 那条警告要防的情况，所以逐条排除：

1. 审查模型在 GLM 的 24 条会话里找到 **0 个 `critical_helped`**，24 条全审、0 条跳过；
2. 唯一丢掉的题 22，GLM 打了 11 个用户轮/36 条消息，审查判定模拟用户完全按指令行事
   ——那是 Agent 自己把默认地址改回去时出的错，属于考试正常工作；
3. 被测侧成本**上升**了（1.6399 → 1.9207 元），会话变长而不是变短。放水应当让会话变短。

### 9.8.5 反直觉的附带发现：赢家想得更少

| | 每次调用的推理 token |
|---|---|
| qwen3.6-plus @ high | 633（111 次共 70259） |
| glm-5.3-flash @ high | **19**（145 次共 2822） |

GLM 在 `high` 档被压制得很厉害（单探针实测：不设参数 2698，`low` 0，`high` 151，`max` 2874），
却没犯 qwen 那个致命的时序错误。

这推翻了换型前留下的一条备注——原本担心 `high` 会削弱 GLM、需要补一轮 `max` 才能下结论。
**不需要了**：GLM 是在思考深度被严重压制的情况下赢的，补 `max` 只会让它赢得更多。

结论：模拟用户的质量瓶颈不在思考深度，在**何时说停**。§9.5.3 说的
「档位对 qwen 几乎没有效果」在这里得到了另一个方向的印证——
两个模型都不是靠想得多来当好模拟用户的。

### 9.8.6 换型的四项代价（都已在代码里留痕）

不是白换的。每一项都写进了测试，不靠记忆：

| 代价 | 后果 | 留痕位置 |
|---|---|---|
| **没有带日期的快照 ID** | 智谱未提供 `glm-5.3-flash-2026xxxx`（2026-09-07 查官方文档）。它若在别名后换模型，只能靠复跑发现 | `test_frozen_user_simulator_alias_risk_is_recorded` |
| **失去「关思考」对照开关** | GLM-5.3 系列服务端强制思考（400 code 1210），`--user-no-thinking` 对它不可用 | `test_disabling_thinking_fails_at_setup_not_mid_run`；`EvalStack.__post_init__` 构造时即报错，不拖到跑批中途 |
| **温度不再由我们控制** | 智谱思考模式下 temperature 固定 1.0，发 0 不生效，所以干脆不发 | `test_frozen_stack_drops_temperature_on_zhipu` |
| **与候选池 glm-5.2 同家族** | 若拿 glm-5.2 当被测，模拟用户是它同门；警告从此每轮出现 | `test_frozen_user_simulator_collides_with_a_candidate_family`（保留警告，不消音） |

另外，**换模拟用户会让此前全部成绩不可比**。旧型号因此保留为
`evaluation.PREVIOUS_USER_SIMULATOR`，价格也保留在 `pricing.py`——
复跑历史结论时显式传 `user_model=PREVIOUS_USER_SIMULATOR` 即可，它会自动走回 DashScope。

### 9.8.7 顺带修掉的一个真 bug

`EvalStack.__post_init__` 此前用 `RSA_USER_MODEL` **无条件覆盖**调用方显式传入的
`user_model`。它一直没暴露，是因为在换型之前没人需要显式指定模拟用户。
换型之后这条路径立刻变成刚需（复跑历史），于是问题浮出来：
按报错信息的指引传 `user_model=...`，会被环境变量悄悄压掉。

现在的优先级是**显式参数 > 环境变量 > 冻结默认**，与判官一致。

### 9.8.8 尚未验证的

- 只跑了 dev 划分 24 题各一轮。噪声底 25% 仍然成立，只是这次的 p 值和机制证据都够硬；
  换 holdout 复核前，不应把 23/24 当成 Agent 的真实水平——
  **它衡量的是新模拟用户下的考卷，不是 Agent 变强了**。
- GLM 在 `max` 档是否还会更好，没测（按 §9.8.5 的推理没有必要，但没测就是没测）。
- 未在 114 题全集上跑过 GLM 模拟用户。


## 9.9 干净评测栈上的独立验证（2026-09-07）

### 9.9.1 为什么必须重跑

M0.5 的验收条件之一是「独立验证完成，**结论足以支持选型**」。复核既有证据后
发现支持不了——整个选型建立在两轮 holdout 上，而这两轮**用的是不同的判官**：

| 运行 | 被测 | 得分 | 判官 | 模拟用户 | 判官 JSON |
|---|---|---|---|---|---|
| `20260906T165340Z` | qwen3.8-max | 32/40 (0.800) | `deepseek-v4-flash` | qwen3.6-plus | 无 |
| `20260906T182221Z` | deepseek-v4-pro | 24/40 (0.600) | `qwen3.7-flash` | qwen3.6-plus | 无 |

0.800 对 0.600 不是模型之间的差距，是**两把不同的尺子量出来的两个数**。

这不只是这两轮的问题：A 轮那 5 个候选的 12 题横评全部由 `deepseek-v4-flash` 判，
而 `deepseek-v4-pro` 的所有轮次全部由 `qwen3.7-flash` 判——
**被选中的那个模型，从来没有和它的竞争者用同一把尺子量过。**

再叠加两条今天之前才修掉的缺陷：两轮都跑在会掐断对话的旧模拟用户上（§9.8），
两轮判官都没有 `response_format`（§9.5.4）。所以选型证据在三个独立的点上都站不住。

### 9.9.2 结果

同一批 holdout 40 题、同一个被测模型，只换评测栈：

| | 旧栈（09-06） | 新栈（09-07） |
|---|---|---|
| 满分 | 24/40 = 0.600 | **35/40 = 0.875** |
| 修好 | — | 14 题 |
| 弄坏 | — | 3 题 |
| 需判官的 11 题 | 5/11 | 9/11 |
| 每题成本 | 0.1279 元 | **0.0716 元** |

**McNemar 精确检验 p = 0.0127，差异显著。**

运行目录 `20260907T080504Z_deepseek-v4-pro_holdout`。三角色成本合计 3.2241 元
（被测 3.0312 + 模拟用户 0.1898 + 判官 0.0031，DeepSeek 谷时）。

**这一轮衡量的是"旧栈整体 → 新栈整体"**，混了模拟用户换型与判官加 JSON Schema
两处改动——旧 holdout 那轮两样都没有。单独隔离模拟用户效应的是 §9.8 那轮
（两边判官配置相同，p = 0.0117）。两轮同向，但本轮不能单独给模拟用户记功。

### 9.9.3 dev 与 holdout 的差距是预期之内的

| | dev | holdout |
|---|---|---|
| 干净栈得分 | 23/24 = 0.958 | 35/40 = **0.875** |

低 8 个百分点。dev 上跑过 7 轮参数实验，它已经被反复看过；holdout 没调过参。
**0.875 才是可以对外说的那个数**，0.958 不是。

### 9.9.4 对选型结论的影响

此前的说法是「deepseek-v4-pro 便宜 5 倍，代价是每 5 单可能多错 1 单」
（0.600 对 qwen3.8-max 的 0.800）。现在是 **0.875 对 0.800**——
成本优势不变，而"质量更差"这个代价在干净栈上不成立。

但**这句话不能写成结论**：qwen3.8-max 的 0.800 是脏栈测的，
拿它和干净栈的 0.875 直接比，就是本节开头批评的"两把尺子"。

已决定**不补测 qwen3.8-max**：它每题 0.3877 元 vs 0.0716 元，贵 5.4 倍，
成本不在一个量级，即使质量更好也不会改变选型。因此选型口径明确记为：

> **成本决策。** deepseek-v4-pro 每题 0.0716 元，在干净评测栈的 holdout 上
> 取得 0.875。其余候选未在同一评测栈下测量过，**本项目不声称做过跨模型的
> 质量比较**。此前 A 轮的所有跨模型数字因判官不一致而作废。

### 9.9.5 副产物：丢题防护

这轮跑到一半，判官所用型号在服务端的调用额度耗尽，**5 题没跑起来**。
问题不在故障本身，而在故障之后发生的事：

上游把这 5 题**从分母里剔掉**，`avg_reward` 显示 **0.886**；
补齐之后的真实成绩是 **0.875**。

**丢题不报错，还让成绩更好看。** 这比直接崩溃危险得多——不去翻日志就发现不了。

补上三层防护（见 `tests/test_incomplete_run_guard.py`）：

| 层 | 位置 | 行为 |
|---|---|---|
| 发现 | `run_eval.summarize(sims, expected)` | 跑完与应有会话数对账 |
| 记录 | `summary.json` | 落 `incomplete` / `expected_count` / `unscored_task_ids` |
| 拒绝 | `analyze_eval.py` | 见到缺口**不报平均分**，除非显式 `--allow-incomplete` |

一条刻意的取舍：`avg_reward` 本身**不改口径**。把分母换成 `expected` 等于把没跑的
题按 0 分计，同样是编造——正确的做法是拒绝把这个数当成绩，而不是换一个错法。

配套 `scripts/resume_run.py` 补跑缺题并合并回原目录。它只核对**环境解析出来的**
那部分（模拟用户、判官、判官 JSON 格式、三个端点）；运行参数从 manifest 照抄，
核对它们等于自己跟自己比。栈不一致即拒绝——补跑的题必须与原轮同栈，
否则合并回去就是两个栈的混合，正是 9.9.1 那个问题的翻版。

`results_io.load_simulations` 相应改为按 `task_id#trial` 去重，有分数的覆盖没分数的；
不同 trial 仍分开保留，避免把多轮重复实验误当成补跑。

### 9.9.6 尚未验证的

- 单轮。§9.6.2 测得的噪声底 25% 仍然成立，只是这次 p 值与机制证据都够硬。
- 未在 114 题全集上跑过干净栈。
- `baseline-v1` 仍未冻结。
