# M6.7: a login, and a demo that goes through it

## 0. Why this step exists

The demo is on the public internet at `https://rsa.proshot.top`, and the only thing keeping
anyone out is the list of addresses in `allowed_cidrs`. That is not access control; it is a
firewall standing in for one. Removing it is the point of this step, and removing it
without a login would hand every visitor the ability to cancel and refund orders.

There is a second problem, and it is the larger one.

**M3's authorization does not run in the demo.** `ui.py` constructs a `RetailAgent` in
process with `SessionState(DEMO_USER_ID)` and never calls the API. So the token
verification, the identity derived from `identities`, the role table and the session
ownership check - all of M3, and the reason M4's ticket permissions mean anything - are
bypassed by the only path a visitor can take. `/health` reports `auth: disabled` and it is
telling the truth: the deployed API has no issuer configured, and nothing reaches it
anyway.

So "add a login" cannot mean putting a password in front of the existing UI. That would
record who came in and then run every action as `ava_moore_2033` regardless. The login has
to establish an identity, and the demo has to spend it.

## 1. Change card

- **Stage and step**: M6.7
- **Type**: feature
- **The specific problem**: the deployed demo authenticates nobody, and its only user
  path does not reach the code that would authorize anyone
- **The single theme of this change**: every action in the demo is attributable to a
  verified account, and authorized by what the database grants that account
- **Control variables this change does not touch**: the model, the simulated user, the
  judge, the task sets, the upstream commit, the price snapshot, the agent's tool set,
  the guard's confirmation rule, the τ²-bench data, every baseline, the idle verdict, and
  the certificate and name from M6.6
- **Explicitly out of scope**:
  - **Registration.** Accounts are provisioned by Terraform and the operator. There is no
    sign-up route, for the same reason M3 gave: an account that chooses its own role at
    registration is the escalation this design exists to prevent.
  - **Password reset, MFA, account recovery, and Cognito's hosted UI.** A demo with four
    fixed accounts needs none of them, and the hosted UI would put a second domain and a
    second certificate in front of the one M6.6 just established.
  - **Streaming.** M7. Moving the UI onto the API is what makes streaming possible later,
    but nothing in this step streams.
  - **Archiving before a teardown, and rollback between image versions.** Later M6 steps.
- **Expected benefit**: `allowed_cidrs` can be dropped to the world, and an unauthenticated
  visitor can reach the login form and nothing else
- **Possible cost**: a user pool bills per monthly active user with the first 10,000 free,
  so at four accounts it adds nothing to the idle cost that M6.1's rule bounds. The real
  cost is latency: every message now crosses a network boundary and carries a signature
  verification. Section 1.6 fixes the threshold.

### 1.1 Why the UI change is in this step and not a separate one

The plan says one theme at a time, and moving the UI from an in-process agent to an API
client is a large change to put alongside a new identity provider.

It is in scope because the theme is attribution, and without it nothing is attributed. A
login that gates the page while the page still acts as a hard-coded user proves the visitor
knocked, not who acted. Splitting the step would mean shipping that intermediate state and
describing it as login, which it would not be.

What that costs is stated rather than hidden: the UI's failure modes change. It can now
fail with 401, 403 and 502 from a service on the other side of a socket, and each needs a
message a person can act on. Section 2 lists them.

### 1.2 Where identity comes from

A Cognito user pool in the same account and region, created by Terraform. The API already
verifies a Cognito-shaped RS256 token against a JWKS endpoint; M3 built and tested that
verifier against a locally generated key pair and deferred the real pool to M6. This
supplies the pool.

**The pool issues tokens. It does not decide anything.** `cognito:groups` stays ignored, as
M3 fixed. The token's `sub` is looked up in `identities`, and `role_memberships` decides
what the caller may do. Revoking a role takes effect on the next request rather than on the
next token.

Four accounts, chosen so the checks in section 1.6 have something to check:

| Account | Retail identity | Roles | Exists to show |
|---|---|---|---|
| `ava` | `ava_moore_2033` | customer | The normal path, on the data every earlier demo used |
| `ivan` | `ivan_santos_6635` | customer | A second customer, so isolation is testable rather than asserted |
| `sam` | `ava_moore_2033` | supervisor | Approvals and the audit trail, and no `ticket:work` |
| `nobody` | *not provisioned* | none | A token that verifies for a subject this system has no account for |

`nobody` exists in the pool and not in `identities`. It is the case that separates
authentication from authorization: the signature is good, and the answer is still 403.

### 1.3 How the password is set, and where it is not

Terraform creates each user with no password argument. Cognito puts the account in
`FORCE_CHANGE_PASSWORD` with a temporary password it never delivers, because the pool sends
no mail. The operator then sets a permanent password once per account with
`admin-set-user-password --permanent`.

That is one manual command per account, and it is deliberate. `aws_cognito_user` accepts
`password` and `temporary_password`, and either one writes the value into Terraform state.
The state bucket is private, but the repository's rule is that credentials live in the
environment or a secret manager, and state is neither. The same reasoning put the model key
in Parameter Store in M6.4 and left the state bucket outside Terraform in M6.4's bootstrap.

`terraform apply` prints the commands to run, with the passwords left blank.

### 1.4 How the database learns the subjects

`identities` maps a token subject to a retail identity, and the subject is generated by
Cognito. Terraform exports it: `aws_cognito_user` has a `sub` attribute.

So Terraform writes the mapping - subject, retail user id, roles - into the instance's
environment file, and a new `seed` role in the image upserts it into the database at every
boot, after `migrate` and before `api` and `ui` start. `provision_identity` is already
idempotent in both halves, so a boot that changes nothing writes nothing.

Boot time rather than apply time, for two reasons. Terraform has no route to the database;
it sits inside a compose network on the instance. And the database is a container volume,
so a volume lost or reset leaves a working pool and an empty `identities` table, which
would refuse every login with a 403 that looks like a bug. Seeding at boot repairs that
without an apply.

Subjects are opaque identifiers, not secrets. The mapping goes in the environment file
beside the region and the image tag, not in Parameter Store.

### 1.5 How the token gets from the browser to the API

The Gradio server performs the sign-in and holds the tokens. The browser sends a username
and a password over TLS to the UI container, the UI calls `InitiateAuth` with
`USER_PASSWORD_AUTH`, and the returned access and refresh tokens stay in `gr.State`, which
is per-browser-session and lives in the UI process's memory.

The browser is never given a token. Gradio splits one interaction into `POST /queue/join`
and a `GET /queue/data` event stream, and a credential the client had to attach would have
to be attached to both; keeping it server-side removes that problem instead of solving it.
It also means no token is in `localStorage` for the page's own JavaScript to read.

Three consequences, all accepted:

- **A UI restart signs everyone out.** State is process memory. The instance stops when
  idle anyway, so a session does not outlive the machine.
- **`USER_PASSWORD_AUTH` sends the password to the app client.** The UI is the relying
  party and the transport is the certificate from M6.6. The alternative, SRP, is a
  four-message exchange to avoid sending a password to a server that is about to be told
  the answer anyway.
- **The access token expires in an hour.** The refresh token is kept and used once on a
  401, and a second 401 returns the visitor to the login form rather than looping.

The app client is created with no secret, `ALLOW_USER_PASSWORD_AUTH` and
`ALLOW_REFRESH_TOKEN_AUTH`, and no other flow.

The UI reaches the API at `http://api:8000` on the compose network. `/chat` is still not
routed through Caddy, so the write routes remain unreachable from the internet. What the
internet can reach does not grow in this step; it is the same surface M6.6 measured, plus a
login form on the page that was already there.

### 2.1 Decisions made during the work

**No AWS SDK for one endpoint.** `InitiateAuth` is unsigned - it is what a client calls
because it has no credentials yet - so signing in is a plain HTTPS POST. The runtime image
gains no dependency, which matters because it is 722 MB already and boto3 would be in every
container including the one that only runs migrations.

**Every raise on a failure path is `from None`.** `urllib.request.Request` holds the posted
body, and for the sign-in that body holds the password; for the API client the headers hold
the bearer token. A chained exception carries that object into every traceback. Both
modules have a test that asserts the chain is empty, on the real transport rather than on a
substitute, because the property belongs to the transport.

**The access token, not the id token.** A Cognito access token has no `aud` claim; it
carries `client_id`. M3's verifier already compares the audience against `aud` when present
and `client_id` otherwise, so no change was needed and `token_use` stays `access`.

**One message for every refusal that could enumerate.** `UserNotFoundException` and
`NotAuthorizedException` told apart would say which usernames exist. They collapse into one
message in the client, and the app client also sets `prevent_user_existence_errors`, so the
pool does not distinguish them either. Both, because either alone is one edit from leaking
it.

**`demo` is not a grantable role.** It is what the service invents for itself when
authentication is off, and it holds `session:reset_all`. Granting it to a signed-in visitor
would let them drop everyone else's sessions. Refused in two places: a Terraform variable
validation, and the seeding, which fails the boot rather than provisioning it.

**A malformed mapping fails the boot.** A typo in a role name would otherwise produce an
account with no powers, and the resulting 403 is indistinguishable from an authorization
defect. Failing loudly names the typo. A partial mapping is worse than none, so nothing is
written when any entry is bad.

**The refresh happens once, not in a loop.** A refresh token the pool has revoked would
otherwise turn one expired session into a stream of requests to the pool while the visitor
watches a page that never resolves. A second 401 returns them to the form.

## 4. Failure analysis and conclusion

### 4.1 What was found by doing the work

**The demo was the one path that skipped every authorization check.** This was not
introduced by M6.7; it had been true since M0.3 and survived M3 and M4 unnoticed, because
the UI was written before there was anything to authorize and nobody went back to it. The
milestone's acceptance line said "login", and the honest reading of that turned out to be
larger than adding a form.

**A supervisor's account and a customer's account can share a retail identity.** `sam` and
`ava` both map to `ava_moore_2033`. That is correct, since a supervisor still has orders of
their own, but it means the retail identity does not identify the account, and any later
check that treated it as one would be wrong.

**A Cognito access token has no `aud` claim.** It carries `client_id`. M3's verifier
already compared the audience against `aud` when present and `client_id` otherwise, so this
cost nothing; had it not, the first real token would have been refused for the wrong
reason.

### 4.2 Limits of these results

- **The agent refused the cross-account cancellation before the guard could.** Section 3.1
  says so plainly. Two layers, and only the first was exercised live.
- **The four accounts' passwords are outside this project.** Nothing here can test that
  they were chosen well, only that an account without one cannot sign in.
- **A role revoked by hand comes back at the next boot**, because the seeding writes what
  the configuration names. Revocation that must outlive a restart belongs in
  `demo_accounts`. Documented in `docs/OPERATIONS.md` rather than fixed: the alternative,
  seeding that deletes rows the configuration does not name, would let a boot remove access
  somebody granted deliberately.
- **A UI restart signs everyone out.** State is process memory. The instance stops itself
  when idle, so no session outlives the machine anyway.

### 4.3 Conclusion

**PASS.** Every threshold in section 1.6 was met on the deployed environment. The demo is
reachable from any address, and what an unauthenticated visitor can reach is a sign-in
form.

Accepted because the capability is the one M6's acceptance line names, and because the
change that makes it real - the UI calling the API - also removes the gap that had made
three earlier milestones' authorization work unreachable from the demo.

### 4.4 What this leaves for later

- **Archiving before a teardown**, and **rollback between image versions**: the remaining
  two M6 items.
- **Streaming**: M7. The UI is now an API client, so streaming becomes a change to what the
  API returns rather than a rewrite of the page's identity handling.
- **The instance is replaced on any cloud-init change**, which discards the database and
  the certificate with it. That was the right trade while the database holds only demo
  state. It stops being right once archiving exists, and M6.8 has to say what it does about
  it.
