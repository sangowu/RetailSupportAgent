# M6.3: deciding that nobody is using this, and turning it off

## 0. Why this step exists

The requirement this stage was given is "start on demand, shut down after fifteen minutes
of idleness". M6.1 chose a shape whose idle cost is a stopped instance's disk, 0.70 USD a
month. That number is only real if something actually stops the instance. Right now nothing
does, and a demo left running costs 0.0228 USD an hour, about 16 USD a month, which is
twenty times the number the shape was chosen for.

The hard part is not the shutdown. It is deciding that the machine is idle. CPU is the
wrong signal in both directions: a request blocked on a model call uses almost none, and a
background task uses plenty while nobody is watching. This application knows things the
machine cannot: whether a write is waiting for confirmation, whether a ticket is open in
front of a human, whether anyone has spoken to it recently.

So idleness is a question the application answers about itself, and the machine acts on the
answer.

## 1. Change card

- **Stage and step**: M6.3
- **Type**: feature
- **The specific problem**: nothing stops the demo instance, so M6.1's idle cost is a
  property of the design and not of the running system
- **The single theme of this change**: defining idleness against application state, and
  acting on it. No change to what the application does when it is busy.
- **Control variables this change does not touch**: the agent, the guard, the prompts, the
  model configuration, the database schema, the migrations, the evaluation harness, every
  baseline, and every existing route's behaviour.
- **Explicitly out of scope**, each its own later step:
  - Terraform, and the base and demo layer split
  - Starting the instance on demand, and the entry URL
  - HTTPS
  - Archiving on stop. This step decides when work is finished, not where it is kept.
- **Expected benefit**: the idle cost M6.1 chose the shape for, enforced by the system
  rather than by whoever remembers.
- **Possible cost**: a wrong "idle" verdict interrupts someone. The definition therefore
  errs towards staying up, and the bound on that mistake is the hard cap in section 1.3.

### 1.1 What idle means here

The instance is idle when **every** one of these holds:

| Condition | Where it comes from |
|---|---|
| No request in the last window | a middleware timestamp, excluding the health and idle routes themselves |
| No write waiting for confirmation | pending confirmations in the store |
| No approval waiting for a human | `store.pending_approvals()` |
| No open ticket | `store.tickets(open_only=True)` |

The last three are the ones a clock alone would get wrong. A confirmation that nobody has
answered, an approval sitting in front of a supervisor, or a ticket a human still owns are
all states where the demo looks quiet and is not finished. M4 built them; this step reads
them.

#### 1.1.1 A condition removed from this card before it was built

The table first also required `registry.active_sessions() == 0`. It cannot be used.
`SessionRegistry` puts an agent in `self._agents` on first use and removes it only on an
explicit reset (`api.py:320` and `api.py:366`); nothing expires. One conversation would
therefore hold the count above zero for the life of the process, and the machine would
never be idle.

The count is still reported, because "why is this instance still up" is answered faster
with it than without it. It just holds nothing open.

That dictionary only growing is also a slow leak in a long-lived process. It is not this
step's theme and it is not fixed here; it is written down so it is not lost.

Removing the condition costs nothing, because the case it was meant to catch is already
covered. A session that someone is using produces requests, and one that is half-finished
has a pending confirmation.

**The poller must not keep the machine alive.** The watcher asks the application whether it
is idle, once a minute. If that request counted as activity, the answer would always be no.
The health and idle routes are therefore excluded from the activity timestamp, and nothing
else is.

### 1.2 What the application answers

A new read-only route reports the verdict and, when it is not idle, what is holding it
open. A watcher that can only see a boolean cannot be diagnosed when it does the wrong
thing, and "why is this instance still running" is the first question anyone will ask.

### 1.3 Two independent reasons to shut down

| Reason | Default | Why it exists |
|---|---|---|
| The application has been idle continuously for a window | 15 minutes | the requirement |
| The instance has been up longer than a cap, whatever it says | 4 hours | the application cannot answer, or answers "busy" forever because of a stuck session |

The second is what bounds the cost of the first being wrong. Without it, one session that
never closes keeps a machine running until someone notices the bill.

**An unreachable application is not idle.** A watcher that shut down when it could not get
an answer would shut down hardest exactly when something is wrong and someone is looking at
it. It stays up, and the cap catches it.

### 1.4 How the shutdown happens

Stop the stack first, then the machine. `docker compose down` lets PostgreSQL close its
files; pulling the power from underneath it does not. The instance is stopped rather than
terminated, so the disk, the database and the image survive, which is what makes M6.1's
restart 41 seconds instead of 122.

### 1.5 The decision must be testable without AWS

The watcher's decision is a pure function of the application's answer, the clock and the
configuration, in a module with no dependencies outside the standard library. The parts
that cannot be tested off an instance are exactly two: the call to `shutdown`, and the
systemd timer that runs the thing. Everything else has a test.

### 1.6 What is measured, and the thresholds

| Metric | Threshold |
|---|---|
| Idle with nothing happening | the verdict flips to idle within one poll of the window elapsing |
| Each holding condition | named individually in the answer, and each one alone prevents shutdown |
| The poller's own requests | do not reset the activity clock |
| An unreachable application | never counted as idle |
| The cap | fires whatever the application says |
| Shutdown order | the stack is stopped before the machine |
| The existing suite | passes unchanged |

### 1.7 Baseline and previous version

No previous version: nothing stops the instance today. The reference is M6.1's idle cost of
0.70 USD a month and M6.2's 41-second restart, both of which this step is what makes real.
No task set is run and no baseline moves.

## 2. Implementation and verification

### 2.1 Files

| File | Responsibility |
|---|---|
| `deploy/instance/idle_shutdown.py` | the watcher: asks, decides, stops the stack, stops the machine |
| `deploy/instance/rsa-idle.service` | runs it once, as root |
| `deploy/instance/rsa-idle.timer` | every minute, first check two minutes after boot |
| `src/retail_support_agent/api.py` | the activity middleware and `GET /idle` |
| `src/retail_support_agent/store.py` | `pending_confirmation_count`, one query across all sessions |
| `tests/test_idle_shutdown.py` | 20 tests |
| `docs/OPERATIONS.md` | how to configure it and how to read its verdict |

### 2.2 The two halves

`GET /idle` returns the verdict, the counts behind it, and a `holding` list naming each
reason the machine cannot stop. It needs no token: the caller is a process on the same
machine, the body carries counts rather than anyone's data, and requiring a token would
mean putting one on the instance in order to stop the instance.

The watcher is standard library only, and `decide()` is a pure function of the answer, the
uptime and the configuration. Two parts cannot be tested off an instance, and only two: the
call to `shutdown` and the timer.

`idle_seconds` is time since the last request, and is reported as zero while anything is
holding. Whatever closes a holding reason is itself a request, so the clock restarts from
that request.

### 2.3 The failure this design exists to avoid

A confirmation that nobody has answered produces no requests. A watcher measuring silence
would call that idle after fifteen minutes and stop the machine on a half-finished write.
`test_time_alone_never_makes_a_held_machine_idle` is that case: a day of silence with one
pending confirmation, and the decision is still to stay up.

### 2.4 Two failures worth keeping

- **User data is limited to 25600 bytes after encoding, and the AWS CLI encodes what it is
  given.** Handing it an already-base64 blob counts the encoding twice: 15607 bytes of
  script became 27750 and `RunInstances` refused it. Passing `file://` and letting the CLI
  encode once fixes it, and the path has to go through `cygpath -m` because the CLI is a
  Windows program and cannot open a Git Bash path.
- **The `--parameters` quoting for `ssm send-command` did not survive**, which is why the
  second instance check did not run. See section 3.2.

## 3. Comparison

No model is called and no task set is run, so task success rate, safety violations and cost
per successful task are unchanged by construction.

### 3.1 On a real instance

One `t3.small` in `eu-west-1`, with the window shortened to two minutes through
`/etc/rsa-idle.env`.

| | Seconds |
|---|---|
| Stack answered after launch | 113 |
| From answering to the instance reaching `stopped`, nothing happening | 198 |

The 198 seconds are the 120-second window, up to 60 seconds of waiting for the next poll,
and about 20 seconds to stop the containers and the machine. At the default fifteen-minute
window that is a little over sixteen minutes.

The route answered `{"idle_seconds": 2.3, "holding": [], "open_tickets": 0, "persistent":
true}` on a fresh instance, so the verdict came from the database rather than from a
missing store.

### 3.2 The instance check that did not run

The plan was to start the machine again, open a ticket, and watch it refuse to stop. The
`ssm send-command` call that was to open the ticket failed on parameter quoting, so no
ticket was created, and the machine then stopped because it genuinely was idle. **That is
not evidence of anything and is not counted.**

Rather than spend another instance on it, the same property is now covered by three tests
against a real PostgreSQL, which run in CI and cost nothing:

| Test | What it holds |
|---|---|
| `test_an_open_ticket_holds_the_machine_open` | an open ticket holds; closing it releases |
| `test_a_write_waiting_for_confirmation_holds_the_machine_open` | a pending confirmation holds |
| `test_time_alone_never_makes_a_held_machine_idle` | a day of silence plus one pending confirmation still says stay up |

What remains unverified on a real instance is only that the watcher reads a non-empty
`holding` list correctly, and that is the same `decide()` the unit tests cover directly.

### 3.3 Against the thresholds

| Metric | Threshold | Result |
|---|---|---|
| Idle with nothing happening | flips within one poll of the window | stopped 198 s after answering, window 120 s, poll 60 s |
| Each holding condition | named, and each alone prevents shutdown | tickets, confirmations and approvals, each tested |
| The poller's own requests | do not reset the clock | tested, and the test fails if the exclusion is removed |
| An unreachable application | never idle | tested |
| The cap | fires whatever the application says | tested at the boundary and either side |
| Shutdown order | stack before machine | `stop_stack` then `power_off` |
| The existing suite | unchanged | 549 tests, 0 failures, 0 errors |

The whole suite runs 549 tests with 0 failures both ways: 107 skipped without a database,
0 skipped with one.

## 4. Failure analysis and conclusion

**PASS.** The instance stops itself, and the things that should stop it from stopping do.

- **What was accepted**: the idle route, the activity clock, the watcher, the timer, and
  20 tests.
- **What this makes real**: M6.1's idle cost. Before this the 0.70 USD a month was a
  property of the design; a demo left running costs about 16 USD a month.
- **What did not run**: the second instance check, section 3.2. It is replaced by tests,
  not by an assumption.
- **Nothing is deployed.** The verification instance, its role, its security group and the
  registry repository were deleted, and a sweep returns nothing belonging to this project.

### 4.1 Not verified

- **The default window on a real instance.** Two minutes was measured; fifteen is the same
  code path with a larger number, but it was not sat through.
- **The cap on a real instance.** Tested as a function, not by leaving a machine up for
  four hours.
- **A busy machine.** Every measurement here had one user and no model call.
- **Restarting on demand.** Something still has to start the instance, and that is the next
  step. Until then the demo stops itself and stays stopped.
- **The session dictionary that only grows** (section 1.1.1) is written down and not fixed.
- **Archiving before shutdown.** M6 is accepted on archiving, and this watcher stops a
  machine without exporting anything. The idle definition gains that condition when there
  is something to export.

## 5. Later defect: the watcher lost the API in M6.6 (found 2026-10-10)

The watcher runs on the host and asks `http://127.0.0.1:8000/idle`; `/etc/rsa-idle.env`
sets no other URL. M6.6 (`7c3a2a8`) removed the API's `ports: ["8000:8000"]` when Caddy
took over the public side, and nothing on the host has listened on 8000 since. The
watcher's rule for no answer is "not idle", so from M6.6 on the instance would stop only at
the 240-minute cap, never after 15 idle minutes. The two-minute measurement above predates
M6.6, and no later stage measured an idle stop.

Found by reading, while planning M10, not observed on the instance. On a running instance
`journalctl -u rsa-idle` would show `staying up: the application did not answer` on every
run if it held.

**Fix.** The instance compose file publishes the API on the loopback address only,
`127.0.0.1:8000:8000`. The compose file ships in the image (M6.8), so this is a release, not
an instance replacement, and the watcher and its user data are unchanged.
`tests/test_deploy_files.py` now holds that nothing but Caddy publishes beyond the machine,
that the only loopback port is this one, and that it is the address the watcher asks.

**Still to verify on AWS**, with the release that carries it: `idle_shutdown.py --check`
on the instance answers with an idle time rather than "did not answer", and an untouched
instance stops after about 15 minutes.
