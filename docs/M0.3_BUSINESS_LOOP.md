# M0.3 最小业务闭环报告

状态：**已实现并用真实模型跑通**。日期：2026-09-06。
演示存档：`evaluation/demo_runs/20260906T132442Z/flows.json`（四个流程的完整对话与数据库指纹）。

## 1. 闭环是否真的闭上了

用参照模型 `qwen3.7-max-2026-06-08`（非思考模式）跑四个流程，每个流程用全新的领域实例：

| 流程 | 结果 | 数据库指纹 |
|---|---|---|
| 查询订单 | 列出名下 4 个订单，答出 `#W4135875` 为 pending | **未变**（读操作不应改状态） |
| 取消订单 | 两段确认后执行，回复"已变为 cancelled，退款已返回礼品卡" | **已变** |
| 退货申请 | 两段确认后执行，回复"状态为 return requested，**退款尚未到账**" | **已变** |
| 越权取消他人订单 | 拒绝，并说明订单归属他人且状态不符 | **未变** |

数据库指纹是关键证据：**模型说"已取消"不算数，指纹变了才算真的落地**；
反过来，越权流程的指纹没变，才能证明拒绝是真的没执行，而不是执行完了嘴上说拒绝。

退货那条回复尤其重要——它如实说明了"申请成功 ≠ 钱已到账"，这正是
`PROJECT_CONTEXT.md` 要求的诚实边界，没有被模型含糊过去。

## 2. 架构

```
用户 → FastAPI / Gradio
        └── RetailAgent（LangGraph：think ⇄ act）
              ├── WriteGuard      ← 归属校验、参数绑定确认、停止条件（纯逻辑，不依赖模型）
              └── RetailDomain    ← 上游 tau2 的 16 个工具、原文政策、模拟数据
```

上游代码作为**按固定 commit 锁定的 git 依赖**引入（`tau2 @ fc0055dc`），
数据仍指向 `third_party/` 下经 SHA256 校验的那份检出。工具、政策、评分器一律不重写。

每个会话持有独立的 Environment 实例（各自一份 DB 副本），会话之间不共享可变状态。

## 3. 硬性底线：模型说了不算

`guardrails.py` 是纯逻辑，模型影响不了它的判定。四条底线：

1. **归属校验优先于一切**。写操作的 `order_id` 会先查真实归属，不属于当前身份直接拒；
   `user_id` 参数与会话身份不符也直接拒。**即使用户确认过也拒**——测试专门锁死了这一条。
2. **确认绑定到具体参数**。确认的指纹是 `工具名 + 规范化参数` 的 SHA256。
   模型在确认后改任何一个参数（换工具、换订单号、甚至多加一个字段），指纹就对不上，必须重新确认。
3. **未知工具直接拒**，不在上游 16 个工具清单里的一律不执行。
4. **停止条件**：最大步骤 20、最大工具调用 15、会话时限 180 秒。超限时**不再发模型请求**，避免无谓计费。

25 条测试覆盖这些路径，全部离线运行——安全底线不该依赖网络或余额才能验证。

## 4. 两段式确认（设计如此，不是冗余）

写操作要过两道确认：

1. **Agent 层**：上游政策原文要求 Agent "explain the cancellation detail and ask for
   explicit user confirmation"。这是政策要求，不能跳过，也不该用提示词去压制。
2. **系统层**：`WriteGuard` 拦下调用，把**完整参数逐项展示**给用户做最终确认。

第一道是政策合规，第二道才是参数绑定的那道。曾尝试用提示词让模型别自己问，
结果是提示词与政策原文直接冲突——**政策是我们声明要遵守的东西，不能为了 UX 去改它**。
所以保留两段，并在演示脚本里如实体现（写流程比读流程多一轮）。

## 5. 应用演示身份 vs 标准评测协议

τ²-bench 政策要求 Agent 用邮箱或姓名+邮编先做身份识别。这在标准评测里必须保留，
但对应用演示没意义——应用层登录已经确定了身份。

按 `DEVELOPMENT_PLAN.md` 的要求，两者**分开处理并分别记录**：

- **应用演示**：系统提示词里声明"身份已由应用层验证，当前用户就是 {user_id}"，
  并禁止调用 `find_user_id_*` 做身份确认。提示词里对此有显式注释。
- **标准评测（M0.4）**：走上游自己的身份识别协议与 Agent 提示词，**不使用**上面这份提示词。

这条分界不能滑坡成"用演示身份去改变标准评分条件"。

## 6. 实现过程中踩到的三个真实问题

### 6.1 上游在 Python 3.13 上装不起来

`tau2` 声明支持 `>=3.12,<3.14`，但其 import 链会加载 `tau2.voice.utils.audio_preprocessing`，
后者 `import audioop`——而 `audioop` 在 Python 3.13 已被移除（PEP 594），直接 `ModuleNotFoundError`。

处理：项目固定 `>=3.12,<3.13`。本项目的 ruff/mypy 本来就按 py312 配置，无额外代价。

### 6.2 序列化 bug，只有真实数据才暴露

上游工具返回的是 pydantic 模型（如 `Order`），我最初用
`json.dumps(raw, default=str)` 序列化——`default=str` 会把**整个对象压成一个字符串字面量**，
再 `json.loads` 回来就是个 `str`，取字段直接 `AttributeError`。

单元测试用的假领域返回的是普通 dict，测不出来；一接真实数据立刻炸。
现已按 `model_dump_json()` 处理，并对"解析结果不是对象"的情况返回 `None`（按拒绝处理）。

### 6.3 LangGraph 的边接错，把"待确认"状态覆盖了

初版 `act → think` 是无条件边。写操作被拦下后仍然回到模型再跑一轮，
`needs_confirmation` 这个结果被下一轮的普通回答覆盖，表现为"确认提示消失、写操作静默不执行"。

改成条件边：只有**真正执行了工具**才回到模型解释结果；待确认与已停止当场结束本轮。
这个 bug 是被测试抓到的，不是靠人眼看出来的。

## 7. 本步明确未做的事

- **Langfuse 未接入**。等 M0.4 真正记录实验时再加，现在不提前声明未使用的依赖。
- **无持久化**：会话在进程内存里，重启即丢。PostgreSQL 与 checkpoint 分别是 M1、M2 的独立主题。
- **无真实认证**：固定模拟身份，仅绑定 `127.0.0.1`，不提供注册。Cognito 是 M3。
- **不宣称并发或幂等**：同一会话串行处理，没做跨进程幂等与恢复。
- **界面是最小可用**：Gradio 只做到能走通三类流程并区分三种状态，完善是 M7。
- **未跑任何评测**：成功率、延迟、成本全部没有数字。选型在 M0.4。

## 8. 复现步骤

```bash
uv sync --group bench                        # 领域环境需要上游包（重依赖，单独成组）
uv run python scripts/fetch_tau2.py          # 拉取并校验数据
uv run ruff check . && uv run mypy && uv run pytest

# 会产生真实费用：
uv run python scripts/demo_flows.py                  # 四个流程全跑
uv run python scripts/demo_flows.py --flow cancel    # 只跑取消

# 本地服务（仅 127.0.0.1）
uv run uvicorn retail_support_agent.api:create_app --factory --host 127.0.0.1 --port 8000
uv run python -m retail_support_agent.ui
```

CI 只安装项目与 dev 组，不装 `bench`——测试用假领域与假模型，离线可跑，也不产生费用。
