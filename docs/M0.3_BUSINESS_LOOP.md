# M0.3 minimal business loop

Status: implemented and exercised against a real model. Date: 2026-09-06.
Demo archive: `evaluation/demo_runs/20260906T132442Z/flows.json`, containing the full
conversation and database fingerprints of four flows.

## 1. Does the loop actually close

Four flows were run with the reference model `qwen3.7-max-2026-06-08` (recorded at the
time as non-thinking, in fact the server's default thinking level; see M0.4 §9.5.1),
each with a fresh domain instance:

| Flow | Result | Database fingerprint |
|---|---|---|
| Order lookup | Listed 4 orders and reported `#W4135875` as pending | unchanged (a read must not change state) |
| Cancel order | Executed after two-stage confirmation; replied that it is now cancelled with the refund returned to the gift card | changed |
| Return request | Executed after two-stage confirmation; replied that the status is return requested and the refund has not arrived yet | changed |
| Cancel someone else's order | Refused, stating the order belongs to another user and its status does not qualify | unchanged |

The fingerprint is the evidence: the model saying "cancelled" does not count, a changed
fingerprint does. Conversely, the unchanged fingerprint on the refusal flow is what
proves nothing was executed, rather than executed and then described as refused.

The return reply matters in particular: it states that an accepted request is not a
refund that has landed, which is the honest boundary `PROJECT_CONTEXT.md` requires and
which the model did not blur.

## 2. Architecture

```
user -> FastAPI / Gradio
        +-- RetailAgent (LangGraph: think <-> act)
              +-- WriteGuard    ownership checks, argument-bound confirmation, stop
              |                 conditions; pure logic, independent of the model
              +-- RetailDomain  upstream tau2's 16 tools, the original policy, simulated data
```

Upstream code is a git dependency pinned to a commit (`tau2 @ fc0055dc`), while the data
still points at the SHA256-verified checkout under `third_party/`. Tools, policy and
evaluators are never rewritten.

Each session holds its own Environment instance with its own database copy, and sessions
share no mutable state.

## 3. Hard limits: the model's word does not count

`guardrails.py` is pure logic that the model cannot influence. Four limits:

1. **Ownership beats everything.** A write's `order_id` is checked against the real
   owner and refused when it is not the session's; a `user_id` argument that differs
   from the session identity is refused as well. This holds even if the user confirmed;
   a test pins that down.
2. **Confirmation binds to specific arguments.** The fingerprint is the SHA256 of the
   tool name plus canonical arguments. If the model changes any argument after
   confirmation, whether the tool, the order id, or one extra field, the fingerprint no
   longer matches and it must be confirmed again.
3. **Unknown tools are refused.** Anything outside upstream's 16 tools does not run.
4. **Stop conditions**: 20 steps, 15 tool calls, 180 seconds. Once a limit is reached no
   further model request is sent, so nothing is billed pointlessly.

25 tests cover these paths, all offline: verifying a safety limit should not depend on a
network connection or account balance.

## 4. Two-stage confirmation, by design

A write passes two confirmations:

1. **Agent layer**: the upstream policy requires the agent to "explain the cancellation
   detail and ask for explicit user confirmation". This is a policy requirement, not
   something to skip or suppress with a prompt.
2. **System layer**: `WriteGuard` holds the call and shows the user every argument for a
   final confirmation.

The first is policy compliance; the second is the argument binding. An attempt to use a
prompt to stop the model from asking put the prompt in direct conflict with the policy
text, and the policy is what this project claims to follow, so it is not edited for the
sake of UX. Both stages therefore remain, and the demo script reflects that honestly: a
write flow takes one more turn than a read flow.

## 5. Demo identity versus the standard evaluation protocol

The τ²-bench policy requires the agent to identify the user by email or by name and zip
code. That must be preserved in a standard run, but it is meaningless for the
application demo, where login has already established the identity.

As `DEVELOPMENT_PLAN.md` requires, the two are handled and recorded separately:

- **Application demo**: the system prompt states that the application layer already
  authenticated the user and that the current user is `{user_id}`, and forbids calling
  `find_user_id_*` to confirm identity. The prompt says so explicitly in a comment.
- **Standard evaluation (M0.4)**: upstream's own identification protocol and agent
  prompt are used, and the prompt above is not.

This boundary must not slide into using the demo identity to change standard scoring
conditions.

## 6. Three real problems hit during implementation

### 6.1 Upstream does not install on Python 3.13

`tau2` declares `>=3.12,<3.14`, but its import chain loads
`tau2.voice.utils.audio_preprocessing`, which imports `audioop`, removed in Python 3.13
(PEP 594). The result is an immediate `ModuleNotFoundError`.

Resolution: the project pins `>=3.12,<3.13`. ruff and mypy were already configured for
py312, so there was no additional cost.

### 6.2 A serialization bug only real data exposed

Upstream tools return pydantic models such as `Order`. The first implementation
serialized with `json.dumps(raw, default=str)`, and `default=str` collapses the whole
object into a single string literal; parsing it back yields a `str`, and reading a field
raises `AttributeError`.

The fake domain used in unit tests returned plain dicts, so nothing failed there; real
data failed immediately. It now uses `model_dump_json()` and returns `None`, treated as a
refusal, when the parsed result is not an object.

### 6.3 A LangGraph edge overwrote the "awaiting confirmation" state

The first version had an unconditional `act -> think` edge. After a write was held, the
graph still returned to the model for another round, and the `needs_confirmation` result
was overwritten by that round's ordinary answer. The symptom was a confirmation prompt
that disappeared while the write silently never ran.

It became a conditional edge: only a real tool execution returns to the model to explain
the result, while a pending confirmation or a stop ends the turn immediately. A test
caught this, not a reading of the code.

## 7. Explicitly not done in this step

- **Langfuse is not wired up.** It is added in M0.4 when experiments are actually
  recorded, rather than declaring an unused dependency early.
- **No persistence**: sessions live in process memory and are lost on restart.
  PostgreSQL and checkpoints are the separate subjects of M1 and M2.
- **No real authentication**: a fixed simulated identity bound to `127.0.0.1`, with no
  registration. Cognito is M3.
- **No claim of concurrency or idempotency**: one session is processed serially, with no
  cross-process idempotency or recovery.
- **The UI is minimal**: Gradio does enough to run the three flows and distinguish three
  states; completing it is M7.
  > Update 2026-09-07: this stopped being true after the upgrade to gradio 6, where
  > `gr.Chatbot(type="messages")` raises TypeError and the UI would not start, and no
  > test touched the UI at the time. M0.5 fixed it and added a construction test; see
  > [M0.5 part two §2.1](M0.5_LOCAL_DEMO.md).
- **No evaluation was run**: there are no success-rate, latency or cost numbers.
  Selection happens in M0.4.

## 8. Reproduction

```bash
uv sync --group bench                        # the domain needs the upstream package
uv run python scripts/fetch_tau2.py          # fetch and verify the data
uv run ruff check . && uv run mypy && uv run pytest

# these spend real money:
uv run python scripts/demo_flows.py                  # all four flows
uv run python scripts/demo_flows.py --flow cancel    # cancellation only

# local services (127.0.0.1 only)
uv run uvicorn retail_support_agent.api:create_app --factory --host 127.0.0.1 --port 8000
uv run python -m retail_support_agent.ui
```

CI installs only the project and dev groups, not `bench`: the tests use a fake domain and
a fake model, run offline, and cost nothing.
