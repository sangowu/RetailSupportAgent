# M6.6: a name that survives a stop, and a certificate

## 0. Why this step exists

The demo answers on `http://3.252.101.236:7860`, and that address changed three times during
M6.5's verification alone. Nobody can be sent a link, nothing can be bookmarked, and a
browser is right to complain about the connection.

Two problems, and only one of them is the certificate. This shape uses no Elastic IP,
because an address costs 0.005 USD an hour whether attached or idle, which is more than the
disk the whole shape was chosen for. So the address is genuinely different after every stop
and the name has to follow it.

M6's acceptance line includes login and streaming through the entry point. Neither is this
step. What this step produces is a name and a certificate, still reachable only from the
addresses in `allowed_cidrs`; opening it to the world is what needs login first, and that
is the next step.

## 1. Change card

- **Stage and step**: M6.6
- **Type**: feature
- **The specific problem**: the demo's address changes on every start and it has no
  certificate
- **The single theme of this change**: a stable name over TLS. Not who may use it.
- **Control variables this change does not touch**: the application, the image's
  application layers, the database, the agent, the guard, the evaluation harness, every
  baseline, and the idle verdict.
- **Explicitly out of scope**, each its own later step:
  - **Authentication, and opening the port to the world.** `allowed_cidrs` still gates who
    can connect. A demo with a certificate and no login is not safer than one without a
    certificate; it just looks it.
  - Archiving before a teardown, and rollback between image versions
  - Streaming, which has nothing to stream yet
- **Expected benefit**: one URL that is the same next week, and a browser that does not
  warn.
- **Possible cost**: a hosted zone costs 0.50 USD a month, which is most of what the idle
  instance costs. Section 1.4 says why it is worth it and what the alternative was.

### 1.1 The name

`rsa.proshot.top`, a subdomain delegated to a Route 53 hosted zone in this account. The
apex domain stays wherever it is; only the subdomain's NS records are added at the
registrar, once, by hand.

**That manual step is a real dependency and this card names it.** Until those NS records
exist, the zone answers to nobody, the certificate cannot be issued, and the demo is
reachable only by address. `terraform apply` prints the records to add.

### 1.2 How the name follows the address

The instance updates its own record at boot, before anything else starts. It reads its
public address from the instance metadata service and writes an A record with a short TTL.

Not a Terraform resource, deliberately. Terraform runs when someone applies; the address
changes when the machine starts, which is a different event and usually a different person.
A record Terraform owned would be wrong from the moment the first stop happened, and
correcting it would mean an apply before every demonstration.

The instance is granted `route53:ChangeResourceRecordSets` on that one zone and nothing
else.

### 1.3 What terminates TLS

Caddy, in a container beside the others, with the certificate on a volume so it survives a
stop, a start and a container being recreated. Let's Encrypt certificates last ninety days
and Caddy renews with thirty left, so any start inside that window renews; a machine left
off for longer simply gets a new one.

**What it exposes is narrower than what runs.** Today two ports are open: the API on 8000
and the UI on 7860. After this, the UI is served at `/`, the two operator routes `/health`
and `/idle` are proxied, and **nothing else of the API is reachable from outside at all**.
The UI builds its own agent in process and never calls the API over the network, so nothing
is lost by closing it.

### 1.4 The costs, and the alternative that was not taken

| | Per month |
|---|---|
| Route 53 hosted zone | 0.50 USD |
| Queries at this volume | rounds to nothing |
| The idle instance it sits beside | 0.88 USD |

Cloudflare Tunnel is free and needs no inbound port at all, and was not chosen: it moves
the entry point outside AWS and outside Terraform, which is the opposite of what M6 is
accepted on.

### 1.5 Port 80, and why it is open to everyone

The certificate is obtained over HTTP-01, which requires Let's Encrypt to reach port 80
from wherever it happens to be. That port therefore cannot be restricted to
`allowed_cidrs`.

What answers there is a redirect to HTTPS and the challenge responder, and nothing else.
Port 443 stays restricted, so opening 80 does not open the demo. The alternative, DNS-01,
needs no open port but needs a Caddy build with the Route 53 module, which is a second image
to build, publish and keep current for a port that serves a redirect.

### 1.6 What is measured, and the thresholds

| Metric | Threshold |
|---|---|
| The name resolves to the running instance after a start | within 120 seconds of the start command returning |
| The certificate | valid, issued for the name, trusted by a stock client |
| A stop and a start | the same URL works again, without reissuing a certificate |
| The API's write routes from outside | refused |
| `/health` and `/idle` through the proxy | answer, so `scripts/demo.py` keeps working |
| Restart time | still inside M6.1's 120 seconds, with Caddy added |
| The existing suite | passes unchanged |

### 1.7 Baseline and previous version

The previous version is M6.5: two ports, plain HTTP, an address that changes. The
comparison is against its measured 29-second start and its `stop` refusing correctly, both
of which must survive.

## 2. Implementation and verification

### 2.1 Files

| File | Responsibility |
|---|---|
| `deploy/terraform/base/main.tf` | the hosted zone, the instance's permission to write one record in it, and the delegation |
| `deploy/instance/update-dns.sh` | writes this machine's address into that record, at every boot |
| `deploy/instance/Caddyfile` | what the internet can reach |
| `deploy/instance/compose.yaml` | Caddy added; the API and the UI stop publishing ports |
| `deploy/terraform/demo/main.tf` | 443 for named addresses, 80 for everyone, the application's ports gone |
| `scripts/demo.py` | one URL instead of two addresses |
| `tests/test_deploy_files.py`, `tests/test_demo_commands.py` | 12 more tests |

### 2.2 The delegation is code, not a remembered step

The parent domain is hosted elsewhere, so the subdomain has to be pointed at the Route 53
zone. Doing that by hand leaves a manual step in an environment whose point is being
reproducible, and a silent one: recreating the zone issues a different set of name servers,
and hand-written records would go on pointing at the old ones without anyone noticing.

The base layer therefore writes the `NS` records itself when given the parent's zone id.
The API token comes from `CLOUDFLARE_API_TOKEN` in the environment, never from a Terraform
variable, because a variable ends up in state in clear. It needs `Zone -> DNS -> Edit` on
that one zone and nothing else.

Optional: with no zone id the layer creates nothing there and prints what to add by hand.
Not everyone's parent domain is at the same provider.

### 2.3 The record is written by the instance, not by Terraform

Terraform runs when someone applies. The address changes when the machine starts, which is
a different event and usually a different person. A record Terraform owned would be wrong
from the first stop, and correcting it would mean an apply before every demonstration.

So the instance reads its own address from the metadata service at boot and upserts an A
record with a 60-second TTL, before the registry login and before anything that needs the
name. It then waits for the change to be accepted: Let's Encrypt resolving last week's
address would fail the challenge and back off for minutes.

### 2.4 What stopped being reachable

Before this step the API and the UI each published a port, both open to `allowed_cidrs`.
Now only Caddy publishes anything.

| Route | Before | After |
|---|---|---|
| The UI | port 7860 | `/` over TLS |
| `/health`, `/idle` | port 8000 | proxied over TLS |
| `/chat`, `/tickets`, `/approvals`, `/session/...` | port 8000 | not routable from outside at all |

`/chat` writes to the database on the caller's behalf. It was reachable from any address in
`allowed_cidrs`; it is now reachable only from inside the compose network. The UI builds its
own agent in process and never calls the API over the network, so nothing is lost.

## 3. Comparison

No model is called and no task set is run, so task success rate, safety violations and cost
per successful task are unchanged by construction.

### 3.1 What was verified, on the real environment

| Check | Result |
|---|---|
| Delegation | `rsa.proshot.top` resolves through a public resolver to the instance |
| The record the instance wrote | `rsa.proshot.top -> 18.201.229.193`, TTL 60 |
| Certificate | `CN=rsa.proshot.top`, Let's Encrypt, valid 2026-09-09 to 2026-12-08 |
| Trust | `ssl_verify_result 0` from a stock client, no flags |
| The UI over TLS | 200, 59161 bytes |
| `/health` and `/idle` over TLS | both answer |
| `/chat`, `/tickets`, `/approvals` | 404: not routed |
| Ports 8000 and 7860 from outside | no answer |
| What the machine listens on | 80 and 443, nothing else |
| Port 80 | 308 to `https://rsa.proshot.top/` |

### 3.2 The certificate survives a stop, and the name follows the address

Stopped and started, then compared:

| | |
|---|---|
| Certificate serial before | `05E2E198208FD0B12164C8170A301A335E57` |
| Certificate serial after | `05E2E198208FD0B12164C8170A301A335E57` |
| Address before | `18.201.229.193` |
| Address after | `34.244.139.114` |
| A record after | `34.244.139.114` |

Same certificate, different machine address, same URL. Reissuing on every start would have
met Let's Encrypt's duplicate-certificate limit inside a week.

### 3.3 What the name costs in start time

| | Seconds to answering |
|---|---|
| M6.5, two plain ports | 29, then 35 |
| M6.6, one name over TLS | 66, twice |

About thirty seconds more, spent on updating the record, waiting for Route 53 to accept the
change, and starting a fifth container. Still inside M6.1's 120-second rule, with half of it
unspent.

## 4. Failure analysis and conclusion

**PASS.** One URL, a real certificate, and less exposed than before.

- **What was accepted**: the hosted zone and its delegation as code, the boot-time record
  update, Caddy, and the narrowing of what the instance publishes.
- **What got smaller**: the attack surface. Three write routes that were reachable from
  `allowed_cidrs` are now not routable from outside at all.
- **What got slower**: the start, by about thirty seconds, half of the remaining budget.
- **What is left running**: the demo environment, stopped, plus a hosted zone at 0.50 USD a
  month. Together with the volume that is 1.38 USD a month idle.

### 4.1 Not verified

- **Renewal.** The certificate is valid until December and Caddy renews with thirty days
  left. Nothing here has watched that happen, and it cannot be watched in an afternoon.
- **A machine left off past expiry.** Caddy should obtain a new certificate on the next
  start. Untested.
- **Anyone but the operator connecting.** `allowed_cidrs` holds one address. **A
  certificate is not a login**, and until authentication is on, that list is the only thing
  deciding who may use this. Opening it is the next step and it needs login first.
- **Streaming through the proxy.** Gradio's queue uses server-sent events and
  `reverse_proxy` passes them through, but the application does not stream yet, so nothing
  was streamed through it.
- **The delegation against a recreated zone.** The argument for putting it in code is that
  recreating the Route 53 zone issues different name servers; that recreation was not
  performed.
