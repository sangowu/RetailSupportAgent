# M6.2: package the application, and find out whether it starts in time

## 0. Why this step exists

M6.1 chose a shape on a decision rule with a 120-second restart budget, and measured
15 seconds of it. Those 15 seconds are Amazon Linux 2023 reaching a systemd unit that
serves a static file. The other 105 seconds have to hold everything this application
actually does on the way up: load an image, start PostgreSQL, run migrations, start the
API, start the UI, and answer.

Nobody knows whether it fits, because the application has never been packaged. There is no
Dockerfile. `compose.yaml` starts PostgreSQL and nothing else, and the application itself
has only ever run from a virtual environment on the developer's Windows machine through
`scripts/start-local.ps1`.

This is the one open number that can still overturn M6.1's decision. Terraform, HTTPS, the
idle timer and archiving are all plumbing with known shapes; if the stack cannot start
inside the budget, none of that plumbing matters and the shape has to be chosen again. So
it is measured before any of it is built.

M6.1 section 3.3 also left the disk size open, and therefore the idle cost. The image size
measured here is what closes it.

## 1. Change card

- **Stage and step**: M6.2
- **Type**: feature
- **The specific problem**: the application has no container image, and the 105 seconds of
  M6.1's restart budget that its own start has to fit into are unmeasured
- **The single theme of this change**: packaging the application and timing its start.
  Nothing about how it behaves once it is up.
- **Control variables this change does not touch**: the application code, the database
  schema, the migrations, the agent, the guard, the prompts, the model configuration, the
  evaluation harness and every baseline. The image is a new way to run the same code;
  section 1.3 states the test that checks it.
- **Explicitly out of scope**, each its own later step:
  - Terraform, and the base and demo layer split
  - HTTPS, the entry URL and login through it
  - The idle definition and the shutdown timer
  - Archiving on stop
  - A streaming UI, which stays with M7; M6 verifies only that streaming survives the
    entry path, and there is nothing to stream through yet
- **Expected benefit**: the budget question answered with a number, and the disk sized from
  a measured image rather than a guess.
- **Possible cost**: `t3.micro` has 1 GiB of memory and would have to hold PostgreSQL, the
  API, Gradio and the benchmark domain at once. If it does not, the instance type changes. That costs 0.0114 USD
  an hour more while running and nothing at all while stopped, so it is a small price, but
  it is a real possibility and not a surprise if it happens.

### 1.1 What gets built

| Piece | What it is |
|---|---|
| `Dockerfile` | one image for the application, able to run either the API or the UI |
| `compose.yaml` | extended from PostgreSQL alone to the whole stack, so the same definition runs locally and on the instance |
| A start path | migrations run once, before the API accepts traffic, and never twice concurrently |

One image, two roles. The API and the UI are separate processes with separate ports today
and stay that way; putting two servers behind one supervisor inside one container would
hide which of them failed.

### 1.1.1 A correction, made before any of it was built

This card first said the image would carry the runtime dependencies only, because the
`bench` group - litellm, tau2, pandas, langfuse - "exists to run evaluations and has no
business in a demo image". Checking it showed otherwise.

`RetailDomain.__init__` imports `tau2.domains.retail.environment`
(`src/retail_support_agent/domain.py:96`), so the running demo needs the benchmark package
and its data. Constructing one domain in the local environment pulls litellm, pandas and
numpy into `sys.modules` and takes 3.6 seconds. `pyproject.toml` already says as much - the
`bench` group is described as "needed only when actually running the domain environment or
an evaluation" - and the demo is a thing that runs the domain environment.

Three consequences, all of which this step now has to handle:

| | |
|---|---|
| Dependencies | `tau2` moves into a new `demo` group, which `bench` includes alongside `langfuse`. The demo needs the domain; only an evaluation needs the tracing. |
| Data | `third_party/` is not in Git, is fetched and SHA256-verified by `scripts/fetch_tau2.py`, and is 888 MB. The demo needs `data/tau2/domains/retail`, which is 34.6 MB. The other domains and the 604 MB of upstream results are not runtime data. A check loads the domain with only the retail data present. |
| Session cost | 3.6 seconds per `RetailDomain`, and `ui.py` builds one per session. That lands on the first message of a session, not on start, so it does not spend the restart budget - but it is measured and recorded here, because it is the same kind of number and this is where it was found. |

### 1.2 The two start times, which are not the same number

A stopped instance keeps its disk. So the image is pulled once, when the environment is
first created, and is already on local disk every time afterwards.

| | What happens | How often |
|---|---|---|
| First creation | pull the image from the registry, then start | once per environment |
| Restart | the image is already on the volume; start only | every demo |

The 120-second budget in M6.1 is a restart budget, so the second row is the one it applies
to. The first row is measured too, because it decides how long the very first start takes
and it is the number someone waits through when the environment is rebuilt.

### 1.3 What is measured, and the thresholds

| Metric | Threshold |
|---|---|
| Restart, from `start-instances` to both the API health route and the UI answering | under 120 seconds total, M6.1's rule |
| First creation, including the image pull | measured and recorded; no threshold, it is not the demo path |
| Image size | recorded, and used to size the disk and close M6.1 section 3.3 |
| A trimmed data directory | the retail domain loads with only its own data present, or the trimming is abandoned and the size recorded as it is |
| Peak memory of the whole stack under a smoke flow | fits the instance type with headroom, or the instance type changes |
| The existing test suite, run inside the image | passes unchanged |
| Migrations | applied exactly once, and a second start does not reset data |

The test-suite line is what protects the control variables. An image that changes
behaviour is not a packaging change.

### 1.4 The decision rule

Accepted only if the restart fits the budget, the suite passes inside the image, and
memory fits an instance type whose running cost is still in the same range.

If the restart does not fit, M6.1's shape is reopened and the budget is not raised to
match. That is why this step comes before the plumbing.

### 1.5 Baseline and previous version

There is no previous version: no image has ever been built. The reference is M6.1's
15-second empty boot, which the restart number must contain rather than replace. No task
set is run and no baseline moves.

## 2. Implementation and verification

### 2.1 Files

| File | Responsibility |
|---|---|
| `Dockerfile` | new; a builder stage, a test stage and a runtime stage, base image pinned by digest |
| `.dockerignore` | new; keeps the build context small and admits one path out of `third_party/` |
| `docker/entrypoint.sh` | new; selects `api`, `ui` or `migrate`, and runs anything else as given |
| `compose.yaml` | extended from PostgreSQL alone to the whole stack, with health checks and an explicit bind address |
| `pyproject.toml`, `uv.lock` | `demo` group split out of `bench`; the resolved package set is unchanged |
| `src/retail_support_agent/ui.py` | the UI's bind address and port read from the environment, defaulting to what they were |
| `.gitattributes` | shell scripts pinned to LF, for the reason in 2.4 |

### 2.2 Why the pieces are shaped this way

**One image, three roles.** The API and the UI are separate processes on separate ports and
stay that way. Migrations are a third role that runs once and exits rather than something
the API does on the way up, because two API containers starting together would otherwise
run them at the same time.

**The base image is pinned by digest**, not by tag. A tag moves, and a demo whose image
changes underneath it cannot be compared with the run before it.

**`uv sync --frozen`** refuses to update the lockfile during a build. An image whose
dependency set is resolved at build time is not the one that was tested.

**The UI's bind address became configurable**, defaulting to `127.0.0.1` exactly as before.
Inside a container the loopback address is reachable only from that container, so a demo
bound to it is not a demo. Exposing it takes an explicit `RSA_UI_HOST=0.0.0.0`, which is a
decision someone makes rather than one they inherit.

**The `demo` group** carries `tau2`; `bench` now includes `demo` and adds `langfuse`. The
lockfile changed by exactly two lines, both of them the new group, and resolved the same
144 packages at the same pinned commit.

### 2.3 The test stage, and why the suite is not baked in

The first attempt copied `tests/` into the image and ran pytest during the build. It failed
on 8 collection errors and then on dozens of tests, none of them about behaviour: the suite
reads frozen baselines, task sets, JSON schemas, the upstream manifest and the environment
template, and the runtime image deliberately carries none of those.

Copying a subset in would have meant choosing which tests to run. So the stage installs
the dependency set and the repository is mounted at run time:

```
docker build --target test -t rsa-test:local .
docker run --rm -v "$PWD":/repo -w /repo   -e TAU2_DATA_DIR=/repo/third_party/tau2-bench/data   rsa-test:local /app/.venv/bin/python -m pytest -q
```

Result: **529 tests, 0 failures, 0 errors, 106 skipped, 11.9 seconds.** The skips are the
`live_model` cases that need a billed API, plus two Langfuse wiring tests that the demo
group does not install. The same tests pass on the versions the demo image runs, so
packaging changed no behaviour.

### 2.4 Four failures worth keeping

- **`tau2` is pinned to a git commit, so resolving it needs git.** The first build died at
  `uv sync` with "Git executable not found". Git is installed in the builder stage only;
  the runtime stage has no use for it.
- **A CRLF entrypoint fails as "no such file or directory".** The error names the file, not
  the line ending, which is the wrong problem. The cause was local: a Python patch written
  on Windows rewrote the file with default newline translation. `.gitattributes` now pins
  `*.sh` to LF so a checkout cannot reintroduce it.
- **The suite cannot be baked in**, for the reason in 2.3.
- **Nested here-documents did not survive.** The measurement script writes three files onto
  the instance; generating them through nested quoting produced an unparsable script. They
  are base64 blobs substituted into a flat template instead.

## 3. Comparison

The template's metric table does not apply. No model is called and no task set is run, so
task success rate, safety violations and cost per successful task are unchanged by
construction. Section 2.3's test result covers the same ground: 529 tests, same outcome,
on the image's versions.

### 3.1 The two start times

Measured on one `t3.small` with a 20 GiB gp3 root volume, in `eu-west-1`. "Answered" means
both the API health route and the UI page returned, not that a process started.

| | Seconds |
|---|---|
| First creation: launch, install Docker, pull the image, migrate, start, answer | 122 |
| Restart, round 1 | 41 |
| Restart, round 2 | 39 |
| Stop, to the instance reaching `stopped` | 33 and 34 |

M6.1 measured an empty Amazon Linux 2023 boot at 15 seconds. This application adds about
25 seconds on top of it, which is what the 105 seconds of unspent budget had to cover.

### 3.2 Against the decision rule

| Metric | Threshold | Measured | |
|---|---|---|---|
| Restart to both endpoints | under 120 s | 41 s and 39 s | pass, with 79 s to spare |
| First creation | recorded, no threshold | 122 s | recorded |
| Test suite on the image's versions | passes unchanged | 529 tests, 0 failures, 0 errors | pass |
| Memory | fits the instance type with headroom | 675 MB used of 1913 MB | pass on `t3.small` |
| Migrations | applied once; a second start does not reset data | the migrate container exits 0 and the database volume survives both restarts | pass |
| Trimmed data directory | the retail domain loads with only its own data | 16 tools, 6699 characters of policy | pass |

### 3.3 Sizes, and the disk number M6.1 left open

| | |
|---|---|
| Image in the registry, compressed | 225 MB |
| Image on the instance's disk, uncompressed | 722 MB |
| Retail domain data inside the image | 34.7 MB, out of an 888 MB checkout |
| Whole root filesystem in use, stack running | 3.2 GB |
| PostgreSQL volume | 48 MB |

**M6.1 section 3.3 is closed, and the threshold holds.** The stack uses 3.2 GB of disk, so
an 8 GiB volume runs it with 4.8 GB to spare. At the `eu-west-1` gp3 rate that is 0.70 USD
a month, inside M6.1's 1 USD idle threshold, and below the 11 GiB that would have broken
it.

The three image sizes are three different things and are not in conflict: 225 MB is what
crosses the network, 722 MB is what sits on the volume, and Docker Desktop reports 1.03 GB
locally because its build also produces attestation layers that the instance never pulls.

### 3.4 Memory, and why the instance type changed

Section 1's "possible cost" happened. The stack uses 675 MB with idle containers, which
does not fit a `t3.micro`'s 1 GiB once the operating system and Docker are accounted for.
The measurement ran on a `t3.small`.

Per-process, measured inside the image:

| | Resident |
|---|---|
| Python, nothing imported | 15 MB |
| After importing the UI module | 208 MB |
| After building one `RetailDomain` | 317 MB |
| After building four | 352 MB |

The first domain costs 109 MB because it pulls in litellm, pandas and numpy; each one after
that costs about 12 MB. It also takes about 2 seconds to build, and `ui.py` builds one per
session, so that lands on the first message of a session rather than on start. It does not
spend the restart budget.

Running cost goes from 0.0114 to 0.0228 USD an hour, only while the demo is up. Idle cost
is the disk and is unaffected.

## 4. Failure analysis and conclusion

**PASS.** The application is packaged, and a restart answers in 41 seconds against a
120-second budget.

- **What was accepted**: the image, the test stage, the whole-stack compose file, the
  `demo` dependency group, and a configurable UI bind address.
- **What changed from the card**: section 1.1.1 records it. The demo needs the benchmark
  package and its data at run time, which the card first denied.
- **What this closes**: M6.1 section 3.3. An 8 GiB volume is enough, so the idle cost stays
  at 0.70 USD a month and M6.1's shape keeps its threshold.
- **What this settles**: the instance type is `t3.small`, from the memory figures in 3.4.
- **Nothing is deployed.** The measurement instance, its role, its security group and the
  registry repository were all deleted, and a sweep of EC2, ECR, IAM and security groups
  returns nothing.

### 4.1 Not verified

- **The application under load.** Every number here is one instance, no user, and no model
  call. The stack was proved to answer, not to answer well.
- **Streaming.** There is nothing to stream yet: `respond` in `ui.py` returns rather than
  yields. M6 is accepted on streaming surviving the entry path, and that entry path does
  not exist either. Both belong to later steps.
- **HTTPS, the idle shutdown, Terraform and archiving.** Untouched, as section 1 said.
- **The restart number on a busy database.** The PostgreSQL volume held 48 MB. A larger
  database takes longer to recover on start, and how much longer is not known.
- **Two restarts are not a distribution**, in the same sense M6.1 said it of three boots.
- **The image build needs a local verified checkout.** `third_party/` is not in Git, so the
  build is reproducible only where `scripts/fetch_tau2.py` has run. A build in CI would
  have to fetch it first, and that has not been tried.
