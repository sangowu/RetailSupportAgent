# M5.1: price a run by its own clock, and measure latency

## 0. Why this step exists

M5 optimizes against three axes at once: quality, latency and cost on the same tasks.
Quality has been measured task by task since M0.1. The other two have not.

**Cost is a function of when it is printed.** `analyze_eval.py` on the `baseline-v3` run
prints this today:

```text
agent cost: 20.3054 CNY (price snapshot 2026-09-06)
    [mismatch] upstream litellm says 10.152675 CNY, this script computes 20.305350 CNY.
    The two must be exactly equal; find out why before citing any cost figure
```

The ratio is exactly 2. DeepSeek's own endpoint charges a peak and an off-peak rate that
differ by exactly that factor, `price_for(model)` defaults its `moment` to
`datetime.now(UTC)`, and the run happened off-peak while the analysis is happening at
peak. litellm was given the price table once, at run start, so upstream's number is the
one that reflects what was actually spent. The script's number is what the same tokens
would cost if they were bought at this afternoon's rate. Neither the mismatch nor the
factor was a mystery in the code; it was simply never the question anyone asked, because
until M5 nothing depended on the absolute cost being right.

**Latency is one averaged number.** `average duration: 105s per task` covers the agent's
model calls, the simulated user's model calls, tool execution and the effects of running
two tasks at a time. The change report template asks for a system-side P95, and nothing
in the repository computes a percentile of anything. The measurement has been sitting in
the raw results the whole time: `generation_time_seconds` is recorded on 1428 of the 1542
assistant messages in the `baseline-v3` run, and no script reads it.

**Cost per successful task does not exist.** The template names it. Total cost divided by
114 is not it, and a configuration that is cheaper per call while failing more tasks is
cheaper only in the sense that giving up is cheap.

M5.1 fixes the instrument. It changes nothing that the instrument measures.

## 1. Change card

- **Stage and step**: M5.1, a prerequisite of M5.2
- **Type**: maintenance (measurement), no change to the agent and no evaluation run
- **The specific problem**: the cost of a past run is computed at the analysis clock
  rather than the run clock, which makes it wrong by a factor of two for every DeepSeek
  run analyzed in the other tier; there is no latency percentile; and there is no cost
  per successful task
- **The single theme of this change**: make cost and latency of an existing run
  measurable and reproducible, so that the M5 optimization steps have something to be
  judged against
- **Control variables this change does not touch**: the agent, the guard, the API, the
  database, the model under test, its parameters, the prompt, the simulated user, the
  judge, the task sets, the upstream commit, and **the numbers in the price snapshot**.
  No task is re-run, no baseline is re-frozen, and no existing raw result is rewritten.
- **Explicitly out of scope**:
  - **No optimization.** Nothing gets faster or cheaper in this step. A step that both
    changes the instrument and moves the number cannot say which one it did.
  - **No new evaluation run.** Everything here is computed from raw results already on
    disk, so this step spends nothing.
  - **No new prices.** The snapshot's rates and its date stay as they are. This step
    changes which moment a rate is looked up for, not what the rate is.
  - **No currency conversion.** CNY stays the unit, for the reason `pricing.py` records.
- **Expected benefit**: a cost figure that is the same number tomorrow as today, a
  latency distribution rather than a mean, and a single comparison that carries all three
  axes for M5.2 to fill in
- **Possible cost**: two cost figures instead of one, which is a reporting burden that
  has to be paid every time either is quoted; and a clock recovery step that can fail on
  a malformed run, which must then say so rather than guess

### 1.1 Design decisions fixed before the work

**A run is priced call by call, at each call's own moment.** Not at the analysis moment,
which is the defect, and not at the run's start either: a run takes about 1.7 hours and
the peak windows are 3 and 4 hours long, so a run can and eventually will straddle a
boundary. Pricing each call at the moment it was made is the only rule that does not need
an exception written for that case.

**The moment comes from the run's own files, never from the analysis machine.** Message
timestamps in the raw results are naive local time from whichever machine ran the
evaluation; `run_id` is UTC by construction. The offset is recovered per run by comparing
the two and rounding to the nearest quarter hour, then checked against the run's wall
time. A run that fails the check is priced at its start tier and says so in the output.
Reading the analysis machine's own timezone would be the same class of error this step is
fixing, one step removed. New runs record the offset directly, so the recovery is only
for the runs already on disk.

**Two cost figures, each named.** *Actual spend* prices every call at its own moment and
answers "what did this run cost". *Normalized cost* prices every call at one stated tier
and answers "what does this configuration cost", which is the question a comparison
between two configurations asks. Reporting one of them alone is what makes a cheaper
configuration indistinguishable from an off-peak one.

**Latency means the agent's own model call.** The per-call `generation_time_seconds` is
the only figure in the raw results that measures this system rather than the harness
around it: task duration also contains the simulated user's thinking, and it is inflated
by running two tasks at once. Task duration is still reported, under its own name, and is
never called latency.

**Cost per successful task divides by the tasks that passed.** A configuration that saves
tokens by failing is not a saving, and this is the metric that says so.

### 1.2 Acceptance thresholds

| Metric | Threshold |
|---|---|
| Cost agrees with upstream | For a run that lies inside one tier, this script's agent cost equals `agent_cost_reported_by_upstream` exactly, and the mismatch warning is gone |
| Cost is stable in time | The same run analyzed at a peak moment and an off-peak moment reports the same actual spend |
| Tier crossing is handled | A run spanning a boundary is priced per call and reports the split, rather than picking one tier for all of it |
| Clock recovery is checked | A run whose recovered offset does not fit its wall time is priced at its start tier and says so, rather than pricing calls at invented moments |
| Latency is a distribution | P50, P95 and max of the agent's per-call latency, plus the task-duration distribution, reported separately and never conflated |
| Cost per successful task | Reported alongside cost per task, with the number of successes it divides by |
| Historical runs still analyze | All 26 existing run directories analyze without error |
| The comparison carries three axes | `compare_runs.py` reports quality, latency and cost for the same shared tasks, with the sample size |
| Nothing measured is changed | `git diff` shows no behavioural change to the agent, the guard, the benchmark subject or the price values |

- **Baseline, previous version, task set and protocol**: the `baseline-v3` run directory
  `20260908T121800Z_deepseek-v4-pro_full_guarded` is the fixture for every threshold
  above. No score is compared, because nothing is re-run and the scores cannot move.

## 2. Implementation

| File | Responsibility |
|---|---|
| `src/retail_support_agent/run_metrics.py` | New. The run's clock, per-call cost at each call's own moment, latency distributions |
| `scripts/analyze_eval.py` | Prices by the run's clock, prints the latency section and cost per successful task |
| `scripts/compare_runs.py` | Quality, latency and cost, all three over the tasks both runs scored |
| `scripts/run_eval.py` | Records `local_utc_offset_seconds`, so a future run needs no recovery |
| `tests/test_run_metrics.py` | 31 tests, one class per part of the instrument |

Nothing under `src/retail_support_agent/` that the service or the benchmark subject runs
was touched. `run_metrics.py` is new and is imported only by the two analysis scripts.

### 2.1 How a moment is recovered

The first message of a run is the opening line of its first task. It is generated
locally, a moment after `run_id` is taken with `datetime.now(UTC)`, and it is written
with the machine's naive local time. The gap between the two is therefore the machine's
offset plus a second or so of setup. Round it to a quarter hour and the offset is back.

The leftover is the check. A gap that is not close to a whole quarter hour is not a
timezone, and rounding it would invent an hour that nothing observed; five minutes is the
tolerance, against a measured setup time of under a second. A run that fails it is priced
at the tier of its start, and the output says the clock could not be recovered.

Messages arriving after the recorded wall time are a different matter and do **not**
reject the offset. That is what a resume looks like: `resume_run.py` writes its results
into the original directory hours or days later and never rewrites `summary.json`. Two of
the twenty-six runs on disk are like that. The offset stays, and a note says why the run
looks longer than it recorded.

### 2.2 Two costs, and which question each answers

| Figure | Priced at | Answers |
|---|---|---|
| Actual spend | each call's own moment | what this run cost |
| Normalized | one stated tier, the same for both runs | what this configuration costs |

`compare_runs.py` prints both, and it charges both runs for the **shared tasks only**.
That last part is not a detail. Comparing two runs of different sizes on their totals
reported a candidate as 93.6% cheaper than its baseline; over the tasks both actually ran,
the same pair differs by 4.9%. The first number is the baseline having run twelve times
as many tasks.

### 2.3 What is not called latency

`generation_time_seconds` is the agent's own model call and is reported as p50, p95 and
max. Task wall clock is reported next to it, under its own name, because it also contains
the simulated user's model calls and is inflated by however many tasks ran at once. The
two are never added, and a run that recorded no per-call timing reports that rather than a
zero.

## 3. Results

Every threshold was checked against the raw results already on disk. No task was re-run,
so this step spent nothing.

### 3.1 The acceptance thresholds

| Metric | Threshold | Measured | Result |
|---|---|---|---|
| Cost agrees with upstream | equal to `agent_cost_reported_by_upstream`, exactly | `baseline-v3`: 10.152675 CNY both ways; 7 of 7 runs that carry an upstream figure and lie in one tier now agree | pass |
| Cost is stable in time | the same answer whenever it is read | no price lookup takes the current time; a call with no moment on a time-varying model is reported unpriced rather than charged at today's rate | pass |
| Tier crossing is handled | priced per call, with the split reported | the 2026-09-07 holdout run: 49 calls off peak, 393 at peak, 5.7012 CNY, against 6.0624 at peak and 3.0312 off peak | pass |
| Clock recovery is checked | a run that fails the check says so | the check became the quarter-hour residual rather than the wall time; see 3.4 | pass, changed |
| Latency is a distribution | p50, p95, max, separately from task duration | `baseline-v3`: agent call p50 2.86s, p95 15.30s, max 59.95s over 1428 calls | pass |
| Cost per successful task | reported with the count it divides by | `baseline-v3`: 0.0954 CNY per task, 0.1066 CNY per successful task, 102 passed | pass |
| Historical runs still analyze | all 26 directories, no error | 26 of 26, and no run reports a mismatch any more | pass |
| The comparison carries three axes | quality, latency and cost on the shared tasks | see 3.3 | pass |
| Nothing measured is changed | no behavioural change to the agent or the prices | `git diff` touches three scripts, adds one module and one test file; `agent.py`, `guardrails.py`, `bench_agent.py`, `pricing.py` and the price values are untouched | pass |

### 3.2 What the instrument says about `baseline-v3`

| Measurement | Value |
|---|---|
| Agent model call, p50 / p95 / max | 2.86s / 15.30s / 59.95s over 1428 calls |
| Task wall clock, p50 / p95 | 93s / 188s over 114 tasks |
| Share of wall clock inside agent calls | 59% |
| Actual spend, three roles | 10.8742 CNY, all of it off peak |
| Cost per task / per successful task | 0.0954 / 0.1066 CNY |

The 59% is the first number the project has for where a task's time goes. The rest is the
simulated user's own model calls, the tools and the harness. A latency optimization aimed
only at the agent has that as its ceiling.

### 3.3 The first three-axis comparison

Run against `baseline-v2` (upstream's agent) and `baseline-v3` (this project's guarded
agent), the same 114 tasks:

| Axis | baseline-v2 | baseline-v3 |
|---|---|---|
| Passed | 97 | 102 |
| Agent call p50 / p95 | 2.55s / 13.83s | 2.86s / 15.30s |
| Task wall p50 | 54s | 93s |
| Normalized cost at peak | 18.449 CNY | 20.305 CNY |
| Per successful task | 0.1902 CNY | 0.1991 CNY |

Paired, the guarded agent is 29.9s slower per task at the median and costs 10.1% more in
tokens. That is the price of the confirmation turns, and it had never been quantified.
The two are different subjects under test, so the scores stay side by side and are not
averaged, exactly as `baseline-v3` records; the cost and latency comparison is unaffected
by that, because both ran the same tasks against the same stack.

### 3.4 What changed from the change card

The card said a recovered offset would be checked against the run's wall time and that a
run failing the check would be priced at its start tier. Implementing it showed the check
rejects a case it should not: a resumed run's last message is legitimately hours past the
recorded wall time, and the 2026-09-07 holdout run was refused a clock for exactly that
reason while its offset was demonstrably right, its first message landing 0.66s after the
run id.

The check moved to where the evidence is. The offset is derived from the first message, so
the residual after rounding is the thing that can falsify it, and a gap that is not close
to a quarter hour is refused. The wall-time overrun became a note. The refusal path still
exists and is still tested; it now fires on the case that means something.

### 3.5 Not verified

- **Anything about a different configuration.** No run was made. This step says what the
  existing runs cost and how long they took, and nothing about what a different thinking
  level would do. That is M5.2.
- **Latency as a server-side number.** `generation_time_seconds` is the round trip as this
  machine measured it, including the network and whatever queuing the provider did, with
  two tasks in flight. It is the right number for "how long did the agent wait", and it is
  not the provider's own processing time.
- **The clock of runs made elsewhere.** Every run on disk came from one machine at UTC+1.
  The recovery is verified against upstream's independent accounting on the 7 runs that
  carry one, and 17 of the runs predate that accounting entirely, so for those the offset
  rests on the residual check alone.
- **The prices themselves.** The snapshot is dated 2026-09-06 and this step did not
  re-check a single rate. A stale price is now applied to the correct hour.
- **The application path.** This measures evaluation runs. The FastAPI service's own
  per-turn latency is not covered here; M4 measured its database reads, and a per-turn
  breakdown of the service is not part of this step.
- **Cost of the simulated user and the judge per task.** Both are reported per run. The
  judge's usage is recorded per run and cannot be split by task, so the shared-task
  comparison covers the agent side only and says so.

## 4. Conclusion

**PASS.** All nine thresholds are met, one of them by a rule that changed during the work
for a reason recorded in 3.4 rather than quietly.

What this step adds, in one line: the cost of a run is now the same number tomorrow as
today, latency is a distribution instead of an average, and a comparison charges two runs
for the same tasks.

What it leaves open is that nothing has been optimized. The instrument now reads correctly
on runs that already exist; M5.2 is the first step that changes a configuration and has to
justify it on quality, latency and cost together.
