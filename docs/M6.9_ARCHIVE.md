# M6.9: what survives the machine

## 0. Why this step exists

`terraform destroy` removes the instance and its volume, and everything the demo
accumulated goes with it: the sessions, the audit trail, the tickets, the approvals, the
timings. So does any change that still replaces the instance, which M6.8 narrowed to the
machine's own scaffolding but did not eliminate.

Until now that has been affordable because the database held nothing anybody wanted. That
stopped being true in M6.7. The demo now runs under real accounts, and the audit trail is
the record of who did what - which is the evidence this whole project exists to produce.
A record that a routine teardown deletes is not a record.

M6's acceptance line names archiving alongside teardown, and this is the last of the six.

## 1. Change card

- **Stage and step**: M6.9
- **Type**: feature
- **The specific problem**: the demo's history exists in one place and a teardown deletes it
- **The single theme of this change**: what the demo recorded outlives the machine that
  recorded it
- **Control variables this change does not touch**: the model, the simulated user, the
  judge, the task sets, the upstream commit, the price snapshot, the agent, the guard, the
  authorization model, the name and certificate, the idle verdict, the version mechanism
  from M6.8, and every baseline
- **Explicitly out of scope**:
  - **Archiving the certificate.** Caddy's `/data` holds a private key. A credential
    belongs in a secret manager, not in an archive that exists to be read later, and the
    alternative costs a two-minute reissue.
  - **Automatic retention.** Section 1.5 says why an expiry timer is the wrong shape here.
  - **Restoring into a different account or region**, and **point-in-time recovery**. This
    is a demo's history, not a production database.
  - **Streaming.** M7, and the last thing outstanding after this.
- **Expected benefit**: a teardown, and any future instance replacement, stop being
  destructive
- **Possible cost**: a bounded delay on every stop, and one more thing that can fail
  quietly. Section 1.4 is about making it fail loudly instead.

### 1.1 What is archived, and what it is for

The application database, whole, as a plain SQL dump. Not a subset: choosing which tables
matter is a decision that has to be right forever, and the whole thing is a few hundred
kilobytes.

Plain SQL rather than a custom-format dump, because an archive that can be read with
`zcat` is one somebody will actually look at, and the size difference is irrelevant here.

It goes to the `archives/` prefix of the bucket that already holds Terraform's state. M6.4
created that prefix and the instance role's write access to it, scoped so a demo cannot
reach the state next to it.

### 1.2 When it runs

**On every stop**, from the unit's `ExecStop`, before the containers come down. The
instance already stops itself whenever nobody has used it for fifteen minutes, so this
means the newest archive is never much older than the last time anyone used the demo, and
an unplanned instance replacement loses at most one idle period.

**On demand**, with `demo.py archive`, which is what an operator runs before a teardown
they have planned.

Not on a timer. A timer would archive an unchanging database repeatedly and would still
miss the last thing that happened before a stop.

### 1.3 Why restoring an identity is not a way back in

The dump includes `identities` and `role_memberships`, so restoring an archive can
reinstate an account that was deliberately removed from `demo_accounts`.

That is safe, and the reason is worth stating because it is the whole shape of the design.
A row in `identities` maps a token's subject to a retail identity; it grants nothing on its
own. Reaching it requires a token the user pool signed, and Terraform removes the account
from the pool when it is removed from the configuration. A subject that no longer exists in
the pool can never present a token, so the restored row authorizes nobody.

**The archive is the record of what happened. The pool is the record of who may act.** A
restore never lets the first decide the second.

### 1.4 How a failed archive is noticed

An archive that silently stops being written is worse than no archive, because it is
believed.

The instance is about to stop, so there is nowhere on it to report to. Instead the archive
itself is the signal: `demo.py status` prints the newest archive and its age, and an
archive that stops being written shows up as an age that keeps growing. That is a check an
operator can do in one command and one that is done every time they look at the
environment.

The archive is given a bounded time and its failure does not block the stop. A machine that
will not shut down costs money by the hour, which is the failure M6.1's whole shape exists
to avoid; a missed archive costs one idle period and is visible in the next `status`.

### 1.5 Why there is no expiry rule

The interesting archive is the last one before a teardown, and it becomes interesting
precisely when somebody comes back to the project after a while. A lifecycle rule that
deletes objects after ninety days would delete exactly that one, and would do it silently.

The volume is a few hundred kilobytes several times a day. Left alone, it is cheaper than
the rule that would manage it.

### 1.6 This step replaces the instance one last time

`ExecStop` changes, which changes the unit file, which changes user data. M6.8 named this
category and accepted it: the systemd units are the machine rather than the application.

It is worth noting that this is the change that makes the category stop mattering. After
this, a replacement loses at most the idle period since the last archive.

### 1.7 Primary metric, protective metrics, acceptance thresholds

Fixed before running, per `MODEL_EXPERIMENTS.md`.

| Metric | Threshold | If not met |
|---|---|---|
| An archive is written on every stop | after `demo.py stop`, an object exists under `archives/` newer than the stop | FAIL |
| The archive is readable | it decompresses, and its row counts match what the database held | FAIL |
| No credential is in it | the dump contains no model key, no token and no password | FAIL |
| Losing the database is survivable | with the volume destroyed and the stack restarted empty, a restore brings the audit trail, the tickets and the sessions back | FAIL |
| A restore refuses on a busy application | the same rule `stop` and `restart` use | FAIL |
| The stop is not delayed unboundedly | archiving is bounded and the time is measured | Investigate |
| A failed archive is visible | `demo.py status` reports the newest archive and its age | FAIL |
| Idle cost | unchanged: S3 storage for a few hundred kilobytes is below the threshold's resolution | FAIL |
| Degradation | the local stack and the whole suite are unaffected | FAIL |
| Evaluation score | Not applicable. Section 3 confirms by import graph, as M6.7 and M6.8 did | - |

### 1.8 How the restore is measured, and what is deliberately not repeated

The measurement destroys the **database volume**, not the instance: the stack comes back
with an empty database, migrations and seeding run, and the archive is restored into it.
That is exactly what a rebuild does to the data, and it is the harder half.

A full `terraform destroy` and re-apply is **not** repeated here. M6.4 verified the teardown
and checked it against the inventory, and repeating it would consume a Let's Encrypt
issuance for the same name while proving nothing further about the archive. Stated rather
than quietly skipped.

### 1.9 Baseline and evaluation protocol

- Baseline: `baseline-v3` (this project's guarded agent) on the full 114-task split, protocol `evaluation/protocol.md` at
  the pinned upstream commit `fc0055dc4e0a316c3f83133267fbd6faaa770992`.
- No re-run. This step adds scripts to the instance and two commands to the operator's
  tool, and changes no module the benchmark imports.

## 2. Implementation

| File | Responsibility |
|---|---|
| `deploy/instance/archive.sh` | Dumps the database whole and puts it in the bucket |
| `deploy/instance/restore.sh` | Brings one back, in a single transaction, with nothing writing |
| `deploy/instance/rsa-stop.sh` | The order the stop happens in, and the bound on it |
| `deploy/instance/rsa.service` | `ExecStop` is one script now, and the unit waits for it |
| `deploy/instance/cloud-init.sh.tftpl` | Installs the three, and names the bucket |
| `deploy/terraform/demo/main.tf` | Passes the bucket in, and tags the instance with it |
| `scripts/demo.py` | `archive`, `restore`, and the age in `status` |

### 2.1 Decisions made during the work

**One `ExecStop`, not two.** systemd stops at the first `ExecStop` that fails, so an archive
and a `docker compose down` as two lines would mean a failed archive leaves the containers
running - the exact failure the bound on the archive exists to prevent. One script, with
the archive's failure swallowed deliberately and the stack coming down either way.

**The scripts bring their own environment.** They are reached two ways: `ExecStop`, which
inherits the unit's `EnvironmentFile`, and Systems Manager, which inherits nothing. Both
now source `/etc/rsa-demo.env` themselves. Section 2.2 says how that was found.

**The bucket is an instance tag.** The same shape as the domain, for the same reason: this
tool finds the environment by tag and should not need Terraform's state to find that
environment's history. It also means `status` can report the archive for an instance that
is switched off, which is this environment's normal state.

**A restore names its archive.** `latest` or a key, never a default. It replaces the
database, and a command that does that on a bare word is one somebody runs by accident. The
key is checked against a pattern before it is used, because it is interpolated into a
command that runs as root on the machine.

**The restore stops the writers, not the database.** The API and the UI come down, `db`
stays up because it is what is being restored into, and a trap brings the writers back
whatever happens. A restore that fails and leaves the demo with no API is a worse outcome
than the state it was trying to fix.

**One transaction.** `--single-transaction` with `ON_ERROR_STOP`, so the result is the
archive or the database that was already there. A half-applied restore would leave a schema
that matches neither, which is the state nothing else in this project knows how to reason
about.

### 2.2 Three defects found by doing this

**The archive worked from systemd and failed from Systems Manager.** `docker compose`
interpolates the stack definition from the environment, and refuses to start without it. The
unit supplies that through `EnvironmentFile`; a Systems Manager session supplies nothing, so
`compose exec` failed on a variable it could not resolve. The automatic archive on stop
would have worked perfectly and `demo.py archive` would have failed every time. Found
before deploying, by running the command through Systems Manager while preparing the
measurement. Both scripts now source the file, and a test pins it.

**`status` did not report the archive for a stopped instance.** It returned early for
anything not running, and a stopped instance is what this environment is most of the time -
including the minute before a teardown, which is exactly when the age is worth reading. The
one signal a silently failing archive gives was therefore invisible in the case that
matters most. The report now comes before the early return, and a test pins it.

**The restore printed PostgreSQL's chatter as its result.** `psql` prints a row for every
sequence the dump resets, and `demo.py restore` reads that stdout to learn which object it
restored. The fix is a redirect; errors still reach stderr and `ON_ERROR_STOP` still fails
the command. Measured before and after: section 3.1's restore was run twice, once with the
noise and once with it gone.

## 3. Comparison

### 3.1 The thresholds from section 1.7, measured

The environment: instance `i-0e4b76e870a950271` in eu-west-1, image `m6.8.1`, bucket
`rsa-569260897196`, `https://rsa.proshot.top`. The apply replaced `i-01921264ec4b387c9`, as
section 1.6 said this one last change would: 1 to add, 1 to destroy.

**The history being protected was written by the application**, not inserted. A full
cancellation flow through the agent: identity verified, the guard holding the write for
confirmation, the write landing on confirmation. Then a second conversation escalated and
opened ticket 1. Twelve tables, twenty-two messages, two sessions.

**An archive is written on every stop**, and the two kinds of stop were measured separately
because they are different paths:

| Stop | Archive | Timing |
|---|---|---|
| `systemctl stop rsa.service` | written at 10:11:37, before the containers came down at 10:11:51 | 15s for the whole stop |
| `demo.py stop`, which is an EC2 stop and an ACPI shutdown | written at 10:40:28 | `stopped` between 20s and 40s after the command |

The second is the one worth having: it is the path the idle watcher uses, and it is most of
the stops this environment ever does.

**Losing the database is survivable.** The database volume was destroyed, not the instance.
The stack came back on an empty one, migrations and seeding ran, and the archive written by
the stop was restored into it.

| Table | Before | After the volume was destroyed | After the restore |
|---|---|---|---|
| `alembic_version` | 1 | 1 | 1 |
| `approvals` | 0 | 0 | 0 |
| `audit_events` | 1 | 0 | 1 |
| `confirmations` | 1 | 0 | 1 |
| `identities` | 3 | 3 | 3 |
| `messages` | 22 | 0 | 22 |
| `operations` | 1 | 0 | 1 |
| `role_memberships` | 3 | 3 | 3 |
| `session_claims` | 2 | 0 | 2 |
| `sessions` | 2 | 0 | 2 |
| `ticket_assignments` | 0 | 0 | 0 |
| `tickets` | 1 | 0 | 1 |

The three identity rows in the middle column are the seeding, which runs at every boot and
is why an empty database is not an inaccessible one.

Counts are not content, so the content was read back too: ticket 1, open, bound to the
session that escalated; the first three messages of the other session, word for word what
was said to the agent and what it answered.

**The archive is readable.** 5,985 bytes gzipped, 983 lines of SQL, all twelve tables
present as `COPY` blocks. It decompresses with `zcat` and needs nothing from this
repository to read.

**No credential is in it.** The dump was scanned for key-shaped, token-shaped and
password-shaped strings: zero matches. That is what the design predicts rather than a
lucky result - the model key is in Parameter Store and the passwords are in the user pool,
and neither has ever been in the database.

**A restore refuses on a busy application.** This measured itself: the restored ticket was
open, so the second restore was refused before it started.

```
not restoring, work is unfinished: 1 open ticket(s)      exit 2
restoring onto i-0e4b76e870a950271 anyway, overriding: 1 open ticket(s)
```

The same verdict the idle watcher and `stop` use, and `--force` says what it overrode.

**The stop is not delayed unboundedly.** The archive is bounded at 120 seconds inside
`rsa-stop`, the unit allows 180, and EC2 allows about four minutes before it pulls the
power. Measured, the archive took 7 seconds on demand and the whole stop 15.

**A failed archive is visible.** After the fix in section 2.2:

```
i-0e4b76e870a950271  stopped
  https://rsa.proshot.top
  archive:    archives/rsa-20260910T104028Z.sql.gz  73s ago
```

**Idle cost is unchanged.** Three archives, 15.5 KB in total, in a bucket that already
exists. Below the resolution of M6.1's 1 USD a month threshold by four orders of magnitude.

**Timing, for the operations this adds:**

| Operation | Seconds |
|---|---|
| `demo.py archive` | 7 |
| `demo.py restore latest` | 41 |
| Stack start on an empty volume, migrations and seeding included | 71 |
| First boot of the replaced instance, Docker install and image pull included | 140 |

**Degradation**: the local stack is untouched, and the whole suite passes.

| | Tests |
|---|---|
| Before this step | 710 |
| After | 754 |

**One thing that was not a threshold and is worth recording.** `rsa.service` was `active` on
the new instance's first boot. That is M6.8's health-check fix confirmed on a machine built
from scratch rather than on the one it was applied to.

## 4. Failure analysis and conclusion

### 4.1 What this changes about how the project is operated

A teardown is now a decision about an environment rather than about its history. So is an
instance replacement, which was the thing M6.8 narrowed and could not remove: the units are
still the machine, and changing them still replaces it, but a replacement now costs the idle
period since the last archive rather than everything the demo ever recorded.

The measurement made that concrete without being asked to. This step's own apply replaced
the instance, the database volume was then destroyed deliberately, and the audit trail, the
tickets and the sessions came back from an archive the machine had written on its way down
without anybody asking it to.

### 4.2 Limits of these results

- **The history was written with authentication disabled.** A temporary API container,
  same image and same database, wrote it through the real endpoints and the real agent,
  because minting a token would have meant a credential passing through a command log. So
  the rows carry the demo identity rather than a signed-in subject. What this measures is
  that the whole database round-trips; what it does not measure is a dump containing a
  Cognito subject, which is the same column with a different string in it.
- **One archive, restored twice.** Both restores were of the same object. Nothing here
  exercises restoring an older archive over a newer database, which is the case where an
  operator most wants to be sure about what they are about to lose.
- **The certificate the new instance serves predates it.** Serial `069B7F…9562`, valid from
  09:05:58; the instance booted at 10:00:53 with an empty Caddy volume. The certificate is a
  genuine Let's Encrypt certificate for the name and the demo answers over it, but why the
  new machine holds one issued before it existed is not established here, and the
  certificate transparency logs have no record of this name to check against. It touches no
  threshold in this step and is recorded rather than explained.
- **A restore signs everyone out**, because the API and the UI are stopped while the
  database is replaced and the UI holds its sessions in process memory.
- **The measurement's own history was deleted afterwards.** An open ticket holds the machine
  open, so leaving one would have kept the instance running until its uptime cap. The rows
  were cleared before the final stop, which is why the last archive is 3,507 bytes rather
  than 5,985.

### 4.3 Conclusion

**PASS.** Every threshold in section 1.7 was met. The database is archived on every stop
including the one the idle watcher does, an archive was restored onto a destroyed volume
with all twelve tables matching, the restore refuses on unfinished work, and the age of the
newest archive is one command away whether the machine is running or not.

Accepted also because doing it found three defects, two of which would have made the
operator's half of this feature fail every time while the automatic half worked - which is
the failure mode section 1.4 is entirely about.

### 4.4 What this leaves for later

- **M6 is complete.** Six steps: an instance that stops itself, a name and a certificate,
  a login, a rollback that keeps the machine, a teardown, and now a record that survives
  all of them.
- **Streaming**: M7, and the next thing. `ui.py`'s `respond` still returns rather than
  yields, so a long answer arrives all at once after a silence.
- **A restore across versions.** Restoring an archive taken under an older schema is not
  something this step tried. The dump carries `alembic_version`, so the shape of the answer
  exists; whether the application tolerates being pointed at the older schema is a question
  for whenever a migration next changes a table the archive holds.
