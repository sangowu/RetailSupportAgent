# M0.1 protocol and environment freeze

Status: implemented and verified locally. Date: 2026-09-06.

This step fixes only which version of the benchmark is evaluated, how tasks are split,
what results look like, and what CI checks. No model was called, no success-rate or
latency number was produced, and no cloud resource was created.

Upstream is not committed here (`third_party/` is gitignored). It is fetched at the
commit and verified file by file with SHA256:

```bash
uv run python scripts/fetch_tau2.py              # fetch and verify
uv run python scripts/fetch_tau2.py --verify-only
uv run python scripts/regen_manifest.py          # regenerate after an upstream change
```

13 files are pinned in `evaluation/tau2_manifest.json`: the policy, the database, tasks,
splits, simulated-user guidelines, the retail tools and data model, the environment, and
3 evaluator files. The manifest is generated by `scripts/regen_manifest.py` rather than
maintained by hand; after an upstream change it is regenerated and the output reviewed
with `git diff`.

**The line-ending trap, exposed and fixed by the first CI run.** Windows'
`core.autocrlf=true` rewrites upstream files to CRLF, so the same commit produces two
different sets of SHA256 values on Windows and Linux: green locally while all 13 files
mismatched in CI. `fetch_tau2.py` now checks out with `core.autocrlf=false` and
`core.eol=lf`, so digests always cover the bytes as upstream committed them, and
`tests/test_upstream_checkout.py` asserts the setting is not changed back.

**Attribution**: the data, tools, policy and evaluators are upstream's work. This
project only calls them and must not present them as its own implementation in a report
or a demonstration.

### 2.3 Scoring semantics

- The final reward is the product of the active components, and which apply comes from
  each task's `reward_basis`.
- Retail distribution: 112 tasks use `DB + NL_ASSERTION`, 2 use `DB` only.
- The `DB` component compares the final database state (`evaluator_env.py`), which is
  exactly this project's requirement to judge success by the final business state.
- The `NL_ASSERTION` component is an LLM judge (`evaluator_nl_assertions.py`).
- The `communicate` and `action` components are not in retail's reward_basis and are
  diagnostic only; they cannot stand in for a score.

**Cost consequence, to be budgeted in M0.2**: every task involves at least three model
roles, the agent under test, the simulated user and the NL judge. The latter two must be
frozen and must not change with the candidate agent, or cross-model comparison does not
hold.

## 3. Key finding: the declared scope does not match the benchmark

Labelling all 114 tasks by their write tools gives
(`evaluation/task_sets/scope_labels.json`):

| Label | Meaning | Count |
|---|---|---|
| `read_only` | Scored actions use no write tool | 8 |
| `in_scope_write` | Cancellation or return only | 34 |
| `out_of_scope_write` | Exchange, order modification, address or payment change | **70** |
| `no_action` | Upstream gives no scored action | 2 |

**The three declared flows (lookup, cancel, return) cover 42 of 114 tasks, 36.8%.**
`docs/DEVELOPMENT_PLAN.md` M0.1 requires checking whether the pinned version contains
the three kinds of task needed. They exist, but they are not the whole set and are under
four tenths of it.

### The frozen convention (confirmed by the user 2026-09-06: run the full set per
upstream's design)

The gap costs almost nothing to implement: the tools come from upstream's `RetailTools`
and are not rewritten; only which tools are exposed to the agent is a decision. So:

1. **The evaluation runs upstream's full set** with all 16 tools exposed. Only then is a
   "τ²-bench Retail score" a standard number that can be quoted externally.
2. **The product narrative stays on the three flows**: the Gradio demo, the permission
   rules and the confirmation rules are designed around lookup, cancel and return.
3. **Results are reported layered by `scope_label`**: the overall score and the 42-task
   in-scope subset are both given, and neither stands in for the other.

The label affects only how results are sliced; it does not modify upstream tasks, policy
or scoring.

An alternative was considered and rejected: running only the 42-task subset. That could
no longer be called a standard τ²-bench Retail run, and it would shrink the holdout from
40 tasks to 13, too few to support a selection conclusion.

**This convention was locked before any candidate result existed**, as
`MODEL_EXPERIMENTS.md` requires. Changing it later must be a separate change with
re-verification, never an adjustment made after seeing results.

Upstream's official split is used rather than a random one of our own, so a "custom
split" cannot become the reason scores are incomparable. `tests/test_task_sets.py`
asserts that dev and holdout are disjoint, that the counts match the manifest, and that
the labels cover every task.

## 5. Raw result and run manifest formats

- `evaluation/schemas/run_manifest.schema.json`: a complete, reproducible description of
  one run. It requires the code commit and whether the working tree was dirty, the
  upstream commit and whether verification passed, the task set and trial count, **the
  exact model id requested and the model id the server returned**, per-parameter
  accepted / rejected / ignored / remapped status, a prompt digest, the simulated-user
  and NL-judge configuration, execution limits and the interleaved run batch, the price
  snapshot, and the Langfuse trace.
- `evaluation/schemas/task_result.schema.json`: per-task raw results. `outcome` must
  distinguish `task_failure` / `service_error` / `unsupported_param` / `timeout` /
  `truncated` / `max_steps_exceeded`, so service errors do not contaminate the business
  failure rate, and usage separates thinking from cached tokens.

Both map directly onto two rules in `AGENTS.md`: HTTP 200 is not proof a budget limit
took effect, and unsupported parameters, service errors and insufficient evidence are
recorded separately.

## 6. CI and gate status

`.github/workflows/ci.yml` has three jobs:

| Job | Contents | Status |
|---|---|---|
| `static-and-unit` | `ruff format --check`, `ruff check`, `mypy --strict`, `pytest -m "not live_model"` | passing on GitHub |
| `upstream-pin` | Fetch at the pinned commit and verify every file's SHA256 | failed on the first run (line endings), passing after the fix |
| `evaluation-gate` | Verify the baseline checksums | active from M0.5; runs no evaluation and produces no new numbers |

> Update 2026-09-07: `baseline-v1` was frozen in M0.5 and this job now verifies baseline
> integrity (see [M0.5 part three](M0.5_BASELINE.md)). It still runs no evaluation and
> produces no success-rate or latency numbers, because a run costs real money. The actual
> candidate-versus-baseline performance comparison is M5's subject; the rules are in
> `EVALUATION_AND_GATES.md`.

The `live_model` pytest marker is registered, so tests that need billed calls stay out of
CI by default.

Local verification 2026-09-06: ruff clean, mypy clean over 9 source files, pytest 16
passed.

The first CI run caught a cross-platform defect that local runs could not (the line
endings in section 1), which is exactly why the `upstream-pin` job exists: a digest pin
that holds on only one platform is not a pin.

## 7. Explicitly not done in this step

- No model was called, and the availability of the 5 candidate model ids is still
  unverified (M0.2).
- Whether thinking parameters actually take effect is unverified; the capability table in
  `MODEL_EXPERIMENTS.md` is still inferred from documentation.
- The business loop, FastAPI, LangGraph and Gradio are not implemented (M0.3).
- The simulated user and NL judge are not chosen, and the total evaluation cost is not
  estimated (a prerequisite of M0.2).
- The `agent` / `api` / `ui` dependency groups are declared and locked but not installed;
  CI syncs only the dev group.
- Verified only on GitHub Actions ubuntu-latest; macOS and other Python versions are
  untested.

```bash
uv sync --only-group dev

```

passes, so nothing is presented as verified when it is not.
