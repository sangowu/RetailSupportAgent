固定 13 个文件的摘要，记录在 `evaluation/tau2_manifest.json`：政策、DB、任务、划分、

**换行转换坑（首次 CI 已暴露并修复）**：Windows 的 `core.autocrlf=true` 会把上游文件
改写成 CRLF，导致同一 commit 在 Windows 与 Linux 上算出**两组不同的 SHA256**——
本地全绿而 CI 上 13 个文件全部不匹配。现已让 `fetch_tau2.py` 以
`core.autocrlf=false` / `core.eol=lf` 检出，摘要一律针对上游提交时的原始字节；
`tests/test_upstream_checkout.py` 增加断言防止该配置被改回。

**归属声明**：数据、工具、政策与评分器均为上游原创，本项目只调用，不得在报告或演示中
宣称为自研实现。

## 2. Retail 域事实核验

均为本次从固定检出中实测得出，非文档推测。

### 2.1 工具清单（16 个）

| 类型 | 工具 |
|---|---|
| READ (7) | `find_user_id_by_name_zip`、`find_user_id_by_email`、`get_user_details`、`get_order_details`、`get_product_details`、`get_item_details`、`list_all_product_types` |
| WRITE (7) | `cancel_pending_order`、`return_delivered_order_items`、`exchange_delivered_order_items`、`modify_pending_order_items`、`modify_pending_order_address`、`modify_pending_order_payment`、`modify_user_address` |
| GENERIC (2) | `calculate`、`transfer_to_human_agents` |

分类取自上游 `@is_tool` 装饰器，合计 16。

政策 `policy.md` 章节：Domain basic / Generic action rules / Cancel pending order /
Modify pending order（含 payment、items）/ Return delivered order / Exchange delivered order。

`get_environment(solo_mode=True)` 在 retail 域会直接抛错——**retail 不支持 solo 模式**，
评测必须带模拟用户运行，这决定了每次运行都有模拟用户模型的成本。

### 2.2 任务与划分

| 项 | 值 |
|---|---|
| 任务总数 | 114 |
| 上游 `train` | 74 |
| 上游 `test` | 40 |
| `base` | 114（= train + test，互斥且完整覆盖，已断言） |

### 2.3 评分语义

- 最终奖励 = 各生效分量奖励**相乘**，分量由每题 `reward_basis` 决定。
- retail 分布：112 题为 `DB + NL_ASSERTION`，2 题为纯 `DB`。
- `DB` 分量比对最终数据库状态（`evaluator_env.py`）——这正好对应项目"以最终业务状态判定成功"的要求。
- `NL_ASSERTION` 分量由 **LLM 评判**（`evaluator_nl_assertions.py`）。
- `communicate` 与 `action` 分量**不在** retail 的 reward_basis 内，只能作诊断，不能拿来充当成绩。

**成本影响（需在 M0.2 预算里计入）**：每题至少涉及三个模型角色——被测 Agent、模拟用户、
NL 评判。后两者必须冻结，不得随候选 Agent 模型一起切换，否则跨模型比较不成立。

## 3. 关键发现：业务范围与基准任务不匹配

按写操作工具给 114 题打标签，结果如下（`evaluation/task_sets/scope_labels.json`）：

| 标签 | 含义 | 数量 |
|---|---|---|
| `read_only` | 评分动作不含写操作 | 8 |
| `in_scope_write` | 只涉及取消 / 退货 | 34 |
| `out_of_scope_write` | 涉及换货 / 改单 / 改地址 / 改支付 | **70** |
| `no_action` | 上游未给评分动作 | 2 |

**项目声明的三类业务（查询 / 取消 / 退货）只覆盖 114 题中的 42 题（36.8%）。**
`docs/DEVELOPMENT_PLAN.md` M0.1 要求"检查所选版本是否具有需要的三类任务"——三类任务确实存在，
但它们不是全集，占比不到四成。

### 处理方式（已落地，不阻塞后续步骤）

好在这个缺口的**实现成本几乎为零**：工具由上游 `RetailTools` 提供，我们不重写业务工具，
只是决定把哪些工具暴露给 Agent。因此：

1. **评测按上游全集跑**，Agent 暴露全部 16 个工具。只有这样"τ²-bench Retail 成绩"才是可对外引用的标准成绩。
2. **产品叙事仍聚焦三类业务**：Gradio 演示流程、自建权限与确认规则围绕查询 / 取消 / 退货设计。
3. **结果按 `scope_label` 分层报告**：总成绩 + 范围内 42 题子集成绩分别给出，两者都不冒充对方。

这个标签只影响报告切片，**不修改上游任务、政策或评分**。

> 需要你确认的一点：如果你更希望把评测范围收窄到 42 题子集（好处是聚焦，代价是**不能再声称跑的是标准
> τ²-bench Retail**，且 holdout 只剩 13 题、统计效力很弱），现在说，我改冻结口径。默认按上面第 1 条执行。

## 4. 冻结的任务集划分

| 文件 | 用途 | 数量 |
|---|---|---|
| `evaluation/task_sets/dev.json` | 开发集（= 上游 train）。**唯一**可用于筛选、调参、提示词迭代 | 74 |
| `evaluation/task_sets/holdout.json` | 保留验证集（= 上游 test）。只用于入围配置独立验证，禁止调参 | 40 |
| `evaluation/task_sets/regression.json` | 回归集，暴露过的失败题在此登记并版本化 | 0（`v0`，尚未跑过评测，为空是事实不是遗漏） |
| `evaluation/task_sets/scope_labels.json` | 业务范围标签，仅用于分层报告 | 114 |

直接采用上游官方划分，而非自行随机切分——避免"自定义划分"成为成绩不可比的隐患。
`tests/test_task_sets.py` 断言 dev 与 holdout 互斥、数量与 manifest 一致、标签覆盖全部任务。

## 5. 原始结果与运行 manifest 规范

- `evaluation/schemas/run_manifest.schema.json` —— 一次运行的完整可复现描述。
  强制记录：代码 commit 与工作区是否 dirty、上游 commit 及校验是否通过、任务集与试跑次数、
  **请求的精确模型 ID 与服务端返回的模型 ID**、逐参数的接受/拒绝/忽略/映射状态、
  提示词摘要、模拟用户与 NL 评判模型配置、执行上限与交错运行批次、价格快照、Langfuse trace。
- `evaluation/schemas/task_result.schema.json` —— 逐题原始结果。
  `outcome` 强制区分 `task_failure` / `service_error` / `unsupported_param` / `timeout` /
  `truncated` / `max_steps_exceeded`，避免把服务错误混进业务失败率；用量区分思考与缓存 token。

设计上直接对应 `AGENTS.md` 的两条纪律：*"不能把 HTTP 200 当作预算限制生效的证明"*、
*"不支持、服务错误、统计证据不足分别记录"*。

## 6. CI 与门禁状态

`.github/workflows/ci.yml` 三个作业：

| 作业 | 内容 | 状态 |
|---|---|---|
| `static-and-unit` | `ruff format --check`、`ruff check`、`mypy --strict`、`pytest -m "not live_model"` | GitHub 上已通过 |
| `upstream-pin` | 按固定 commit 拉取 τ²-bench 并逐文件校验 SHA256 | 首跑失败（换行转换），修复后通过 |
| `evaluation-gate` | **N/A** | MVP 基线尚未冻结，无可比对象 |

`evaluation-gate` 只输出一条 notice 说明不适用，**不产生任何数值**。真实评测门禁在 M0.5
冻结 `baseline-v1` 后启用，规范见 `EVALUATION_AND_GATES.md`。

`live_model` pytest marker 已注册：需要真实计费的用例默认不进 CI。

本地验证结果（2026-09-06）：`ruff` 全部通过、`mypy` 9 个源文件无问题、`pytest` 16 passed。

首次 CI 运行即抓出本地测不出的跨平台缺陷（见第 1 节换行转换），这正是 `upstream-pin`
作业存在的意义——摘要固定若只在一种平台成立，等于没有固定。
