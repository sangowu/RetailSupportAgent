# M6.8: changing the version without rebuilding the machine

## 0. Why this step exists

M6's acceptance line includes rollback between image versions. There is no rollback.

`image_tag` is rendered into the instance's user data, and user data runs once per
instance, so `user_data_replace_on_change = true` is the only thing that can make a change
to it take effect. Terraform's answer to a new tag is therefore to destroy the instance and
create another one. M6.7 went through exactly that: the database was discarded, the
certificate was reissued, and the first boot took 135 seconds against the 74 a restart
takes.

That is not a rollback. It is a rebuild that happens to end up on an older image, and it
costs everything the machine was holding.

The same defect has a second face, and it is the one that will bite hardest. **Any change
to the rendered user data replaces the instance**, so editing the Caddyfile, adding an
account, or changing a compose setting all discard the database. Three milestones have now
been shipped by destroying and rebuilding, and each time that was fine only because the
database held nothing anybody wanted.

The rule this step establishes: **user data holds what is true for the life of the machine.
Anything that changes more often than the machine does has to live somewhere the machine
can read again.**

## 1. Change card

- **Stage and step**: M6.8
- **Type**: fix
- **The specific problem**: changing the image version rebuilds the instance and discards
  its database and its certificate, so rollback does not exist
- **The single theme of this change**: a version is one thing, and changing it is a
  restart rather than a rebuild
- **Control variables this change does not touch**: the model, the simulated user, the
  judge, the task sets, the upstream commit, the price snapshot, the agent, the guard, the
  authorization model from M6.7, the name and certificate from M6.6, the idle verdict from
  M6.3, and every baseline
- **Explicitly out of scope**:
  - **Archiving before a teardown.** M6.9. This step reduces how often the database is
    discarded; it does not preserve it across a `destroy`.
  - **The systemd units, the idle watcher and `rsa-start` itself.** They stay in user data.
    They are the machine's own scaffolding, they change rarely, and when they do change a
    new machine is the honest answer. Section 1.4 says what that still costs.
  - **Streaming.** M7.
- **Expected benefit**: a rollback that takes a restart instead of a rebuild, and keeps the
  database and the certificate
- **Possible cost**: two more Parameter Store reads at boot, and one more thing that can be
  out of step with Terraform, since the parameter is now the source of truth for what runs

### 1.1 What moves out of user data, and where to

| Value | Changes when | Today | After |
|---|---|---|---|
| Image tag | any release or rollback | user data | `/rsa/demo/image` |
| Identity mapping | an account or role is added | user data | `/rsa/demo/identities` |
| Region, registry, zone, domain, ACME address, pool and client ids | almost never | user data | user data |
| The systemd units, the idle watcher, `update-dns`, `rsa-start` | a repository change to the machine's scaffolding | user data | user data |

Parameter Store rather than instance tags: the mapping is already over the 256 characters a
tag holds, and it grows with each account. Standard parameters, not SecureString - neither
value is a credential, and a subject that could be read by anyone still authenticates
nobody.

The instance role gains read on those two names. Named, not a prefix wildcard: the same
reasoning that kept `read_model_key` to one parameter.

### 1.2 What travels with the image instead

Moving the tag out is not enough on its own, and M6.7 shows why. Rolling back to `m6.6`
today would leave the machine running M6.7's compose file, which declares a `seed` service
that M6.6's image has no entrypoint for. The stack would fail on a service that did not
exist in the version being rolled back to.

So **the stack definition ships inside the image**: the compose file and the Caddyfile are
copied into it at build time, and `rsa-start` extracts them from the image it is about to
run. A version then brings its own description of how to run it, and rolling back moves
both together.

This has a consequence to state rather than discover: **no image published before this step
can be rolled back to**, because none of them carries a stack definition. Rollback is
available from this version onward, and the report will not pretend otherwise.

### 1.3 What a rollback becomes

```
terraform apply -var="image_tag=<older>"     # writes one parameter, replaces nothing
uv run python scripts/demo.py restart        # re-reads it, pulls, restarts the stack
```

`rsa.service` is a `oneshot` unit whose `ExecStart` is `rsa-start`, so restarting it stops
the stack, re-reads the parameter and brings the old version up. The machine does not
reboot, the volume is untouched, and the certificate is in a volume that was never involved.

`/health` gains the image it is running, so which version is answering is a question with an
answer rather than an assumption. `demo.py status` reports the configured version and the
running one, which are different exactly while a restart is in flight or has failed.

### 1.4 What still replaces the instance, and what that still costs

Changing the systemd units, the idle watcher, `update-dns` or `rsa-start` still renders
different user data and still replaces the machine, taking the database with it.

That is accepted here for two reasons. Those files are the machine, not the application, so
a new machine is a defensible answer to changing them. And the frequency is different: they
changed in M6.3, M6.4 and M6.6, and not at all in M6.7 except to pass two new values
through - which is precisely the kind of change this step removes.

What makes the remaining cost bounded is archiving, which is M6.9. Until then, a change to
those files still loses whatever the demo was holding, and this document says so rather
than leaving it to be found.

### 1.5 Primary metric, protective metrics, acceptance thresholds

Fixed before running, per `MODEL_EXPERIMENTS.md`.

| Metric | Threshold | If not met |
|---|---|---|
| A version change replaces nothing | `terraform plan` for a different `image_tag` shows 0 to destroy and 0 to replace | FAIL |
| An account change replaces nothing | the same, for a changed `demo_accounts` | FAIL |
| The rollback runs the older version | `/health` reports the older image, and the difference between the two versions is visible | FAIL |
| The database survives | a row written before the rollback is readable after it, and after rolling forward again | FAIL |
| The certificate survives | the same serial before, after the rollback and after rolling forward | FAIL |
| Rolling forward again | returns to the newer version by the same two commands | FAIL |
| Rollback time | under 120 s, which is M6.1's restart rule | Investigate |
| A version brings its own stack definition | the compose file and Caddyfile on the instance are the rolled-back image's, not the repository's | FAIL |
| Nothing else became readable | the instance role reads exactly three named parameters | FAIL |
| Idle cost | unchanged: standard parameters are not billed | FAIL |
| Degradation | the local stack and the whole suite are unaffected | FAIL |
| Evaluation score | Not applicable. Section 3 confirms by import graph, as M6.7 did, rather than assuming | - |

### 1.6 How rollback is measured, given 1.2

A rollback needs two versions that both carry a stack definition, and before this step none
did. So the measurement uses a purpose-built pair: `m6.8` and a second image from the same
tree with one difference visible in `/health`. That the pair is built for the measurement is
stated here rather than presented as a release history.

The one honest thing this cannot show is a rollback across a real behavioural change. What
it shows is that the mechanism moves versions in both directions without touching the
machine, which is the claim being made.

### 1.7 Baseline and evaluation protocol

- Baseline: `baseline-v3` (this project's guarded agent) on the full 114-task split, protocol `evaluation/protocol.md` at
  the pinned upstream commit `fc0055dc4e0a316c3f83133267fbd6faaa770992`.
- No re-run. This step changes how the instance learns which image to run and adds one
  field to `/health`. Section 3 lists the changed files against the benchmark's import
  graph.

### 2.1 Decisions made during the work

**Parameter Store, not instance tags.** A tag holds 256 characters and the identity mapping
is already past that with three accounts. Standard parameters, not SecureString: an image
reference is not a credential, and a subject that anyone could read still authenticates
nobody.

**The stack definition travels inside the image.** Moving the tag alone would have produced
a rollback that runs an old image under the newest compose file. That is not hypothetical:
M6.7's compose declares a `seed` service, and M6.6's image has no entrypoint for it, so a
rollback across that boundary would have failed on a service the older version has never
heard of. `rsa-start` extracts both files from the image it is about to run, into a
temporary directory, and moves them into place only once both are there.

**`restart` waits twice.** First for the Systems Manager command to finish, then for
`/health` to report the version that was asked for. The first alone is not enough because
the old containers keep answering until they are down; the second alone is not enough
because a version can be configured and never picked up.

**The image reference is the version's identity.** `/health` reports it, so "which version
is running" has an answer rather than an inference from what was last applied.

### 2.2 Two defects found by doing this

**The Caddy health check had been failing on every boot since M6.6.**

`wget --spider http://127.0.0.1:80/` gets Caddy's redirect to HTTPS, follows it, and opens
a TLS connection to an IP address. There is no certificate for an IP address and there
never will be, so the handshake fails, the container never reports healthy,
`docker compose up --wait` gives up after 150 seconds, and `rsa.service` reports a failure.

Meanwhile the demo answers perfectly, because everything except the health check works.
This survived M6.6 and M6.7 because nothing read the unit's result: both milestones
measured a start by polling the URL. `demo.py restart` is the first thing in this project
that asks systemd whether the unit succeeded, and it got "failed" on a stack that was
serving requests.

Measured on the instance before the fix:

```
systemctl is-active rsa.service   ->  failed
journalctl -u rsa.service         ->  container rsa-caddy-1 is unhealthy
                                      Failed to start rsa.service
curl https://rsa.proshot.top/health  ->  200
```

The health check now asks Caddy's admin API, which answers the question a container health
check should answer - is this process alive and configured - and leaves "does the proxy
serve the site" to `scripts/demo.py`, which asks from outside where that question can be
answered honestly.

One consequence is worth naming and was not measured: a unit in `failed` is not `active`,
so `ExecStop` was not reliably running on a stop, and `docker compose down` may not have
been what brought PostgreSQL down. What did was Docker's own shutdown, which sends SIGTERM.
No corruption was observed across the several stop and start cycles in M6.6 and M6.7, and
this step does not investigate further because the unit now succeeds.

**Nothing pinned the `/health` image field.** It was added, then silently lost when a file
was reverted during the work, and the only symptom was `demo.py status` printing "not
reported". Two tests now pin it: the field is present with a value, and it reads "unknown"
rather than disappearing when there is no image. A field that only a deployed instance
exercises needs a test more than most, not less.

## 3. Comparison

### 3.1 The thresholds from section 1.5, measured

The pair: `m6.8.1` and `m6.8.1-probe`, built from the same tree with two deliberate
differences - `/health` reports a different milestone, and the compose file inside the
image carries a marker line. Purpose-built for this measurement, as section 1.6 said they
would be.

**A version change replaces nothing.** Both directions, from `terraform plan`:

| Change | Plan |
|---|---|
| `image_tag` to `m6.8.1-probe` | 0 to add, 1 to change, 0 to destroy |
| `image_tag` back to `m6.8.1` | 0 to add, 1 to change, 0 to destroy |

The one change is the parameter. Compare with what this step's own apply had to do, which
is the last time it will be necessary: 2 to add, 0 to change, 1 to destroy, because the
user data itself changed.

**The rollback runs the older version**, and the difference is visible:

| | Before | After rolling | After rolling back |
|---|---|---|---|
| `/health` image | `...:m6.8.1` | `...:m6.8.1-probe` | `...:m6.8.1` |
| `/health` milestone | `M4` | `M4-probe` | `M4` |
| First line of the compose file on the instance | the repository's | the probe's marker | the repository's |

The third row is the one that matters most: the stack definition on the machine changed
with the version and changed back, without Terraform touching the machine.

**Nothing was lost**, checked across both moves:

| | Before | After rolling | After rolling back |
|---|---|---|---|
| Certificate serial | `0683FA...F338` | unchanged | unchanged |
| A row written before the first move | present | present | present |
| `systemctl is-active rsa.service` | active | active | active |

**Time**, against M6.1's 120 second rule:

| Move | Seconds |
|---|---|
| To the probe version | 87 |
| Back | 82 |

Both include pulling an image the machine had not seen. A restart onto an image already on
disk is faster and was not measured separately, because the slow case is the one the rule
is about.

**Nothing else became readable.** The instance role now reads three named parameters: the
model key, the image and the identities. No prefix wildcard.

**Idle cost is unchanged.** Standard parameters are not billed, and no resource was added

**Degradation**: the local stack is unaffected, and `/health` reports `unknown` where no
image is set.

## 4. Failure analysis and conclusion

### 4.1 What this changes about how the project is operated

Before this step, three of the last four milestones ended by destroying the instance,
because each changed something rendered into user data. That was affordable only because
the database held nothing anyone wanted. From here, a version change and an account change
both keep the machine.

What still replaces it: the systemd units, the idle watcher, `update-dns` and `rsa-start`.
Those are the machine rather than the application, and section 1.4 accepted that. The
remaining exposure is bounded by archiving, which is M6.9 and is now the next thing worth
doing.

### 4.2 Limits of these results

- **The measured pair was built for the measurement.** It shows the mechanism moves
  versions in both directions without touching the machine. It does not show a rollback
  across a real behavioural change, because the two versions differ in a milestone string
  and a comment.
- **No image published before this step is a rollback target.** `m6.6` and `m6.7` carry no
  stack definition, so `rsa-start` cannot extract one from them. The registry currently
  holds exactly one image that can be rolled back to, which is the one running.
- **The plan does not show which version it is moving to.** The provider marks
  `aws_ssm_parameter.value` sensitive, so a review of the plan sees `(sensitive value)`.
  `demo.py status` prints both the configured and the running version, which is where an
  operator should look; a plan alone is not enough to review a rollback.
- **`ExecStop` under the old broken unit was not investigated.** Section 2.2 says what is
  known and what is not.

### 4.3 Conclusion

**PASS.** Every threshold in section 1.5 was met. A version change is one parameter and a
restart; the volume, the database and the certificate are not involved; and the version
that answers can be read from the thing that is answering.

Accepted also because the work found a defect that had been present since M6.6 and that
nothing else in the project was positioned to notice.

### 4.4 What this leaves for later

- **Archiving before a teardown**: M6.9, and the last M6 item.
- **Streaming**: M7.
- **A second rollback target.** The next real release gives the registry two versions that
  can be rolled between, and that is the point at which a rollback across a behavioural
  change can be measured rather than described.

### 4.5 Recorded after the fact: the rollback across a behavioural change

Written on 2026-09-10, the day the M7 release put a second version in the registry. Kept
here because section 4.2 is where the gap was admitted.

`m6.8.1` and `m7.3` differ in streaming, in the turn states and in the case sections: a
release, not a pair built for a test. The round trip was `m7.3` to `m6.8.1` and back, each
leg one targeted apply and one `demo.py restart`.

**Each apply planned `0 to add, 1 to change, 0 to destroy`**, and the parameter's version
went 7, 8. In between, `demo.py status` reported the state section 3 said was worth being
told about:

```
running:    ...rsa-app:m7.3
configured: ...rsa-app:m6.8.1
the configured version is not the one running; `restart` picks it up
```

**The version change is visible from outside, with no token.** The page Caddy serves is
the whole of what the internet can see, and it changes:

| | `m7.3` | `m6.8.1` | `m7.3` again |
|---|---|---|---|
| Page bytes | 214174 | 100050 | 214175 |
| `Cases`, `Work this case`, `Assign`, `Approvals` | 1 each | **0 each** | 1 each |
| `/health` image | `m7.3` | `m6.8.1` | `m7.3` |
| Restart to reach it | - | 98s | 85s |

The rolled-back page is under half the size and none of the four section labels is in it.
That is the difference section 4.2 said the measured pair could not show.

**The machine is not involved.** Read at all three points, unchanged at all three:

| | Value |
|---|---|
| Instance | `i-0e4b76e870a950271` |
| Volume | `vol-00f006880939fde79` |
| Launched | 2026-09-10T14:32:33Z |
| Public address | 34.244.174.24 |
| Certificate serial | `069B7F4A...9562`, issued 09:05:58Z |

The launch time is the load-bearing row: an instance that had been stopped and started
would have a new one, and a new address with it.

**The database is the same database.** An archive was taken at each of the three points
and the rows counted per table without reading them: 9 rows, identical every time,
including the four `identities` rows - one of them `mia`, who exists only because of the
release being rolled away from and back to.

**A restart is a new owner.** `/health` reported `p-2c28800fb751`, then `p-ee629633a910`,
then `p-a32808b77e2e`. M2's session claim moving to the process that now holds the
sessions, seen in passing.

### 4.6 Limits of the round trip

- **No business data was written under the new version.** `sessions` and `messages` were
  empty throughout, so what is shown is that the database survived, not that rows written
  by `m7.3` were readable by `m6.8.1` and again by `m7.3`. Producing that needs a signed-in
  conversation before the rollback, and this run did not have one.
- **The two versions share a schema.** No migration has been added since M4, so the round
  trip carries no question about downgrading one. **A version pair that did not share a
  schema is the harder case and is still not measured**, and it is the one where a
  rollback can genuinely fail.
- **The page was compared as served, not as rendered.** The counts are of the Gradio
  configuration in the HTML. A person looking at the rolled-back page was not part of this.
- **The two `m7.3` pages differ by one byte.** Not investigated. Something in the served
  configuration is not constant across a restart, which is expected of an identifier and
  would be worth knowing if it were anything else.
