# M0.5 part two: local start/stop and the three demo flows

The second theme of M0.5: turn "start locally, stop locally, and reproduce the three demo
flows" into three real commands. The first theme, cost accounting and observability, is in
[M0.5 part one](M0.5_OBSERVABILITY.md).

Result first: the three scripts are implemented and verified by running them.
**Three real bugs were caught along the way, two of which would either break the demo on
the spot or silently underreport.** They were caught because this time the work was not
only writing scripts but actually starting, calling and stopping the services.

| Script | Behaviour |
|---|---|
| `scripts/start-local.ps1` | Check prerequisites, start the API and the UI, wait for health, print the URLs |
| `scripts/stop-local.ps1` | Stop only processes this project registered; touch no data on disk |
| `scripts/reset-demo.ps1` | Reset demo sessions; delete no baseline, no evaluation result, no file |

```powershell
pwsh scripts/start-local.ps1          # API on :8000, demo UI on :7860
uv run python scripts/demo_flows.py   # all four flows in one go (this is billed)
pwsh scripts/reset-demo.ps1
pwsh scripts/stop-local.ps1
```

---

## 1. Stop only the processes we started

This is the one genuinely hard thing to get right among the three scripts.

Windows reuses PIDs. The 4321 recorded at startup may belong to someone else's process by
the time the service is stopped. Stopping by PID alone kills the wrong process, and fuzzy
matching on names such as `python` or `uvicorn` is worse: **a tau2-bench evaluation runs
for tens of minutes and is exactly the thing most likely to be killed by mistake.**

So each service registers not only its PID but also its **process start time**
(`.local/run/<name>.json`), and both must match before anything is stopped. On a mismatch
the stop is refused, the registry file is kept, and the exit code is 1 so a human
investigates.

Measured (the registered start time was moved an hour earlier to simulate PID reuse):

```
Refusing to stop api: PID 59720 now reports start time 2026-09-07T20:03:43.7284410+01:00,
                      the registry says 2026-09-07T19:03:43.0000000 - this PID belongs to
                      another process
```

The service stayed alive and was not killed. With the registry corrected, the stop worked
normally.

## 2. The three bugs that were caught

This section is the main value of this part. None of the three was thought up while writing
the scripts; all three appeared once the scripts actually ran.

### 2.1 The demo UI would not start at all

On the first `start-local.ps1`, the UI process crashed immediately:

```
TypeError: Chatbot.__init__() got an unexpected keyword argument 'type'
```

`gr.Chatbot(type="messages")` was written for gradio 5, while the lockfile installs
**gradio 6.26.0**, where that argument is gone (messages is now the only format). The UI had
therefore been broken in the repository for some time, and **no test touched the UI**, so
the M0.3 report's claim that "the UI runs the three flows" stopped holding after a
dependency upgrade without anyone noticing.

Fix: drop the `type` argument (the message format we produce is already v6's) and tighten
`gradio>=5.5` to `gradio>=6.0` in `pyproject.toml`, since anyone installing 5.x according to
our own declaration gets a UI that will not start. A new `tests/test_ui.py` constructs the
UI once: offline, free and fast, so the next incompatibility of this kind turns red
immediately.

### 2.2 Read queries always reported "no tool was called"

On the first real message through the API, the agent correctly listed 4 orders, but
`tool_calls` in the response was **empty**: it had clearly queried the database while
claiming it called no tool.

The cause is the structure of one turn: `think (call a tool) -> act (execute) -> think
(answer)`. The final think has no tool call, and the code built a fresh empty list there,
discarding everything the preceding act had executed. **Write operations happened to be
unaffected** (their turn ends inside act), so the most visible cancel and return flows
looked fine and only read queries underreported.

This is not a cosmetic display issue: this project's selling point is proving what it did,
and both the UI and the API present "tools called" on that basis. Checking the historical
archives confirmed the extent: **every demo archive since M0.3 records `tools=[]` for the
query flow**:

```
20260906T131912Z  query tools=[]
20260906T132119Z  query tools=[]
...
20260907T190959Z  query tools=['get_user_details', 'get_order_details' x4]   <- after the fix
```

Fix: accumulate "tools executed this turn" across the turn (`_turn_tools`), cleared on each
`send()`, and have every `TurnResult` report the accumulated value.

Why the existing tests missed it: the read-path tests asserted `domain.executed` (the domain
really did execute), and **nobody asserted what we report outwards**. Four new tests cover
that angle, including "turn two must not inherit turn one's tools".

### 2.3 Stopping did not kill the real service

The services were first started through `uv run`. `uv run` starts a uv process first, and
the real service is its child; the PID we registered was the wrapper. Killing it on stop
does **not** kill the child: the port stays occupied and the service stays alive, while the
registry file is already deleted, so nothing can manage it any more. The first real run left
exactly such an orphan.

Fix: start `.venv/Scripts/python.exe` directly, so the registered PID is the service itself
and the identity check in section 1 means something.

## 3. Preflight checks

A failure has to be stated before startup, not once the UI is open and the first message
explodes, when the diagnosis points in entirely the wrong direction.

| Check | Message when it fails |
|---|---|
| `uv` on PATH | Give the install URL |
| `.venv` exists | `uv sync --group bench` |
| `.env` exists and `DASHSCOPE_API_KEY` is non-empty | Point at `.env.example` |
| tau2-bench data fetched | `uv run python scripts/fetch_tau2.py` |
| `import tau2` succeeds | `uv sync --group bench` |
| Ports free | Run `stop-local.ps1` first, or change the port |

The key check **only decides whether that line has a non-empty value**, and never prints the
value or writes it to a log.

If startup fails, whatever this run already started is stopped before exiting: half a stack
is worse than nothing, because the UI opens and then errors on the first message.

## 4. Scope of a reset

All of M0's demo data lives in memory, each session holding its own copy of the tau2-bench
database, so "reset" means dropping sessions and the next message gets a fresh initial
dataset.

`reset-demo.ps1` **deletes no file**. Evaluation results, demo archives, baselines and
`.env` are untouched, and it offers no way to delete files, so one mistaken invocation
cannot destroy an experiment that cannot be reproduced.

When no service is running it says plainly that there is no registered instance rather than
pretending the reset succeeded. The API gained `POST /sessions/reset`, returning the number
of sessions cleared: both 0 and 3 are success, but they mean different things to the
operator. `/health` also carries `active_sessions`, which is used before stopping to warn
that shutting down now interrupts a demo in progress.

## 5. Measured results of the three demo flows

`uv run python scripts/demo_flows.py`, model deepseek-v4-pro, archived at
`evaluation/demo_runs/20260907T190959Z/flows.json`:

| Flow | Per-turn state | Tools executed | Database |
|---|---|---|---|
| query | answered x2 | get_user_details, get_order_details x4 | unchanged |
| cancel | answered -> **needs_confirmation** -> answered | get_order_details, cancel_pending_order | **changed** |
| return | answered -> **needs_confirmation** -> answered x2 | get_order_details, return_delivered_order_items | **changed** |
| ownership_denied | answered x2 | get_order_details | unchanged |

Two pieces of key evidence: every write was **held for confirmation before it ran**, and the
out-of-scope request produced **no write at all** even after the user added "confirm the
cancellation", with the database fingerprint unchanged. The fingerprint is required: the
model saying "cancelled" does not count.

## 6. Explicitly not done

- PowerShell scripts only. The target machine is Windows and the contract in
  `docs/OPERATIONS.md` is written for `.ps1`; there is no Linux or macOS version and none is
  claimed.
- No containers: M0 needs neither PostgreSQL nor Docker, and two local processes are enough.
- The scripts have no automated tests. They start processes, occupy ports and kill
  processes, which is not worth putting in CI; the cost is a manual run after every change.
  **All three verifications here were manual runs**: a normal start and stop, the PID-reuse
  guard refusing, and the session count before and after a reset.
- The service still uses a fixed simulated identity, binds to `127.0.0.1` only, and has no
  authentication or registration. **It must never be exposed to the public internet.**
