# M0.5（二）本地一键启停与三类演示流程

M0.5 的第二个主题：把「本地一键启动、停止和三类演示流程可复现」变成三条真命令。
第一个主题（成本记账与可观测接入）见 [M0.5（一）](M0.5_OBSERVABILITY.md)。

结论先说：三个脚本已实现并实跑验证；**过程中抓出三个真 bug，其中两个会让演示
当场翻车或悄悄少报**。它们能被抓出来，正是因为这次不再只写脚本，而是真的去启动、
去调用、去停止。

| 脚本 | 行为 |
|---|---|
| `scripts/start-local.ps1` | 检查前提，起 API + 界面，等健康，打印网址 |
| `scripts/stop-local.ps1` | 只停本项目登记过的进程，不动任何磁盘数据 |
| `scripts/reset-demo.ps1` | 重置演示会话，不删基线、评测结果或任何文件 |

```powershell
pwsh scripts/start-local.ps1          # 业务接口 :8000，演示界面 :7860
uv run python scripts/demo_flows.py   # 四类流程一次跑完（会计费）
pwsh scripts/reset-demo.ps1
pwsh scripts/stop-local.ps1
```

---

## 1. 只停自己启的进程

这是三个脚本里唯一真正难做对的地方。

Windows 会复用 PID。启动时记下的 4321，等到停服时可能已经是别人的进程了。
只按 PID 停会误杀；按 `python`、`uvicorn` 之类的名字模糊匹配去停更糟——
**一轮 τ²-bench 评测要跑几十分钟，正是最容易被误杀的东西**。

所以每个服务登记的不只是 PID，还有**进程启动时刻**（`.local/run/<名字>.json`），
停之前两者都要对上；对不上就拒绝停、保留登记文件、退出码 1，让人自己查。

实测（把登记里的启动时刻改早一小时，模拟 PID 被复用）：

```
拒绝停止 api：PID 59720 现在的启动时刻是 2026-09-07T20:03:43.7284410+01:00，
              登记的是 2026-09-07T19:03:43.0000000——这个 PID 已被别的进程占用
```

服务仍然活着，没有被误杀。改回正确的登记后再跑，正常停止。

## 2. 抓出来的三个 bug

这一节是本篇的主要价值。三个都不是写脚本时想出来的，是脚本真的跑起来之后撞出来的。

### 2.1 演示界面根本起不来

`start-local.ps1` 第一次启动，界面进程当场崩：

```
TypeError: Chatbot.__init__() got an unexpected keyword argument 'type'
```

`gr.Chatbot(type="messages")` 是按 gradio 5 写的；锁文件里实际装的是 **gradio 6.26.0**，
该参数已被删除（messages 成了唯一格式）。也就是说界面在仓库里坏了一段时间，
而**没有任何测试碰过界面**，M0.3 报告里"界面能走通三类流程"这句话在依赖升级后
已经不成立，只是没人发现。

修法：去掉 `type` 参数（我们本来产出的就是 v6 的消息格式），并把
`pyproject.toml` 里的 `gradio>=5.5` 收紧成 `gradio>=6.0`——照着我们自己的声明
装 5.x 的人会拿到一个起不来的界面。新增 `tests/test_ui.py` 构造一次界面，
离线、免费、够快，以后再有同类不兼容会立刻变红。

### 2.2 读类查询永远报「未调用任何工具」

第一次通过接口发真实消息，Agent 正确列出了 4 笔订单，但响应里
`tool_calls` 是**空的**——它显然查了数据库，却说自己没调工具。

根因在一轮的执行结构：`think(要调工具) → act(执行) → think(给出答复)`。
最后那次 think 没有工具调用，原先在那里现造一个空列表，把前面 act
执行过的工具全丢了。**写操作碰巧不受影响**（它在 act 里就结束了本轮），
所以最显眼的取消/退货流程看起来一切正常，只有读类查询在少报。

这不是无关紧要的显示问题：本项目的卖点是"能证明它做了什么"，而界面和 API
都据此展示"已调用工具"。翻历史存档确认了影响范围——**M0.3 以来每一份演示存档
的 query 流程都记着 `工具=[]`**：

```
20260906T131912Z  query 工具=[]
20260906T132119Z  query 工具=[]
...
20260907T190959Z  query 工具=['get_user_details', 'get_order_details', ×4]   ← 修复后
```

修法：把"本轮执行过的工具"改成按轮累计（`_turn_tools`），每次 `send()` 清空，
所有 `TurnResult` 一律汇报累计值。

原有测试为什么没拦住：读路径测试只断言 `domain.executed`（领域侧确实执行了），
**没人断言"我们对外怎么说"**。新增 4 条测试补上这个角度，包括"第二轮不许继承
第一轮的工具"。

### 2.3 停服杀不掉真正的服务

最初用 `uv run` 起服务。`uv run` 会先起一个 uv 进程，真正的服务是它的子进程；
我们登记到的 PID 是那个包装进程。停服时杀掉它**并不会**杀掉子进程——
端口还占着、服务还活着，而登记文件已经删了，从此没人管得了它。
第一次实跑就留下了这样一个孤儿进程。

修法：直接用 `.venv/Scripts/python.exe` 启动，让"登记的 PID"就是"服务本身"，
第 1 节的身份核对才有意义。

## 3. 起飞前检查

失败要在启动前说清楚，而不是等界面开着、一发消息才炸——那时排查方向全错。

| 检查 | 不满足时的提示 |
|---|---|
| `uv` 在 PATH | 给安装地址 |
| `.venv` 存在 | `uv sync --group bench` |
| `.env` 存在且 `DASHSCOPE_API_KEY` 非空 | 指到 `.env.example` |
| τ²-bench 数据已拉取 | `uv run python scripts/fetch_tau2.py` |
| `import tau2` 成功 | `uv sync --group bench` |
| 端口空闲 | 先 `stop-local.ps1`，或换端口 |

密钥检查**只判断这一行有没有非空值**，绝不把值本身打印或写进日志。

起不来时会把本次已经起来的服务一并停掉再退出：留下半套服务比什么都没起更糟——
界面能开、一发消息就报错。

## 4. 重置的范围

M0 的演示数据全在内存里：每个会话各持一份 τ²-bench 数据库副本，
所以"重置"就是丢掉会话，下次发消息拿到一份全新的初始数据。

`reset-demo.ps1` **不删除任何文件**。评测结果、演示归档、基线、`.env` 都不碰；
它也不提供删文件的能力，免得一次误操作毁掉不可重现的实验。

服务没起时会明说"没有登记在案的实例"，而不是假装重置成功。
接口新增 `POST /sessions/reset`，返回被清掉的会话数——0 条和 3 条都是成功，
但对操作者是两件不同的事。`/health` 也带上 `active_sessions`，
停服前据此提示"现在关掉会打断正在进行的演示"。

## 5. 三类演示流程实跑结果

`uv run python scripts/demo_flows.py`，模型 deepseek-v4-pro，
存档 `evaluation/demo_runs/20260907T190959Z/flows.json`：

| 流程 | 逐轮状态 | 执行的工具 | 数据库 |
|---|---|---|---|
| query | answered ×2 | get_user_details, get_order_details ×4 | 未改变 |
| cancel | answered → **needs_confirmation** → answered | get_order_details, cancel_pending_order | **已改变** |
| return | answered → **needs_confirmation** → answered ×2 | get_order_details, return_delivered_order_items | **已改变** |
| ownership_denied | answered ×2 | get_order_details | 未改变 |

两条关键证据：写操作**都先被拦下来要确认**才执行；越权请求即使用户追加
"确认取消"也**始终没有发生写操作**，数据库指纹纹丝不动。
指纹是必须的——光看模型嘴上说"已取消"不算数。

## 6. 明确未做的事

- 只有 PowerShell 脚本。目标机器是 Windows，`docs/OPERATIONS.md` 的契约也是按
  `.ps1` 写的；没有 Linux/macOS 版本，也不假装有。
- 不涉及容器：M0 不需要 PostgreSQL/Docker，起两个本地进程就够。
- 脚本没有自动化测试。它们要真的起进程、占端口、杀进程，进 CI 得不偿失；
  代价是每次改动都要手工实跑一遍。**本次的三条验证都是手工实跑的**：
  正常启停、PID 复用守卫拒绝、重置前后会话数变化。
- 服务仍是固定模拟身份、仅绑定 `127.0.0.1`、无认证无注册。**绝不能暴露到公网。**
