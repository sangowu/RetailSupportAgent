# M0.5（一）成本记账与可观测接入

本篇只覆盖 M0.5 的一个主题：**让成本变成真数字，让面板上的 trace 能对回某一轮运行**。
M0.5 的另外两项——本地一键启停 + 三条演示流程、`baseline-v1` 冻结与校验和——另行交付。

结论先说：

| 事项 | 结论 |
|---|---|
| 上游 `agent_cost` | 从恒为 0 修成真值，与我们自己的记账**严格相等** |
| Langfuse trace / 延迟 / token | 已接入，可用 |
| Langfuse **成本** | **不用**。面板恒显示 0，成因在上游，且"修好"它会得到一个错 5 倍的数 |
| 成本的唯一权威口径 | `scripts/analyze_eval.py` |

---

## 1. 上游 `agent_cost` 为什么一直是 0

`tau2` 每跑完一次调用会问 litellm 要成本：

```python
cost = get_response_cost(response)  # llm_utils.py
```

litellm 按 `model` 字符串去自己的价格表里查。我们发出去的模型名带 `openai/` 前缀
（因为三个角色都走 OpenAI 兼容端点），于是 litellm 判定 `custom_llm_provider=openai`，
在 OpenAI 的价目里找 `deepseek-v4-pro`——找不到，抛异常，上游一路捕获后 `return 0.0`。

**这个 0 不会报错，也不写日志。** 它只是安静地出现在每一份 summary.json 里，
看起来像"本轮免费"。

早先文档里写过一句"litellm 不认识 DashScope 与 DeepSeek 的型号"，那是错的：
litellm 1.82.6 里**有** `deepseek/deepseek-v4-pro`（1.32 / 3.96 美元）。
真正的原因是前缀让它查错了表。

### 修法

`pricing.register_with_litellm()` 把我们自己的价格快照按**我们实际发出去的模型名**
（带 `openai/` 前缀）注册进 `litellm.model_cost`，在任何调用发生前执行。

注册进去的是**人民币每 token**，不是美元。litellm 不带币种概念，只有数字；
所以 `LITELLM_COST_CURRENCY = "CNY"` 会写进每一轮的 summary.json，
免得日后有人拿这个数字当美元汇报。

### 验证

同一轮 pilot 上，两套互不相干的记账对上了：

| 来源 | 数值（元） |
|---|---|
| 上游 litellm（`agent_cost_reported_by_upstream`） | 0.158577 |
| 我们自己按 usage 逐项算（`analyze_eval.py`） | 0.158577 |
| 若按全价、不算缓存 | 0.82 |

第三行是这次验证的关键：两边同为 0.1586 而不是 0.82，说明**缓存价（全价的 1/30）
确实传进了 litellm 的账**，不是碰巧凑对。

`analyze_eval.py` 现在会主动打印这条交叉校验，并对价格注册之前跑的旧轮次
明确说明"上游 litellm 记账为 0——那轮跑在价格注册之前，不是真的免费"。

## 2. Langfuse：回调名选错不会报错，只会静默不上报

上游 `tau2` 的接法是：

```python
litellm.success_callback = ["langfuse"]  # llm_utils.py
```

在 langfuse 4.15.1 + litellm 1.82.6 上实测：

| 回调名 | 结果 |
|---|---|
| `"langfuse"` | 初始化抛 `AttributeError`（去找 v2 SDK 的 `langfuse.version`），litellm 捕获后返回 `None` |
| `"langfuse_otel"` | 正常返回 `LangfuseOtelLogger` |

也就是说，**把 `tau2.config.USE_LANGFUSE` 翻成 `True` 是错的**：跑完一整轮，
面板上一条 trace 都没有，而运行本身完全正常，退出码 0，日志里没有任何迹象。

我们用 `langfuse_otel`，并把旧名字留成常量 `LANGFUSE_BROKEN_CALLBACK`，
让后来者能顺着它搜到这段说明。有一条测试盯着旧回调——它变绿的那天，
说明 litellm 修好了对 v4 SDK 的支持，届时可以重新评估用哪个。

配置要么三项齐全（`LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY` / `LANGFUSE_HOST`）
要么完全不启用：半套配置连不上，却要等到跑批中途才暴露。

## 3. 面板成本恒为 0——为什么不修

先说事实。2026-09-07 用真实运行 + Langfuse API 回查确认：

- 到达 Langfuse 的有 trace、延迟、模型名、输入/输出 token 数
- 没到达的是成本：observation 里 `costDetails: {}`、`modelId: null`

两条路都断了：

**路一，litellm 把算好的成本发过去。**
litellm 算对了（0.1586 元），但它发出的属性里**根本没有成本这一项**——
`langfuse.observation.cost_details.*` 这个字符串在整个
`litellm/integrations/langfuse/` 目录里都不存在。它只把成本写成 `gen_ai.cost.*`，
而 Langfuse 的摄取端不认这个键。这是 litellm 的功能缺失，不是我们配错了。

**路二，Langfuse 拿到用量自己算。**
它收到了用量，但不认识 `deepseek-v4-pro` 这些型号，没有单价。

### 那把价格表同步给 Langfuse 不就行了

不行，而且**这才是真正的坑**。Langfuse 收到的 `usageDetails` 只有笼统的
input / output 两个数，**没有缓存明细**。而被测侧约 95% 的输入 token 命中缓存，
缓存价是全价的 1/30：

```
Langfuse 会这么算：  5467 × 全价                → 0.82 元
实际应该这么算：      273 × 全价 + 5194 × 缓存价  → 0.16 元
```

差 5 倍。同步价格表的结果不是"面板显示成本"，而是**面板显示一个看起来完全正常
的错数字**——比一个扎眼的 0 危险得多，因为没人会去质疑它。

### 决定

**Langfuse 只用于 trace / 延迟 / token 观测；成本以 `scripts/analyze_eval.py` 为准。**

理由是让成本只有一个权威来源。`analyze_eval.py` 的成本分角色、区分缓存、
与 litellm 的独立记账交叉校验且严格相等；两个地方各显示一个数、其中一个还是错的，
不如只留一个。

这一点在三处留痕，任何一处都足以阻止误读：

- summary.json 里 `langfuse_cost_reported: false` 加原因
- `run_eval.py` 启动时打印"面板只有 trace/延迟/token，**成本恒为 0**（上游缺口，非免费）"
- 一条测试盯着 litellm 是否开始发 `cost_details`——它变红那天可以重新评估

> 与 [EVALUATION_AND_GATES.md](EVALUATION_AND_GATES.md) 的偏差：那里写过
> "Langfuse 成本配置使用实际价格"。这条要求成立的前提是 Langfuse 拿得到
> 分缓存的用量，实测拿不到。同一份文档更硬的那条要求——"未核验价格时不能把
> 缺失成本记为免费"——恰恰是**不同步价格表**才满足：同步了就等于让面板报一个
> 未经核验的数。

## 4. trace 与结果相互关联

面板上有 trace 却对不回是哪一轮跑的，观测和结果就是两张皮。

Langfuse 的分组维度是 **session**。litellm 的 `langfuse_otel` 只从
`litellm_params["metadata"]` 里读 `session_id` / `tags`
（见 `LangfuseOtelLogger._set_metadata_attributes`），而这只能**逐次调用**传入：
没有全局入口，唯一相关的环境变量 `LANGFUSE_TRACING_ENVIRONMENT` 是 dev/prod
那种环境名，不是会话号。上游 `tau2` 又不给传 metadata 的口子。

做法：在 `tau2.utils.llm_utils.completion` 上包一层。这是被测 Agent、模拟用户、
两个判官**共用的唯一出口**，一处覆盖全部；包这里而不是包 `litellm.completion`，
是为了不波及同进程里任何别的用途。

会话号直接取**运行目录名**（形如 `20260907T141354Z_deepseek-v4-pro_dev`）——
它已经是本项目里一轮运行的唯一标识，两边不用再维护一张对照表。补跑
（`resume_run.py`）用原轮的目录名，让补跑的 trace 落进同一条会话，
而不是在面板上多出一条只有几题的孤儿会话。

查法：面板 Tracing → Sessions 搜运行目录名；或 API
`GET /api/public/traces?sessionId=<运行目录名>`。会话号同时写进 summary.json 的
`observability.langfuse_session_id`。

`metadata` 是 litellm 自己的参数（在 `get_litellm_params` 的名单里），不会被转发
给模型服务端，也不受 `litellm.drop_params` 影响——有一条测试钉着这一点，
因为它一旦不成立，会话号会**静默消失**。

## 5. 不显式 flush 会静默丢 trace

2026-09-07 实测，三次真实调用 + API 回查：

| 场景 | 面板上有没有这条 trace |
|---|---|
| 调用后立刻退出 | **没有，且永远不会有**，退出码仍是 0 |
| 调用后等几秒再退出 | 有 |
| 调用后 `flush_langfuse()` | 有 |

OTEL 的 `TracerProvider` 本来会在进程退出时自己 shutdown，但 litellm 的
`langfuse_otel` **没有把 provider 设成全局的**——
`opentelemetry.trace.get_tracer_provider()` 拿到的仍是 `ProxyTracerProvider`，
连 `force_flush` 都没有，那条退出路径根本轮不到它。唯一的入口是 logger 实例
自己持有的 `tracer.span_processor`。

整轮评测跑得久，中途的 span 会被批量导出器按时发走，**丢的是末尾几题**——
恰好是"跑完了去面板看看"时最想看的那几条。

`flush_langfuse()` 先等 3 秒（litellm 的成功回调跑在另一个线程里，span 还没建
出来就 flush 等于什么也没推），再对 span processor 强制导出。推不出去只报告
`langfuse_flushed: false` 并打一条警告，**不抛错**——观测失败不该让一轮好结果作废。

它依赖上游私有名字 `_in_memory_loggers`，有测试钉着；改名那天会变红，
否则 flush 会静默退化成"什么都不推"，trace 又开始悄悄丢。
