# M0.5 part one: cost accounting and observability

This part covers one theme of M0.5: **make cost a real number, and make a trace on the
dashboard traceable back to a specific run**. The other two M0.5 items - local start/stop
plus the three demo flows, and the `baseline-v1` freeze with checksums - are delivered
separately.

Result first:

| Item | Result |
|---|---|
| Upstream `agent_cost` | Fixed from a constant 0 to a real value, **exactly equal** to our own accounting |
| Langfuse trace / latency / tokens | Wired up and usable |
| Langfuse **cost** | **Not used.** The dashboard shows a constant 0; the cause is upstream, and "fixing" it would produce a number 5x wrong |
| The single authority for cost | `scripts/analyze_eval.py` |

---

## 1. Why upstream `agent_cost` was always 0

After each call, `tau2` asks litellm for the cost:

```python
cost = get_response_cost(response)  # llm_utils.py
```

litellm looks the `model` string up in its own price table. The model name we send carries an
`openai/` prefix (all three roles use OpenAI-compatible endpoints), so litellm decides
`custom_llm_provider=openai` and looks for `deepseek-v4-pro` in OpenAI's price list. It is
not there, an exception is raised, and upstream catches it and returns 0.0.

**That 0 raises nothing and logs nothing.** It simply appears quietly in every summary.json,
looking like "this run was free".

An earlier document claimed litellm does not know DashScope's and DeepSeek's model names.
That was wrong: litellm 1.82.6 **does** carry `deepseek/deepseek-v4-pro` (1.32 / 3.96 USD).
The real cause is that the prefix sent it to the wrong table.

### Fix

`pricing.register_with_litellm()` registers our own price snapshot into `litellm.model_cost`
under **the model names we actually send** (with the `openai/` prefix), before any call
happens.

What is registered is **CNY per token**, not USD. litellm has no notion of currency, only
numbers, so `LITELLM_COST_CURRENCY = "CNY"` is written into every run's summary.json to stop
anyone later reporting the figure as dollars.

### Verification

On the same pilot run, two independent accounts agree:

| Source | Value (CNY) |
|---|---|
| Upstream litellm (`agent_cost_reported_by_upstream`) | 0.158577 |
| Our own per-item computation from usage (`analyze_eval.py`) | 0.158577 |
| At full price, ignoring cache | 0.82 |

The third row is what makes the check meaningful: both sides give 0.1586 rather than 0.82,
which shows **the cache price (1/30 of full) really did reach litellm's accounting** rather
than the two matching by coincidence.

`analyze_eval.py` now prints this cross-check, and for runs made before price registration it
states explicitly that "upstream litellm reported 0 - that run predates price registration
and was not actually free".

## 2. Langfuse: the wrong callback name raises nothing and silently reports nothing

Upstream `tau2` wires it as:

```python
litellm.success_callback = ["langfuse"]  # llm_utils.py
```

Measured on langfuse 4.15.1 + litellm 1.82.6:

| Callback name | Result |
|---|---|
| `"langfuse"` | Initialization raises `AttributeError` (it looks for the v2 SDK's `langfuse.version`); litellm catches it and returns `None` |
| `"langfuse_otel"` | Returns `LangfuseOtelLogger` normally |

In other words, **flipping `tau2.config.USE_LANGFUSE` to `True` is wrong**: a whole run
completes with not one trace on the dashboard, while the run itself is entirely normal, exits
0, and leaves no trace of the problem in the logs.

We use `langfuse_otel` and keep the old name as the constant `LANGFUSE_BROKEN_CALLBACK` so a
later reader can search their way to this explanation. A test watches the old callback: the
day it turns green, litellm has fixed v4 SDK support and the choice can be revisited.

Configuration is either complete (`LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY` /
`LANGFUSE_HOST`) or disabled entirely: half a configuration cannot connect and would only
surface midway through a batch.

## 3. Dashboard cost is always 0, and why it is not fixed

The facts first. Confirmed on 2026-09-07 with a real run and a Langfuse API read-back:

- What reaches Langfuse: traces, latency, model names, input/output token counts
- What does not: cost. Observations carry `costDetails: {}` and `modelId: null`

Both routes are broken:

**Route one, litellm sends the cost it computed.**
litellm computes it correctly (0.1586 CNY), but the attributes it emits **contain no cost at
all**: the string `langfuse.observation.cost_details.*` does not appear anywhere in
`litellm/integrations/langfuse/`. It only writes cost as `gen_ai.cost.*`, and Langfuse's
ingestion does not recognize that key. This is a missing feature in litellm, not a
misconfiguration on our side.

**Route two, Langfuse computes it from usage.**
It receives usage but does not know models such as `deepseek-v4-pro` and has no unit price.

### Then just sync the price table into Langfuse

That does not work, and **this is the real trap**. The `usageDetails` Langfuse receives has
only aggregate input and output counts, with **no cache breakdown**. About 95% of the input
tokens on the subject side are cache hits, and the cache price is 1/30 of full price:

```
What Langfuse would compute:  5467 x full price                  -> 0.82 CNY
What is actually correct:      273 x full + 5194 x cache price    -> 0.16 CNY
```

A factor of 5. Syncing the price table would not produce "the dashboard shows cost" but
**the dashboard shows a wrong number that looks entirely normal**, which is far more
dangerous than a conspicuous 0, because nobody would question it.

### Decision

**Langfuse is used for traces, latency and token observation only; cost comes from
`scripts/analyze_eval.py`.**

The reason is to keep exactly one authority for cost. `analyze_eval.py` splits cost by role,
separates cached input, and cross-checks against litellm's independent accounting with exact
equality. Two places each showing a number, one of which is wrong, is worse than one place.

This is recorded in three places, any one of which is enough to prevent a misreading:

- `langfuse_cost_reported: false` in summary.json, with the reason
- `run_eval.py` prints at startup that the dashboard has only trace/latency/tokens and that
  **cost is always 0** (an upstream gap, not free usage)
- A test watches whether litellm starts emitting `cost_details`; the day it turns red, the
  decision can be revisited

> Deviation from [EVALUATION_AND_GATES.md](EVALUATION_AND_GATES.md): it states that the
> Langfuse cost configuration should use real prices. That requirement presumes Langfuse can
> obtain usage split by cache, which measurement shows it cannot. The harder requirement in
> the same document - never record a missing cost as free when the price is unverified - is
> satisfied precisely by **not** syncing the price table: syncing it would make the dashboard
> report an unverified number.

## 4. Correlating traces with results

A trace on the dashboard that cannot be tied back to a run leaves observation and results as
two separate worlds.

Langfuse groups by **session**. litellm's `langfuse_otel` reads `session_id` and `tags` only
from `litellm_params["metadata"]` (see `LangfuseOtelLogger._set_metadata_attributes`), and
that can only be passed **per call**: there is no global entry point, and the one related
environment variable, `LANGFUSE_TRACING_ENVIRONMENT`, is an environment name like dev/prod,
not a session id. Upstream `tau2` offers no way to pass metadata either.

Approach: wrap `tau2.utils.llm_utils.completion`. It is the **single shared exit** for the
agent under test, the simulated user and both judges, so one place covers everything.
Wrapping there rather than `litellm.completion` avoids affecting any other use in the same
process.

The session id is the **run directory name** (of the form
`20260907T141354Z_deepseek-v4-pro_dev`): it is already the unique identifier of a run in this
project, so no lookup table has to be maintained on either side. A resume (`resume_run.py`)
uses the original run's directory name, so resumed traces land in the same session instead of
adding an orphan session with a handful of tasks.

How to look one up: on the dashboard, Tracing -> Sessions and search the run directory name;
or via the API, `GET /api/public/traces?sessionId=<run directory name>`. The session id is
also written into summary.json as `observability.langfuse_session_id`.

`metadata` is litellm's own parameter (it is in the `get_litellm_params` list), so it is not
forwarded to the model server and is unaffected by `litellm.drop_params`. A test pins that
down, because once it stops holding, the session id **disappears silently**.

## 5. Without an explicit flush, traces are lost silently

Measured 2026-09-07 with three real calls and an API read-back:

| Scenario | Is the trace on the dashboard |
|---|---|
| Exit immediately after the call | **No, and never will be**, while the exit code is still 0 |
| Wait a few seconds, then exit | Yes |
| Call `flush_langfuse()` after the call | Yes |

OTEL's `TracerProvider` would shut itself down at process exit, but litellm's `langfuse_otel`
**never sets the provider as the global one**: `opentelemetry.trace.get_tracer_provider()`
still returns a `ProxyTracerProvider`, which does not even have `force_flush`, so that exit
path never applies. The only entry point is the `tracer.span_processor` held by the logger
instance itself.

A full evaluation run takes a long time, and the batch exporter ships mid-run spans on
schedule, so **what is lost is the last few tasks** - exactly the ones you want to see when
you open the dashboard after a run finishes.

`flush_langfuse()` waits 3 seconds first (litellm's success callback runs on another thread,
and flushing before the span exists pushes nothing), then forces an export on the span
processor. If the export fails it reports `langfuse_flushed: false` and logs a warning but
**does not raise**: an observability failure must not invalidate a good run.

It depends on the upstream private name `_in_memory_loggers`, pinned by a test. The day it is
renamed the test turns red; without it, flush would silently degrade to pushing nothing and
traces would start disappearing again.

> **A gate distortion fixed along the way**: litellm and opentelemetry are both in the
> `bench` group, which CI's `uv sync --locked` does not install. mypy previously set
> `ignore_missing_imports` only for `tau2.*`, so a machine with bench installed read real
> types while CI read Any, and the same `# type: ignore` was required locally but reported as
> an unused ignore in CI: all green locally, 12 errors in CI. Switching to
> `follow_imports = "skip"` makes both sides agree, so `uv run mypy` is strictly equivalent to
> CI. New tests guard bench dependencies with `pytest.importorskip` following the existing
> convention: without bench, 209 pass and 4 skip; with it, 238 pass. Both environments were
> verified by running them.

Keys are read from the environment only, set in-process only, and never written to disk, to a
log, or into a manifest.
