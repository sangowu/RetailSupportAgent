# M0.5 part three: frozen baselines

The last theme of M0.5: fix M0's results into a **comparable object** and have CI protect it
from silent modification. The first two parts are
[M0.5 part one: cost and observability](M0.5_OBSERVABILITY.md) and
[M0.5 part two: local start/stop](M0.5_LOCAL_DEMO.md).

```
evaluation/baselines/
    baseline-v1/   holdout, 40 tasks, upstream agent, **archived**
    baseline-v2/   full set, 114 tasks, upstream agent, **control**
    baseline-v3/   full set, 114 tasks, this project's guarded agent, **current baseline**
        baseline.json      the baseline record (every number computed by the script)
        checksums.sha256   digests of the dependency files, in tracked / local_only sections
```

```bash
uv run python scripts/freeze_baseline.py --id baseline-v3   # freeze one baseline
uv run python scripts/freeze_baseline.py --verify           # verify all baselines (CI runs this)
```

| Run directory | `20260908T121800Z_deepseek-v4-pro_full_guarded` | `20260907T205640Z_deepseek-v4-pro_full` | `20260907T080504Z_deepseek-v4-pro_holdout` |

| Cost per task | 0.0954 CNY (10.8742 CNY total) | 0.0855 CNY (9.7414 CNY total) | 0.0806 CNY (3.2241 CNY total) |

**v2 and v3 are two different subjects under test.** They can be compared task by task as a
paired sample (McNemar p = 0.3018, not significant), but their scores must not be averaged
together. That is why v2 is kept as a control rather than archived.

The evaluation stack they share: deepseek-v4-pro under test (thinking effort=high,
temperature 0.0), glm-5.3-flash as the simulated user, qwen3.7-flash-2026-07-15 as the NL
judge, each on its own endpoint; upstream tau2-bench v1.0.1 `fc0055dc...0992` with all 13
files verified; price snapshot 2026-09-06.

**Why the full-set score (0.8509) is below the holdout score (0.8750)**: the full set
includes the 74 dev tasks, and holdout is simply an easier or harder subset of the whole, so
sampling variation alone explains it. Both numbers come from the same model on the same
stack, and a gap of 0.024 is within a reasonable range. More importantly they follow
**different conventions** and must not be read as a regression.

## 1.1 Layered by business scope

The three flows this project declares (lookup / cancel / return) cover **42** of the 114
tasks (8 read-only plus 34 in-scope writes). The rule fixed in M0.1 is that both conventions
are reported and neither stands in for the other:

| Layer | Score |
|---|---|
| Read-only (lookup) | 8/8 = 1.0000 |
| In-scope writes (cancel / return) | 31/34 = 0.9118 |
| Out-of-scope writes (modify / exchange / address / payment) | 56/70 = 0.8000 |
| No scored action upstream | 2/2 = 1.0000 |
| **The three declared flows (42-task subset)** | **39/42 = 0.9286** |
| **Full set (standard tau2-bench Retail)** | **97/114 = 0.8509** |

`analyze_eval.py` now prints this table automatically. When the sample is too small it
**refuses to report a subset score** rather than forcing a number out: only 13 holdout tasks
fall in the subset, 13 tasks support no conclusion, and a printed ratio looks exactly as
authoritative as the full-set score.

The table also shows why running the full set is necessary: the 70 out-of-scope tasks are
61% of the total and are what pulls the score from 0.9286 down to 0.8509. Reporting only the
subset score means picking the convention that flatters us.

## 2. Three deliberate trade-offs

### 2.1 The run directory is hard-coded rather than "the latest run"

`BASELINES` is a registry inside the script, and each baseline hard-codes its own run
directory. The point of a baseline is precisely that it does **not** drift with the latest
run; changing one means adding an entry to the registry and stating in the PR why. The tests
hard-code the same facts, so a baseline changes only when both sides change and a one-sided
edit turns red immediately.

**Old baselines are archived, not deleted.** Delete one and the number quoted in a historical
report can never be checked again; keeping it and continuing to verify its checksums means
every CI run confirms that the raw records of that run have not been touched. `--verify`
therefore verifies **all** baselines, archived ones included.

### 2.2 Cost is not frozen into the baseline

The price snapshot gains entries over time. Copying "0.0806 CNY per task" into
`baseline.json` would silently go stale after a price change, and **nothing would warn you**.

So cost is always recomputed by `scripts/analyze_eval.py` (conventions in
[M0.5 part one](M0.5_OBSERVABILITY.md)), and the baseline freezes only the score, the
evaluation stack and the upstream pin. A test pins down that no cost field may appear in a
baseline.

### 2.3 Checksums come in two sections

| Section | Contents | Rule |
|---|---|---|
| `tracked` | Committed files: task sets, the upstream manifest, the schemas, that run's summary | Missing or changed is a failure; **CI verifies this section** |
| `local_only` | Raw per-task traces (about 100KB per task, not committed per `.gitignore`) | Digests are recorded; **missing is not a failure**, changed is |

Without the split, CI would be **permanently red** because the raw traces are not supposed
to be in the repository, and a permanently red gate is no gate at all.

Three cases were exercised:

```
raw traces absent on this machine -> pass, reporting "2 not present locally, not committed
                                     by design, not a failure"
summary.json modified             -> fail, exit code 1, naming the file that changed
restored                          -> pass
```

## 3. A published number corrected along the way

Recomputing cost before the freeze exposed that **the per-task cost of 0.0716 CNY was wrong;
the correct value is 0.0806 CNY.**

```
0.0716 = 3.2241 / 45     <- wrong denominator
0.0806 = 3.2241 / 40     <- this run had only 40 tasks
```

Where 45 came from: 5 tasks in that run failed to start because of a server-side quota fault
and were later resumed with `resume_run.py`. A resume leaves **two** records for the same
task in the result file (the earlier failure and the successful resume), which counted as 45
simulations before deduplication. Deduplication was fixed in PR #5, but **the numbers already
written into the documents were not recomputed at the time**.

Impact: the per-task cost in the README and in the M0.4 experiment plan was 11% low, and the
derived claim that "qwen3.8-max is 5.4x more expensive" is in fact **4.8x**. The direction of
the conclusion is unchanged (the costs are still in different ranges, and model selection is
still a cost decision), but the numbers themselves were wrong; all have been corrected and a
correction note is recorded in the M0.4 document.

This is the direct reason the baseline script **never copies numbers from documents and
always recomputes from raw results**, and why one test watches specifically that the
denominator is the task count, not the number of simulation records.

## 4. What changed in the CI gate

The `evaluation-gate` job went from "N/A, produces no numbers" to doing something real:

```yaml
- name: Verify baseline checksums
  run: uv run python scripts/freeze_baseline.py --verify
```

It **still runs no evaluation**: a run costs real money, which CI cannot and should not
spend. What it protects is that the baseline itself was not quietly changed. If a task set,
the upstream manifest or that run's summary changes, the baseline no longer represents the
run it claims to, and every later comparison loses its meaning.

## 5. One deviation from the archiving convention

`EVALUATION_AND_GATES.md` suggests the path `artifacts/baselines/baseline-v1/`. This uses
`evaluation/baselines/baseline-v1/`: the original text calls it a suggested path pattern
rather than a requirement, and this repository's experiment artefacts (`results/`,
`task_sets/`, `schemas/`, `demo_runs/`) already live under `evaluation/`. A second
`artifacts/` tree would only split like things across two places. When the AWS stage copies
to S3 it follows the key prefix in the convention, independent of the local directory name.

## 6. Explicitly not done

- **No performance gate.** Having a baseline only means having something to compare against;
  a real candidate-versus-baseline comparison requires running an evaluation, which is M5's
  subject and needs explicit billing authorization.
- **The full set has been run once.** The variance of repeating the same configuration has
  not been measured, so 0.8509 is a single observation, not an estimate with a confidence
  interval.
- **Only one model has been tested on this stack.** Selection was a cost decision, not a
  quality comparison; the reasoning is in [M0.4 section 9.9](M0.4_EXPERIMENT_PLAN.md).
- **The raw per-task traces have no off-machine backup.** They exist only locally and
  `.gitignore` keeps them out of the repository; the convention's "copy to S3 and verify in
  the AWS stage" is not done. Their digests are recorded, so a loss would be detected but not
  recovered.

## Appendix: how v1 became v2 (added 2026-09-07)

`baseline-v1` was replaced on the day it was frozen, and the reason is worth recording.

**It started with a question: why not run the full set?** Investigation showed this was not
an argued decision but **a missed action**: on 2026-09-06 the convention had already been
locked as "run the full 114 tasks per tau2-bench Retail's original design, and report the
42-task subset separately as a layer", but M0.4's structure was "screen on dev, then verify
independently on holdout", and after selection nobody went back to run the full set. **No
historical run exceeded 40 tasks**, and the 74-task dev set had only been sampled at 12 or 24
tasks.

It was not a cost problem: one full-set run costs 9.74 CNY and about an hour.

So the full set was run, `baseline-v2` was frozen, and `baseline-v1` became archived.

### A real problem hit during that run

After `regen_manifest.py` ran, `freeze_baseline.py --verify` immediately reported four files
as changed while `git diff` was **empty**.

The cause: `Path.write_text()` converts `\n` to `\r\n` on Windows. `.gitattributes` requires
LF in the repository, so a commit and checkout normalize it, and **that is why CI passed when
v1 was frozen** - not because the bytes matched, but because CI received normalized files.
Before a commit, though, the local file differs from the repository bytes, and checksums are
computed over bytes.

The consequence: anyone running `regen_manifest.py` on Windows turns the baseline check red
while `git diff` shows nothing, and a red light with no discoverable cause is worse than no
light.

Fix: all 10 `write_text` calls across 8 scripts now pass `newline="\n"` explicitly, so
generated files are byte-identical on any platform. This is the precondition for the checksum
mechanism to mean anything; without it, what it guards is "the local line endings happen to
match the repository", not the content.
