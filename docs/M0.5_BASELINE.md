# M0.5（三）冻结基线

M0.5 的最后一个主题：把 M0 的成绩固定成一个**可比对象**，并让 CI 守住它不被悄悄改动。
前两篇见 [M0.5（一）成本与观测](M0.5_OBSERVABILITY.md)、[M0.5（二）本地启停](M0.5_LOCAL_DEMO.md)。

```
evaluation/baselines/
    baseline-v1/   holdout 40 题，**留档**
    baseline-v2/   全集 114 题，**当前基线**
        baseline.json      基线记录（数字全部由脚本现算）
        checksums.sha256   依赖文件的摘要，分 tracked / local_only 两段
```

```bash
uv run python scripts/freeze_baseline.py --id baseline-v2   # 冻结某个基线
uv run python scripts/freeze_baseline.py --verify           # 校验全部基线（CI 跑这个）
```

## 1. 基线内容

| | baseline-v2（当前） | baseline-v1（留档） |
|---|---|---|
| 运行目录 | `20260907T205640Z_deepseek-v4-pro_full` | `20260907T080504Z_deepseek-v4-pro_holdout` |
| 任务集 | **全集 114 题** | holdout 40 题 |
| 完整性 | 114/114 全部评分，无丢题 | 40/40（其中 5 题补跑） |
| 平均奖励 | **0.8509**（97/114） | 0.8750（35/40） |
| 口径 | **标准 τ²-bench Retail 分数** | 子集分，性质是「未用于调参的独立验证」 |
| 每题成本 | 0.0855 元（三角色合计 9.7414 元） | 0.0806 元（合计 3.2241 元） |

两者共同的评测栈：被测 deepseek-v4-pro（思考 effort=high，temperature 0.0）、
模拟用户 glm-5.3-flash、NL 判官 qwen3.7-flash-2026-07-15，三者各自独立端点；
上游 τ²-bench v1.0.1 `fc0055dc…0992`，13 个文件逐一校验；价格快照 2026-09-06。

**为什么全集分（0.8509）低于 holdout 分（0.8750）**：全集含 dev 74 题，
holdout 只是其中较容易的一批还是较难的一批，本身就有抽样波动；
两个数字来自同一评测栈的同一模型，差 0.024 落在合理范围内。
更要紧的是它们**口径不同**，不该被当成"退步"来读。

## 1.1 按业务范围分层

本项目声明的三类业务（查询 / 取消 / 退货）只覆盖 114 题中的 **42 题**
（只读 8 + 范围内写 34）。M0.1 定的规矩是两个口径都给，谁也不冒充谁：

| 分层 | 成绩 |
|---|---|
| 只读（查询类） | 8/8 = 1.0000 |
| 范围内写（取消 / 退货） | 31/34 = 0.9118 |
| 范围外写（改单 / 换货 / 改址 / 改支付） | 56/70 = 0.8000 |
| 上游未给评分动作 | 2/2 = 1.0000 |
| **本项目声明的三类业务（42 题子集）** | **39/42 = 0.9286** |
| **全集（标准 τ²-bench Retail）** | **97/114 = 0.8509** |

`analyze_eval.py` 现在会自动打印这张表。样本不足时它**拒绝报子集分**而不是硬给
一个数——holdout 只有 13 题落在这个子集里，13 道题撑不住任何结论，
但一个印出来的比例看上去和全集分一样权威。

这张表也说明了为什么"跑全集"是必须的：范围外的 70 题占了 61%，
它们才是把总分从 0.9286 拉到 0.8509 的部分。只报子集分等于挑对自己有利的口径。

## 2. 三个刻意的取舍

### 2.1 运行目录写死，不取"最新一轮"

`BASELINES` 是脚本里的登记表，每个基线写死自己的运行目录。基线的意义恰恰在于
它**不会**跟着最新一次运行漂移；要换基线就在登记表里加一条，并且必须在 PR 里说清
为什么换。测试里也写死了同一份事实——两边都改才算换基线，单边改动会立刻变红。

**旧基线只留档、不删除。** 删掉它，历史报告里引用的那个数字就再也无从校验；
留着它并继续校验校验和，等于每次 CI 都确认"当初那一轮的原始记录没被动过"。
`--verify` 因此校验**全部**基线，留档的也不例外。

### 2.2 成本不冻结进基线

价格快照会随时间新增条目。把「每题 0.0806 元」抄进 `baseline.json`，
它会在某次调价后悄悄过期，而**没有任何东西会提醒你**。

所以成本以 `scripts/analyze_eval.py` 现算为准（口径见 [M0.5（一）](M0.5_OBSERVABILITY.md)），
基线只冻结成绩、评测栈与上游固定点。有一条测试钉着"基线里不许出现成本字段"。

### 2.3 校验和分两段

| 段 | 内容 | 校验规则 |
|---|---|---|
| `tracked` | 入库文件：任务集、上游 manifest、schema、那一轮的 summary | 缺失或变动都算失败，**CI 校验这一段** |
| `local_only` | 原始逐题轨迹（约 100KB/题，按 `.gitignore` 不入库） | 摘要照记；**缺失不算失败**，变了才算 |

不分段的话，CI 会因为原始轨迹本来就不该在仓库里而**永远红**——
一个恒红的门禁等于没有门禁。

实测三种情形：

```
原始轨迹不在本机   -> 通过，并报告「2 个不在本机——按设计不入库，不算失败」
改动 summary.json  -> 失败，退出码 1，指名道姓说哪个文件变了
还原后             -> 通过
```

## 3. 顺带订正一个对外报过的错数字

冻结前重算成本时发现：**每题成本 0.0716 元是错的，正确值是 0.0806 元。**

```
0.0716 = 3.2241 ÷ 45     ← 分母错了
0.0806 = 3.2241 ÷ 40     ← 这一轮只有 40 题
```

45 从哪来：这一轮有 5 道题因服务端额度故障没跑起来，后来用 `resume_run.py` 补跑。
补跑会让同一道题在结果文件里留下**两条**记录（先前失败的那条和补跑成功的那条），
去重前被算作 45 次模拟。去重在 PR #5 已经修好，但**当时没有回头重算已经写进文档的数字**。

影响：README 与 M0.4 实验方案里的每题成本偏低 11%；由它推出的
「qwen3.8-max 贵 5.4 倍」实为 **4.8 倍**。结论方向不变（成本仍不在一个量级，
选型仍是成本决策），但数字本身是错的，已全部改正并在 M0.4 文档里留下订正说明。

这也是基线脚本**不从文档抄数字、一律从原始结果现算**的直接原因，
以及为什么有一条测试专门盯着「分母必须是题数，不是模拟记录条数」。

## 4. CI 门禁的变化

`evaluation-gate` 作业从「N/A，不产生任何数值」换成真的做一件事：

```yaml
- name: 校验基线的校验和
  run: uv run python scripts/freeze_baseline.py --verify
```

它**仍然不跑评测**——跑一轮要真实计费，CI 里跑不起也不该跑。它守的是基线本身
没被悄悄改过：任务集、上游 manifest、那一轮的 summary 任何一个变了，
基线就不再代表它自称的那次运行，后续所有对比也就失去意义。

## 5. 与归档规范的一处偏差

`EVALUATION_AND_GATES.md` 建议路径 `artifacts/baselines/baseline-v1/`。
这里用的是 `evaluation/baselines/baseline-v1/`：原文写的是"建议路径模式"而非强制，
而本仓库的实验产物（`results/`、`task_sets/`、`schemas/`、`demo_runs/`）已经全在
`evaluation/` 下。再开一棵 `artifacts/` 树只会让同类东西分居两处。
AWS 阶段复制到 S3 时按规范的 key 前缀走，不受本地目录名影响。

## 6. 明确未做的事

- **没有性能对比门禁**。有了基线只是有了可比对象；真正的"候选 vs 基线"对比要
  真实跑评测，那是 M5 的主题，且必须显式授权计费。
- **只跑过 1 次全集**。同一配置重复跑的方差没有测过，所以 0.8509 是一次观测值，不是带置信区间的估计。
- **只有一个模型在这个栈上测过**。选型是成本决策，不是质量比较，理由见
  [M0.4 §9.9](M0.4_EXPERIMENT_PLAN.md)。
- **原始逐题轨迹没有异地备份**。它们只在本机，`.gitignore` 挡着不入库；
  规范里"AWS 阶段复制到 S3 并校验"尚未做。摘要已记，丢了能发现，但找不回来。

## 附：从 v1 到 v2 的经过（2026-09-07 补记）

`baseline-v1` 冻结当天就被换掉了，原因值得记下来。

**起因是一个问题：为什么不跑全集？** 查下来发现这不是一个论证过的决定，而是
**一个漏掉的动作**：2026-09-06 就锁定过口径「按 τ²-bench Retail 原始设计跑全集
114 题，42 题子集另行分层报告」，但 M0.4 的结构是「dev 上筛选 → holdout 独立验证」，
选完型之后没有人回头跑一次全集。所有历史运行里**没有一轮超过 40 题**，
dev 集 74 题也只跑过 12 或 24 题的抽样。

它不是成本问题：全集一轮 9.74 元、约 1 小时。

于是补跑了全集，冻结 `baseline-v2`，`baseline-v1` 转为留档。

### 补跑过程中撞到的一个真问题

`regen_manifest.py` 跑完之后，`freeze_baseline.py --verify` 立刻报四个文件
「内容已变」，而 `git diff` 是**空的**。

原因：`Path.write_text()` 在 Windows 上把 `\n` 换成 `\r\n`。`.gitattributes`
规定入库统一 LF，所以提交+检出之后会归一——**这正是 v1 冻结时 CI 能通过的原因**，
不是因为字节一致，而是因为 CI 拿到的是归一后的文件。但在提交之前，
本机文件与仓库字节不同，而校验和是按字节算的。

后果是：任何人在 Windows 上跑一次 `regen_manifest.py`，基线校验就会红，
而 `git diff` 什么都看不出来——一个查不出原因的红灯，比没有灯更糟。

修法：8 个脚本里 10 处 `write_text` 全部显式 `newline="\n"`，
让生成物在任何平台上字节一致。这是校验和机制**能够成立**的前提，
不修的话它守的其实是"本机行尾恰好和仓库一致"，而不是内容。
