# M7.1: showing the work while it happens

## 0. Why this step exists

A turn takes as long as it takes. Measured on the deployed environment during M6.9, the
first turn of a cancellation flow took 18 seconds, and the page showed nothing for all of
it. Then the whole answer arrived at once.

Most of that silence is not the model writing the answer. It is the turn doing its work:
asking the model, running a tool, asking again, holding a write for confirmation. Every one
of those is a thing this project exists to demonstrate, and all of them happen behind a
blank panel.

So this step is not really about speed. The turn will take the same time afterwards. It is
about a demo that shows the guard holding a write, rather than a demo that mentions
afterwards that it did.

M7's acceptance line is "user actions, state and error display", with no regression in the
existing backend. This is the first of the three.

## 1. Change card

- **Stage and step**: M7.1
- **Type**: feature
- **The specific problem**: a turn is a blank panel until it is over, and the work it does

- **The single theme of this change**: the page shows what the turn is doing while it does

- **Control variables this change does not touch**: the model, the simulated user, the

- **Explicitly out of scope**:

    more here, and what it would cost to add tokens later.
  - **Changing `RetailAgent.send`.** Section 1.3. The benchmark calls it, and a step that
    edits it owes an evaluation re-run that this step would otherwise not need.

  - **Tickets and approvals in the UI**: M7.3.
- **Expected benefit**: the demo's central claim - a guard that holds writes - becomes
  something a viewer watches rather than something they are told
- **Possible cost**: a second route into the same turn, which can drift from the first.
  Section 1.4 is about making drift fail a test rather than a demo.

### 1.1 What is streamed

Progress events, as server-sent events, ending with the same reply the existing route
returns.

| Event | When | What it says |
|---|---|---|
| `thinking` | the turn starts, and after each tool result | the model has been asked |
| `tool` | a read-only tool ran | which tool, and that it succeeded |
| `held` | the guard held a write | which tool, and that confirmation is needed |
| `refused` | the guard refused | which tool, and the verdict |
| `reply` | the turn ended | the whole of what `/chat` would have returned |

The last event carries the complete answer, so a client that ignores every other event
behaves exactly like a client of `/chat`. That is deliberate: the events are a view of a
turn, never a second source of truth about it.

### 1.2 Why events rather than tokens

Token streaming would fill the last part of the silence. The events fill all of it.

Of those 18 seconds, the model wrote the final answer during perhaps three. The rest was
two tool calls and two more round trips, during which a token stream has nothing to emit
and the panel stays blank exactly as it does now.

The second reason is what this project is for. A viewer watching `held: cancel_pending_order`
appear, and then the confirmation prompt, has seen the guard work. A viewer watching the
same sentence appear one word at a time has seen a chat box.

Tokens are a later addition rather than a rejected idea: the event stream is the transport,
and a `token` event fits it without changing the route, the client or the page.

### 1.3 Why `send` is not touched

`RetailAgent.send` is on the benchmark's import path. Reimplementing it in terms of a new
streaming method would put the measured path through new code, and the honest response to
that is a full 114-task re-run - real model calls, real money - to show a baseline did not
move.

So `send` keeps its `graph.invoke`, and `stream` is a second entry point over the same two
nodes using `graph.stream`. The nodes, the guard, the journaling and the persistence are
one implementation; only the driving differs.

The cost is two paths that could diverge. Section 1.4 makes that a test failure.

### 1.4 How drift is caught

One scripted conversation, run twice - once through `send`, once by draining `stream` - with
both the returned result and the database compared afterwards.

That is the test that matters, because the failure it catches is silent: a streaming route
that answers correctly while journaling one row fewer would look right in the demo and be
wrong in the audit trail, which is the artefact this project is built to produce.

### 1.5 What a disconnected client loses

Nothing that was written, and the reply.

The turn runs to completion server-side once it has started; it is not cancelled when the
browser goes away. Every write it made is committed and journaled, and the assistant's reply
is in `messages` like any other. What the viewer loses is seeing it, and the next request
for that session reads it back.

The alternative - cancelling the turn on disconnect - is worse in the direction that
matters: a write already executed cannot be un-executed by hanging up, so a cancellation
would produce a session whose database moved and whose transcript does not say so.

### 1.6 What does not change

The existing `POST /chat` keeps its behaviour, its response model and its tests. The
streaming route requires the same token and the same permission, and refuses before any
event is emitted: a 401 or a 403 is a status code, never a stream that opens and then says
it should not have.

## 2. Implementation

| File | Responsibility |
|---|---|
| `src/retail_support_agent/agent.py` | `TurnEvent`, and `stream` beside `send` |
| `src/retail_support_agent/api.py` | `POST /chat/stream`, and the wire format |
| `src/retail_support_agent/client.py` | `chat_stream`, and what each event becomes |
| `src/retail_support_agent/ui.py` | `respond` is a generator; the steps are the bubble |
| `tests/test_streaming.py` | The events, and the comparison that holds the two routes together |

### 2.1 Decisions made during the work

**Events are derived, not emitted.** The nodes could have called an observer, and that
would be better code. It would also add a line to the path the benchmark measures, for a
feature the benchmark never uses. `stream` reads what the nodes left behind instead - the
tools that were appended, the result that was set - so `git diff` on `send` and on both
nodes is empty and section 1.8's claim is checkable rather than argued.

**A fourth event kind appeared.** The card named `thinking`, `tool`, `held` and `refused`.
A write that needs a supervisor is none of those: it is not held pending the user, it is
waiting for somebody else entirely, and telling a customer to confirm something only a
supervisor can decide would be wrong. `approval` was added.

**The client opens the stream eagerly.** `chat_stream` is not a generator function; it
opens the response and returns one. Otherwise nothing happens until the first `next`, and
a 401 would surface after the page had already committed to rendering a turn - too late
for the token refresh the UI does on exactly that error.

**A failure mid-turn is an event, not a status.** Once the first event is out, the status
code is spent. The route emits `{"kind": "error"}` and the client raises the same
exception it would have raised for a 502, so a caller handles one failure rather than two.

**The turn survives the client.** A disconnect stops the events and nothing else. A write
already executed cannot be un-executed by hanging up, so a cancelled turn would produce a
session whose database moved and whose transcript does not say so.

### 2.2 One defect found by measuring

**The first measurement said streaming did not stream.** Through fastapi's `TestClient`,
the first event arrived at 8.58s and the whole turn took 8.60s: every event landing at the
end, which is exactly what no streaming looks like.

It was the measurement. `TestClient` buffers a streaming response, so the same test that
proves the events are correct and in order proves nothing about when they arrive. Over
real HTTP against uvicorn the first event arrives at 0.16s.

Recorded because the test is still there and still cannot see this: `tests/test_api.py`
checks the events and their order, and the timing is checked by hand against a real
server. A test that appears to cover delivery and does not is worth naming.

## 3. Comparison

### 3.1 The thresholds from section 1.7, measured

The environment: a local uvicorn against local PostgreSQL, the same model and the same
prompt on both routes, five rounds each, alternating. Local rather than deployed on
purpose: the question is what the two routes do differently, and running them on one
machine within seconds of each other is the way to see that rather than the machine.

**Time to the first visible event**, against the threshold of 2 seconds:

| | Seconds |
|---|---|
| First event, median of 5 | 0.17 |
| First event, worst of 5 | 0.17 |
| The same turn on `/chat`, median: the panel is blank for all of it | 8.80 |

**Where the time goes in one turn**, which is the thing the card is actually about:

| At | Event |
|---|---|
| 0.16s | `thinking` |
| 3.95s | `tool` · get_order_details |
| 3.95s | `thinking` |
| 7.75s | `reply` |

Two of those four moments are inside what used to be an unbroken silence. Token streaming
would have filled the last stretch only, which is section 1.2's argument in numbers.

**Added latency for a whole turn**, against the 5% threshold:

| | Seconds |
|---|---|
| `/chat`, median of 5 | 8.80 |
| `/chat/stream`, median of 5 | 8.19 |

That is -6.9%, which is not a speedup. Model latency on these turns ranged from 7.75s to
10.66s, so the difference between the two medians is noise and the honest reading is that
streaming costs nothing measurable. What it does not do is make the turn faster.

**The stream and the existing route agree**, and **they write the same rows**: one
conversation run both ways, compared on the result and then on the database.

| Compared | Result |
|---|---|
| reply, status, tool calls | identical |
| tools actually executed | identical |
| a held write: status and the arguments held | identical |
| rows in `messages`, `operations`, `audit_events` | identical, for a read turn and for a confirmed write |

The last row is the one worth having. A streaming route that answers correctly while
recording one row fewer would look right in the demo and be wrong in the audit trail.

**A held write is its own event**, carrying the tool and the arguments, not a sentence
inside the reply.

**Authorization is unchanged.** `/chat/stream` joins the parametrized list in
`tests/test_auth.py` that asserts every route refuses an anonymous caller, and it refuses
with a status code because the agent is resolved before the response begins.

**Degradation**: the streaming tests run with no database configured, as `/chat`'s do.

**No regression in the backend.** `git diff` on `RetailAgent.send`, `_node_think` and
`_node_act` is empty, which is the whole of section 1.8's argument.

|---|---|
| Before this step | 754 |
| After | 793 |

## 4. Failure analysis and conclusion

### 4.1 What this changes about the demo

The claim this project makes is that a model proposes and a guard decides. Until now the
demo asserted that: a viewer sent a message, waited through a blank panel, and read a
sentence saying a confirmation was needed.

Now the panel says the model was asked, then which tool ran, then that the write was held
and for which arguments. The same claim, watched instead of reported.

### 4.2 Limits of these results

- **The test that checks the events cannot see when they arrive.** Section 2.2. Order and
  content are covered; incremental delivery was verified by hand against a real server and
  is not pinned by anything that runs in CI.
- **Measured locally, not on the deployed environment.** The instance runs `m6.8.1`, which
  predates this. The comparison is controlled - two routes, one machine, minutes apart -
  but the deployed numbers include Caddy, and a proxy that buffered would undo this
  entirely. The route sets `X-Accel-Buffering: no` and Caddy honours it; that is a claim
  from documentation, not a measurement, until this is deployed.
- **Five rounds is enough to see 0.17s against 8.80s and not enough to say anything about
  the 5% threshold.** The spread of model latency is larger than the effect being looked
  for, so "streaming costs nothing measurable" is the strongest honest statement.
- **The UI's own rendering was not measured.** Gradio's generator support is what turns
  yielded tuples into a page that updates, and what was measured is the API and the
  client. What a person sees in a browser is M7.2's problem as much as this one's.
- **A disconnect was reasoned about, not tested.** The turn runs to completion because
  nothing cancels it, and its writes are committed by the same code as always. There is no
  test that hangs up mid-turn.

### 4.3 Conclusion

**PASS.** The first event arrives in 0.17 seconds where the panel used to be blank for
8.8 seconds, the streaming route and the existing one produce the same answer and the same
rows, a held write is an event of its own, and the path the benchmark measures is
unchanged by diff rather than by argument.

### 4.4 What this leaves for later

- **How each state looks**: M7.2. There are now more states worth distinguishing, not
  fewer.
- **Tickets and approvals in the UI**: M7.3. The `approval` event added here points at a
  screen that does not exist yet.
- **Tokens**: a `token` event fits the transport without changing the route, the client or
  the page. Worth doing when the answer itself is long enough for the last stretch to
  matter.
- **A deployment, and a second rollback target.** M6.8 noted that the registry holds one
  image that can be rolled back to. Publishing this one gives it two, and a rollback across
  a real behavioural change becomes measurable rather than described.
