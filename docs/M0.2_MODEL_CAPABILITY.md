# M0.2 model capability verification

Status: measured. Date: 2026-09-06.
Raw records: `evaluation/capability_checks/20260906T123218Z/`, containing each probe's
request parameters, response summary and verbatim errors.

Calls go through the OpenAI Python SDK with
`base_url = https://dashscope.aliyuncs.com/compatible-mode/v1` (Beijing region).
21 probes x 5 models = 105 requests, with `max_retries=0`, because retries hide the real
error type.

**Measured usage: 7496 input tokens / 9313 output tokens**, about 0.31 CNY at the price
snapshot in section 5.

> **Correction 2026-09-06**: that 0.31 CNY is a theoretical figure computed from published
> prices. The account was later found to be in free-quota-only mode, so the run most likely
> consumed free quota rather than real credit. See section 4 of
> `docs/M0.4_EXPERIMENT_PLAN.md`.

## 1. Summary

**All five candidate models are callable, and the exact model id requested matches the id
returned in the response**, with no alias fallback and no silent substitution.
The tool-call chain works on all five, which is the precondition of the single-agent
LangGraph design; it is now verified rather than assumed.

But **documentation and measurement disagree in three places**, which affects the M0.4
experiment design directly (section 3).

## 2. Basic capabilities (all pass)

| Probe | What it verifies | Result across five models |
|---|---|---|
| `basic` | The account can call it, the model id is echoed verbatim, usage is returned | all pass |
| `tool_call` | A tool call is issued with valid JSON arguments of the right types | all pass |
| `tool_result_roundtrip` | A `role=tool` message is accepted and the model continues afterwards | all pass |
| `stream_usage` | `stream_options.include_usage` returns usage and tool calls stream incrementally | all pass |
| `sampling_params` | `temperature` and `seed` are accepted | all pass |
| `truncation` | An output cap triggers `finish_reason="length"` | all pass |
| `thinking_off` | With `enable_thinking=false`, `reasoning_tokens` is zero or absent | all pass |

The `usage` structure matches the documentation:
`completion_tokens_details.reasoning_tokens` and `prompt_tokens_details.cached_tokens` are
both readable, so every field needed for cost accounting is present.

## 3. Disagreements with the documentation (three, each evidenced by a server response)

### 3.1 The exclusivity of `reasoning_effort` and `thinking_budget` is enforced by only 2 of 5

Sending both parameters:

| Model | Server behaviour | Parameter that took effect |
|---|---|---|
| `qwen3.8-max` | **rejected** (400) | - |
| `qwen3.8-flash` | **rejected** (400) | - |
| `qwen3.7-max-2026-06-08` | silently accepted | `thinking_budget` (64 thinking tokens) |
| `glm-5.2` | silently accepted | `thinking_budget` (64 thinking tokens) |
| `deepseek-v4-pro-0813` | silently accepted | `reasoning_effort` (68 thinking tokens) |

Three models not only do not error, **they disagree on which parameter wins**. Code must
never rely on this exclusivity rule; the caller has to guarantee that only one is sent.
Otherwise the same configuration produces different thinking behaviour on different models,
with no error to indicate it.

### 3.2 `deepseek-v4-pro-0813` does not obey `thinking_budget`

With `thinking_budget=64`, the measured `reasoning_tokens` is 106, **65% over the limit**.
The other four models stay at or below 64 (qwen3.8-max at 61).

So on that model the thinking budget is a suggestion, not a cap, and cost cannot be bounded
through the parameter. If M0.4 includes it in a budget comparison, billing must use
**measured token counts** rather than the configured value.

### 3.3 `qwen3.7-max-2026-06-08` does not support the `max` level

The server states the allowed values explicitly: `none`, `minimal`, `low`, `medium`,
`high`, `xhigh`. The other four accept `max`. The reference model and the candidates have
different level spaces, so **a level-by-level comparison cannot use one shared set**.

The server error also reveals that model's level mapping:

| Level | Mapped thinking_budget |
|---|---|
| `low` | 8192 |
| `medium` | 32768 |

This is the only place where a level's real budget can be read from outside (see 4.2). The
other models pass under a small cap and expose no number, and **"not exposed" does not mean
the budget is zero**.

## 4. Methodology notes

### 4.1 The first probe version was defective and has been fixed

The first version set `max_completion_tokens` to 512 while testing levels, so `low` and
`medium` returned 400 and were nearly recorded as "this model does not support those two
levels". The verbatim error was:

```
max_completion_tokens [512] must be greater than thinking_budget [8192]
```

The rejection was caused by **an insufficient total output limit**, not by an unsupported
level. This is exactly the distinction `MODEL_EXPERIMENTS.md` requires between "not enough
thinking" and "not enough total output". The corrected level probe sets no
`max_completion_tokens`.

### 4.2 The defect became a measurement technique

Since the server writes the level's mapped budget into the error, one probe,
`effort_budget_mapping_*`, deliberately keeps the cap low: the error is the evidence. It is
currently the only way to read from outside how many tokens a level corresponds to, and
because the request is rejected it costs almost nothing.

### 4.3 Where the evidence is insufficient, it is marked

Measured `reasoning_tokens` per level **does not rise monotonically with the level** (for
`qwen3.7-max`, `low`=226 > `xhigh`=174).

**That does not establish that levels have no effect.** Each level was run once with a very
short prompt, and the variation is fully consistent with sampling noise. Whether levels
actually change behaviour has to be judged in M0.4 with real tau2-bench tasks and repeated
sampling. This report records only whether a parameter was accepted and what a single
observation was; it draws no conclusion about level effectiveness.

Likewise, the `minimal` level returned empty `reasoning_tokens` on `qwen3.7-max` and
`glm-5.2`, and `glm-5.2` produced only 3 output tokens. That level may produce unusable
answers, which M0.4 has to confirm separately.

**What could not be obtained is not guessed**:

- The qwen3.x-max prices above are documented for **non-thinking mode**; thinking-mode
  prices are not given on the page and must be checked in the console and recorded.
- Whether thinking tokens are billed as input or output is not stated clearly enough to
  cite; this report estimates cost as **output**, and that assumption has to be checked
  against the bill.
- The page describes a cache-hit price as 10% of the standard input price and cache
  creation as 125%, but gives no concrete numbers in the main price table.

Prices are a snapshot, not a commitment, and M0.4's cost conclusions must carry the date
they were taken.

## 6. Direct consequences for later stages

1. **M0.3**: the tool-call chain works on all five models, so the single-agent LangGraph
   design has no interface-level blocker and can start.
2. **M0.4**:
   - Thinking configuration must send **only one parameter**, enforced in code rather than
     relying on a server-side exclusivity check.
   - A level comparison cannot assume the five models share one set of levels
     (`qwen3.7-max` has no `max`).
   - Cost is always computed from **measured tokens**; `deepseek-v4-pro-0813` in particular
     cannot be estimated from the configured budget.
   - Level effectiveness needs repeated sampling; this stage's data cannot support any
     elimination decision.
3. **The simulated user and the NL judge model are not chosen yet**, and remain a
   prerequisite of M0.4.

## 7. Reproduction

```bash
uv sync --group dev --group agent
# needs DASHSCOPE_API_KEY in .env; this spends real money (about 0.31 CNY here)
uv run python scripts/probe_models.py --dry-run     # see how many requests would be sent
uv run python scripts/probe_models.py
uv run python scripts/summarize_capability.py       # build the matrix from raw records
```

The capability matrix is generated from the raw records by a script (`matrix.md`), not
typed by hand, so every conclusion traces back to a specific request. Keys are read from
the environment only and appear in neither the raw records, the summary, nor this report.
