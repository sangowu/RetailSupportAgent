# M6.4: the demo environment as code, created and destroyed on command

## 0. Why this step exists

Everything on AWS so far has been made by throwaway shell scripts in a scratch directory
and deleted at the end of each measurement. That was right for measuring and is wrong for
running: nothing describes the environment, nothing can recreate it, and the only record of
what an instance had on it is a report.

M6's acceptance line is "Terraform, one-command start/stop", accepted on creation, login,
streaming, archiving, teardown and rollback. This step does the first and the last of those:
creating the environment, and removing it. The entry points that start and stop a demo
between those two events are the step after.

`docs/OPERATIONS.md` already describes a base and demo layer split, written before the shape
was chosen. M6.1 changed the shape underneath it, so what each layer holds changes with it,
and section 1.2 says how.

## 1. Change card

- **Stage and step**: M6.4
- **Type**: feature
- **The specific problem**: the demo environment exists only as commands that were run once
  and are not in the repository
- **The single theme of this change**: describing the environment in Terraform, and being
  able to create and destroy it. No change to what runs inside it.
- **Control variables this change does not touch**: the application, the image, the
  database schema, the agent, the guard, the evaluation harness, every baseline, the idle
  watcher's logic, and the M6.2 start measurements. The instance this creates runs the same
  image the same way.
- **Explicitly out of scope**, each its own later step:
  - The start and stop entry points, and archiving on stop
  - HTTPS and a stable entry URL
  - GitHub Actions and OIDC. Terraform is run from a developer's machine here; who runs it
    is a separate question from what it describes.
  - Rollback between image versions
- **Expected benefit**: an environment that can be recreated from the repository, and torn
  down completely enough that the inventory shows nothing.
- **Possible cost**: Terraform's state becomes a thing that can be lost or corrupted, and a
  half-applied environment is harder to clean up than a shell script's leftovers. Section
  1.4 says what is done about that.

### 1.1 What "stop when idle" means for Terraform

M6.1 chose an instance that is **stopped** when idle, not destroyed. So stopping is not a
Terraform operation. Terraform creates the environment and destroys it; between those, the
instance is stopped and started by the watcher and by the entry points, and its power state
is not something Terraform tracks.

That is worth stating because it is the opposite of the assumption in `docs/OPERATIONS.md`,
where a demo layer is applied and destroyed around every demonstration. Applying takes
minutes and pulls a 722 MB image; starting a stopped instance takes 41 seconds. The second
is the demo path.

**To be verified rather than assumed**: that `terraform plan` against a stopped instance
reports no changes. If Terraform wants to recreate a stopped instance, this whole shape
needs a different answer, and finding that out is part of this step.

### 1.2 The two layers, as the chosen shape needs them

| Layer | Holds | Lifetime |
|---|---|---|
| Base | the image registry, the state and archive bucket, the instance's IAM role | survives teardown; deleting it loses the archives |
| Demo | the instance, its volume, its security group, its instance profile attachment | created by `apply`, removed by `destroy` |

The split is by what a teardown must not take with it. Archives and the image outlive any
one environment; the instance does not.

**The state bucket cannot hold its own creation.** The base layer therefore starts with
local state, and moves into the bucket it just made. That is one manual step, done once,
and it is written down rather than automated: automating a step that runs once per account
hides it.

### 1.3 What is measured

| Metric | Threshold |
|---|---|
| `apply` from nothing to a demo that answers | recorded; under 10 minutes |
| `plan` immediately after `apply` | no changes |
| `plan` against a stopped instance | no changes |
| `destroy` | completes, and `scripts/aws_inventory.py` then shows nothing tagged |
| The instance it creates | answers on both ports, and stops itself when idle, as M6.2 and M6.3 measured |
| Cost while stopped | the volume alone, matching M6.1's 0.70 USD a month |

### 1.4 What is done about state

- **Versioning on the bucket**, so a corrupted or truncated state can be rolled back.
- **Native S3 locking** (`use_lockfile`), not DynamoDB. DynamoDB-based locking is
  deprecated and would be a second billed resource for no gain.
- **Encryption and public access blocked** on the bucket, because the same bucket holds
  archives later.
- **No secret in state.** The model key reaches the instance through the environment, not
  through a Terraform variable, since anything Terraform is told ends up in state in clear.
  How the key gets there is settled in this step and stated in section 2.

### 1.5 Baseline and previous version

No previous version: no Terraform exists. The reference is what the M6.2 and M6.3
measurement scripts created by hand, and the acceptance is that Terraform produces an
environment those measurements would have accepted.
