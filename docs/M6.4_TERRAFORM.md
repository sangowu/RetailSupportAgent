# M6.4: the demo environment as code, created and destroyed on command

## 0. Why this step exists

Everything on AWS so far has been made by throwaway shell scripts in a scratch directory
and deleted at the end of each measurement. That was right for measuring and is wrong for
running: nothing describes the environment, nothing can recreate it, and the only record of
what an instance had on it is a report.

M6's acceptance line is "Terraform, one-command start/stop", accepted on creation, login,
streaming, archiving, teardown and rollback. This step does the first and the last of those:
creating the environment, and removing it. The entry points that start and stop a demo
between those two events are the step after.

`docs/OPERATIONS.md` already describes a base and demo layer split, written before the shape
was chosen. M6.1 changed the shape underneath it, so what each layer holds changes with it,
and section 1.2 says how.

## 1. Change card

- **Stage and step**: M6.4
- **Type**: feature
- **The specific problem**: the demo environment exists only as commands that were run once
  and are not in the repository
- **The single theme of this change**: describing the environment in Terraform, and being
  able to create and destroy it. No change to what runs inside it.
- **Control variables this change does not touch**: the application, the image, the
  database schema, the agent, the guard, the evaluation harness, every baseline, the idle
  watcher's logic, and the M6.2 start measurements. The instance this creates runs the same
  image the same way.
- **Explicitly out of scope**, each its own later step:
  - The start and stop entry points, and archiving on stop
  - HTTPS and a stable entry URL
  - GitHub Actions and OIDC. Terraform is run from a developer's machine here; who runs it
    is a separate question from what it describes.
  - Rollback between image versions
- **Expected benefit**: an environment that can be recreated from the repository, and torn
  down completely enough that the inventory shows nothing.
- **Possible cost**: Terraform's state becomes a thing that can be lost or corrupted, and a
  half-applied environment is harder to clean up than a shell script's leftovers. Section
  1.4 says what is done about that.

### 1.1 What "stop when idle" means for Terraform

M6.1 chose an instance that is **stopped** when idle, not destroyed. So stopping is not a
Terraform operation. Terraform creates the environment and destroys it; between those, the
instance is stopped and started by the watcher and by the entry points, and its power state
is not something Terraform tracks.

That is worth stating because it is the opposite of the assumption in `docs/OPERATIONS.md`,
where a demo layer is applied and destroyed around every demonstration. Applying takes
minutes and pulls a 722 MB image; starting a stopped instance takes 41 seconds. The second
is the demo path.

**To be verified rather than assumed**: that `terraform plan` against a stopped instance
reports no changes. If Terraform wants to recreate a stopped instance, this whole shape
needs a different answer, and finding that out is part of this step.

### 1.2 The two layers, as the chosen shape needs them

| Layer | Holds | Lifetime |
|---|---|---|
| Base | the image registry, the state and archive bucket, the instance's IAM role | survives teardown; deleting it loses the archives |
| Demo | the instance, its volume, its security group, its instance profile attachment | created by `apply`, removed by `destroy` |

The split is by what a teardown must not take with it. Archives and the image outlive any
one environment; the instance does not.

**The state bucket cannot hold its own creation.** The base layer therefore starts with
local state, and moves into the bucket it just made. That is one manual step, done once,
and it is written down rather than automated: automating a step that runs once per account
hides it.

### 1.3 What is measured

| Metric | Threshold |
|---|---|
| `apply` from nothing to a demo that answers | recorded; under 10 minutes |
| `plan` immediately after `apply` | no changes |
| `plan` against a stopped instance | no changes |
| `destroy` | completes, and `scripts/aws_inventory.py` then shows nothing tagged |
| The instance it creates | answers on both ports, and stops itself when idle, as M6.2 and M6.3 measured |
| Cost while stopped | the volume alone, matching M6.1's 0.70 USD a month |

### 1.4 What is done about state

- **Versioning on the bucket**, so a corrupted or truncated state can be rolled back.
- **Native S3 locking** (`use_lockfile`), not DynamoDB. DynamoDB-based locking is
  deprecated and would be a second billed resource for no gain.
- **Encryption and public access blocked** on the bucket, because the same bucket holds
  archives later.
- **No secret in state.** The model key reaches the instance through the environment, not
  through a Terraform variable, since anything Terraform is told ends up in state in clear.
  How the key gets there is settled in this step and stated in section 2.

### 1.5 Baseline and previous version

No previous version: no Terraform exists. The reference is what the M6.2 and M6.3
measurement scripts created by hand, and the acceptance is that Terraform produces an
environment those measurements would have accepted.

## 2. Implementation and verification

### 2.1 Files

| File | Responsibility |
|---|---|
| `deploy/terraform/base/` | the registry, the instance's role and its permissions |
| `deploy/terraform/demo/` | the instance, its volume, its security group |
| `deploy/instance/cloud-init.sh.tftpl` | what Terraform renders onto a new instance |
| `deploy/instance/compose.yaml` | the stack as it runs on the instance, pulling a published image |
| `deploy/instance/rsa-start.sh` | registry login, fetches the model key, brings the stack up |
| `deploy/terraform/README.md` | the bootstrap, publishing an image, creating and destroying |
| `tests/test_deploy_files.py` | 23 tests over the files that only ever run on an instance |

### 2.2 Where the model key lives

Not in Terraform, and not in the repository. It is a SecureString in Parameter Store, put
there once by hand; Terraform is told the parameter's name and grants the instance
`ssm:GetParameter` on that one name. Anything a Terraform variable carries ends up in state
in clear, and the state is a file in a bucket.

On the instance, `rsa-start` fetches it under `umask 077` and writes `/opt/rsa/.env` at mode
600 for compose to read. It never reaches a command line, because a value in `argv` is
visible to every process on the machine. Three tests pin that.

### 2.3 The bucket is not a Terraform resource

A bucket cannot hold the state of its own creation. Every way around that is a bootstrap
dance: local state that is migrated afterwards, or a backend block added after the first
apply. Both were tried and both are worse than three CLI commands, which is what the README
documents. The base layer reads the bucket as a data source.

This also removes a hazard rather than mitigating one. No `terraform destroy` can reach the
archives, because nothing in either state file owns them.

### 2.4 What Terraform is told not to do

- **`ignore_changes = [ami]`.** The AMI is resolved with `most_recent`, so an unrelated
  apply weeks later would otherwise replace a working instance, and its database with it,
  because Amazon published a new image. Replacing the instance stays a deliberate act.
- **`user_data_replace_on_change = true`.** The opposite case: changing what the instance
  installs must actually reinstall it, and a boot script that only applies to instances
  created afterwards is a trap.
- **Immutable image tags.** The registry rejects a tag that already exists, and
  `image_tag = "latest"` is refused by a variable validation. A rollback is applying an
  older tag.
- **`volume_size` is validated to 8-11 GiB.** Below 8 the stack does not fit; above 11 the
  idle cost passes M6.1's threshold, which is a decision to re-agree rather than to make in
  a variable default.

### 2.5 Three failures worth keeping

- **User data is capped at 16 KB.** The six base64 file blobs came to 16.4 KB and the apply
  was refused. `base64gzip` brings it well under; cloud-init decompresses it.
- **Git Bash rewrote an SSM parameter name.** `/rsa/demo/dashscope-api-key` reached the API
  as a Windows path, so the parameter was created under the wrong name and the instance's
  first boot failed with `ParameterNotFound`. `MSYS_NO_PATHCONV=1` fixes it. This is the
  third time this environment has done that to an argument beginning with a slash, after
  `/dev/xvda` in M6.1.
- **The first `terraform init` cannot use a backend that does not exist yet**, which is
  section 2.3.

## 3. Comparison

No model is called and no task set is run, so task success rate, safety violations and cost
per successful task are unchanged by construction.

### 3.1 Creating and destroying, measured

`eu-west-1`, one `t3.small`, a 10 GiB gp3 root volume, image tag `m6.4`.

| Step | Seconds |
|---|---|
| Base layer `apply`, eight resources | 12 |
| Publish the image to the new registry | 37 |
| Demo layer `apply`, five resources | 47 |
| From that returning to the API answering | 96 |
| Demo layer `destroy` | 16 |

Creating a whole environment from nothing is a little over two and a half minutes,
comfortably inside the ten the card allowed. The instance it produces is the one M6.2 and
M6.3 measured: 3.2 GB of the 10 GiB volume in use, both ports answering, and it stopped
itself under the default fifteen-minute window without being asked.

### 3.2 The question the card said to settle

**A plan against a stopped instance wanted to replace it, and that would have destroyed the
database.**

A stopped instance reports `associate_public_ip_address = false`, because the auto-assigned
address is released on stop. That attribute forces replacement, so Terraform planned to
destroy and recreate. M6.1 chose a shape where a stopped instance is the *normal* state, so
a routine apply on an untouched environment would have wiped it.

`ignore_changes` on that attribute fixes it. After the fix, a plan against the stopped
instance reports no resource changes at all. The `public_ip` output does change, to empty,
which is the truth about a stopped instance rather than drift.

### 3.3 Against the thresholds

| Metric | Threshold | Result |
|---|---|---|
| `apply` from nothing to a demo that answers | under 10 minutes | 2 min 35 s |
| `plan` immediately after `apply` | no changes | no changes |
| `plan` against a stopped instance | no changes | no resource changes, after 3.2 |
| `destroy` | completes, inventory then clean | 16 s, and the inventory shows only the base layer |
| The instance it creates | answers, and stops itself when idle | both ports answered; stopped itself under the default window |
| Cost while stopped | the volume alone | 10 GiB gp3, 0.88 USD a month |

### 3.4 Two problems this found in earlier steps

**The idle watcher was never enabled on the first instance.** Cloud-init ran under `set -e`,
`systemctl enable --now rsa.service` failed because the model key was not yet readable, and
the script stopped there. The timer that was supposed to stop the machine was the next line.
A machine that fails to start its stack is exactly the machine that will sit there billing,
and the thing meant to catch that had not been installed.

The fix is an order and a coupling. The watcher is enabled first and its failure is not
tolerated; the stack is started afterwards with `|| true`, because a machine that boots
without the demo can still be logged into and diagnosed. `rsa-idle.service` no longer
`Requires=rsa.service`, only `After=`: tying the one thing that bounds the bill to the one
thing that just failed is backwards. Four tests pin this.

**The inventory over-reported to the point of being useless.** After a clean `destroy` it
listed eleven EC2 resources, every one of them already terminated, above the one that was
still there. It now resolves state for instances, volumes, security groups and their rules,
groups what is left by Terraform layer, and counts the dead separately. After this step's
teardown it reports one live resource, the base layer's registry, which is correct.

## 4. Failure analysis and conclusion

**PASS.** The environment is in the repository, and one command creates it and one removes
it.

- **What was accepted**: two Terraform layers, the instance files they install, the
  bootstrap documentation, and 26 tests over files that only ever run on a machine
  elsewhere.
- **What this found**: a plan against a stopped instance would have destroyed it, and the
  idle watcher was not installed when it was most needed. Both are fixed and both are
  tested.
- **Where the model key is**: Parameter Store, put there by hand. Terraform is told the
  name and never the value, and the instance writes it to a root-only file rather than
  passing it on a command line.
- **What is left running**: the base layer, which is a registry holding one image and an
  IAM role. The demo layer was destroyed. Nothing is billed by the hour.

### 4.1 Not verified

- **Rollback.** Applying an older `image_tag` should replace the instance with one running
  the previous image. The registry keeps ten images and the variable refuses `latest`, but
  the operation was not performed.
- **A second environment side by side.** Names have a prefix variable but two environments
  in one account share the security group name, so it would collide. Nothing needed two
  yet.
- **Recovery from a lost or corrupted state.** The bucket has versioning; rolling a state
  back was not tried.
- **`use_lockfile` under contention.** One person applied. Two applies at once were not
  attempted.
- **Anything reachable over HTTPS.** The demo answers on plain HTTP to one address. That is
  the next step, and until it exists this environment should not be shown to anyone whose
  address is not in `allowed_cidrs`.
- **Archiving on stop.** The instance stops itself and exports nothing. M6 is accepted on
  archiving; that condition joins the idle definition when there is something to export.
