# M7.2: what happened, and what to do about it

## 0. Why this step exists

The page has one status line and it reports the last thing that happened. A session that
has stopped, an account that lacks a permission, a token that expired, a write waiting for
a supervisor and a conversation a person has taken over all arrive there as a bold
sentence, and the input box stays ready for a message that will go nowhere.

Those are not shades of one thing. They are different states, and the answer to each is
different: sign in again, ask something else, start a new session, confirm, wait. A page
that reports the event and leaves the reader to work out the state is asking them to know
how the system works.

Two specific gaps make this concrete rather than a matter of taste. Three of the seven
statuses a turn can return have no label on the page at all and appear as their internal
name. And a session held open by another process arrives as the same generic failure as a
malformed request, so the one thing that would resolve it - a new session - is never
suggested.

M7's acceptance line is "user actions, state and error display". This is the middle one,
and after M7.1 there are more states worth telling apart rather than fewer.

## 1. Change card

- **Stage and step**: M7.2
- **Type**: feature
- **The specific problem**: the page reports events, and a visitor has to infer the state
  and the remedy
- **The single theme of this change**: every state the page can be in says what it is and
  what to do next
- **Control variables this change does not touch**: the model, the simulated user, the
  judge, the task sets, the upstream commit, the price snapshot, the agent, the guard, the
  authorization model, the persistence, the API's routes and status codes, the deployment,
  and every baseline
- **Explicitly out of scope**:
  - **New API routes or new statuses.** This step renders what the service already says.
    Section 1.5.
  - **Rewording the service's refusals.** A 403 names the missing permission; the page
    shows that text rather than replacing it with something friendlier and vaguer.
  - **Tickets and approvals as screens**: M7.3. This step gets as far as saying a ticket
    exists and who has it.
  - **Retry and reconnect logic.** A failed turn is reported, not retried.
- **Expected benefit**: a demo where the failure paths are as legible as the happy one,
  which is where an authorization model is actually judged
- **Possible cost**: a rendering layer between the service's answers and the page, which
  is somewhere for the two to disagree. Section 1.6's first two thresholds are about
  making that impossible rather than unlikely.

### 1.1 The states, and what each says

Eleven, from two sources: the status of a turn that succeeded, and the exception of one
that did not.

| State | From | What the page says | Box |
|---|---|---|---|
| answered | status | nothing; the reply is the answer | open |
| needs_confirmation | status | the exact arguments being held, and that a yes runs them | open |
| needs_approval | status | a supervisor has to decide this one | open |
| denied | status | the guard's verdict, as the guard worded it | open |
| handed_off | status | which ticket was opened, and that a person owns it now | closed |
| waiting_for_human | status | which ticket, and that the answer will arrive here | closed |
| stopped | status | why the session stopped, and to start a new one | closed |
| expired token | 401 | signed out, with the conversation cleared | n/a |
| not permitted | 403 | the service's own sentence, which names the permission | open |
| session held elsewhere | 409 | this session is open somewhere else; start a new one | open |
| service failed | 5xx | the failure is not this account; try again | open |

### 1.2 Why the box is part of the state

Three of those states cannot be advanced by typing. A session that has stopped will refuse
the next message, a session behind an open ticket will answer that a person has it, and a
conversation just handed off is the same. Leaving the box open in those states invites a
message whose only possible answer is the sentence already on screen.

Closing it is not about preventing anything - the service refuses these on its own, and
that refusal is tested. It is about the page not offering an action that does nothing.
Each of the three names what to do instead.

### 1.3 Why a session held elsewhere needs a name of its own

`409` currently becomes the same generic error as a malformed request. They are not alike:
one is a caller's mistake and the other means this session is being driven from another
place, which M2 made a real possibility and which a new session resolves immediately.

The client gets an exception for it, the way 401 and 403 already have one, because a page
that cannot tell two failures apart cannot suggest different things about them.

### 1.4 Where a message appears is part of what it means

A sign-in failure belongs to the form; a turn's failure belongs to the conversation. They
are already two areas of the page and the update tuple already carries both, so the rule
is only that neither ever writes into the other's. A stale sentence in the wrong place is
how a page tells a visitor something untrue about where they are.

### 1.5 What this step does not change about the service

No new routes, no new statuses, no new fields, and no rewording of what the API says. The
one change below the page is an exception class in the client for a status the service
already returns.

That boundary is deliberate. The service's refusals are the tested artefact - a 403 names
the permission because `tests/test_auth.py` requires it to - and a page that paraphrased
them would quietly become the thing people read instead.

### 1.6 Primary metric, protective metrics, acceptance thresholds

Fixed before running, per `MODEL_EXPERIMENTS.md`.

| Metric | Threshold | If not met |
|---|---|---|

| Every client exception has its own rendering | enumerated from the exception classes, same way | FAIL |
| A session held elsewhere is its own exception | 409 is distinguishable from 422 | FAIL |
| A state that cannot be advanced closes the box | and names what to do instead | FAIL |
| A held write shows its exact arguments | the arguments, not a summary | FAIL |
| A refusal shows the service's own words | including the permission a 403 names | FAIL |

The first two are the ones that matter. Deriving the cases from the type rather than
listing them means a status added later fails this suite until the page has something to
say about it, which is exactly how the three unlabelled statuses got there.

## 2. Implementation

| File | Responsibility |
|---|---|
| `src/retail_support_agent/ui.py` | `Situation`, the state table, and the box as part of it |
| `src/retail_support_agent/client.py` | `ConflictError`, so 409 stops looking like 422 |
| `tests/test_ui_states.py` | The enumerations, and the wiring the page depends on |
| `tests/test_ui.py` | Gradio's own view of that wiring, at runtime |

### 2.1 Decisions made during the work

**One table, keyed by the service's own vocabulary.** `TURN_STATES` maps each status to a
label, a remedy and whether the box stays open. The page never decides any of that inline,
so two states cannot drift into looking like each other, and the test that enumerates them
has one thing to enumerate.

**Failures are keyed on the exception class, not the status code.** The client already
decided what a status code means when it chose which exception to raise. Deciding it again
in the page would be two places to keep in agreement.

**The status line carries the service's words verbatim, in a code span.** A 403 names the
missing permission and the guard's refusal names the account; both are tested artefacts of
the service. The page adds a sentence about what to do and changes nothing about what was
said.

**The ticket number is not parsed.** `handed_off` and `waiting_for_human` say a person owns
the case, and the number reaches the reader inside the service's sentence. Digging an id
out of prose to render it separately would be a page inventing structure the API does not
offer. M7.3 needs that id properly, and it should come from the API rather than from a
regular expression.

**`needs_approval` leaves the box open.** It was tempting to group it with the other two
waits. It is not one: the customer's action is stuck, the conversation is not, and they can
ask about anything else while a supervisor decides.

### 2.2 What was actually wrong before

Not a matter of taste, and worth being precise about since section 0 claims it.

The old page had four labels. A turn can end in seven states. `handed_off`,
`needs_approval` and `waiting_for_human` fell through to the raw status name, so a visitor
whose case had been escalated read `**Status: waiting_for_human**` above a live input box,
and typing into it produced the same sentence again.

The client mapped 409 to the base `ApiError`, the same class as a 422. The page could not
tell "this session is open somewhere else", which a new session fixes in one click, from
"the service rejected that request", which it does not.

## 3. Comparison

### 3.1 The thresholds from section 1.6, measured

Six of the ten are structural and are checked by tests that derive their own cases; the
rest were driven against a running service.

**Every turn status has its own rendering**, enumerated from `TurnResult`'s type rather
than from a list:

| | Before | After |
|---|---|---|
| Statuses a turn can return | 7 | 7 |
| Statuses with a rendering of their own | 4 | 7 |
| Statuses reaching the page as their internal name | 3 | 0 |

The enumeration is read with `typing.get_type_hints`, and a guard test asserts it finds
something. That guard earned itself immediately: the first version read
`__annotations__["status"]`, which under `from __future__ import annotations` is the string
`"Literal[...]"`, so `get_args` returned nothing and every enumerated test passed over an
empty set.

**Every client failure has its own rendering**, enumerated from the exception classes: four
subclasses, four distinct labels, four distinct remedies, and exactly one of them signs the
visitor out.

**A session held elsewhere is its own exception.** 409 becomes `ConflictError`; 422 stays
the base class.

**What a visitor actually sees**, driven through the page's own handler against a running
service, with real model calls:

```
**Status: ⚠ waiting for your confirmation**

`Run cancel_pending_order with these arguments:
  - order_id: "#W4135875"
  - reason: "no longer needed"`

Reply yes to run exactly these arguments, or say what to change.
```

That is the held write showing the exact arguments, which is the guard's claim rather than
a summary of it.

**A state that cannot be advanced closes the box**, measured on the same running service by
escalating a case:

| Turn | Status shown | Box |
|---|---|---|
| the escalation | → handed to a person · tools called: transfer_to_human_agents | closed |
| the next message | → with a person | closed |
| the one after | → with a person | closed |

Before this step both of those read as `handed_off` and `waiting_for_human` with the box
open.

**A refusal shows the service's own words.** Rendered from the exceptions the client
raises:

| Failure | Label | Remedy |
|---|---|---|
| 401 | signed out | sign in again, and the conversation is cleared |
| 403 | ✗ not permitted | the sentence names the permission; sign in as an account that holds it |
| 409 | ✗ this session is open somewhere else | start a new session |
| 5xx | ✗ the service failed | this is not your account; try again |

**Messages stay in their own area.** Pinned on the two shape helpers: a turn's update
always writes an empty string into the sign-in area, and a sign-out always writes an empty
string into the status line.

**The page is wired consistently.** Two checks, because the failure is a runtime error the
first time one particular handler fires, and for the failure paths that can be long after
the change. Statically, every shape helper returns a tuple as wide as the outputs list.
At runtime, Gradio reports every event wired to nine outputs, except the follow-up that
clears the password box and deliberately touches one.

**Degradation**: with no pool configured the page still opens straight into the
conversation, and no sign-in state can occur.

## 4. Failure analysis and conclusion

### 4.1 What this changes about the demo

The interesting half of an authorization model is what it refuses. Until now the demo
refused correctly and reported it as a bold sentence a reader had to interpret, and the
three states that most needed explaining were the three with no explanation at all.

A viewer now sees which permission was missing, which arguments are being held, that a
person owns the case and that typing will not change that, and that a session open in
another tab is fixed by starting a new one. Same service, same refusals, said out loud.

### 4.2 Limits of these results

- **No browser was involved.** The states were driven through the page's own handler and
  read from the update tuples, and Gradio's wiring was checked at runtime, but nobody
  clicked anything. What a disabled Gradio textbox looks like to a person is not measured.
- **Two states were not produced live.** `needs_approval` and `denied` both need a setup
  this measurement did not build: a supervisor's approval path, and a guard refusal that
  the agent does not pre-empt by refusing first, which M6.9 already found it does. They are
  covered by unit tests over the table, not by a live turn.
- **The remedies are untested claims about the world.** "Start a new session" resolves a
  409 because that is what a new session id does, and nothing here proves a visitor
  following the advice gets unstuck. Only that the advice is present, distinct, and matches
  the state.
- **The ticket number is still inside prose.** Section 2.1. M7.3 needs it as a field.

### 4.3 Conclusion

**PASS.** Every threshold in section 1.6 was met. Seven statuses and four failures each
have a rendering of their own, derived from the types rather than from a list, so the way
the three unlabelled states arrived cannot happen again quietly. The three states that
cannot be advanced close the box and say what to do instead, measured on a running service.

### 4.4 What this leaves for later

- **Tickets and approvals as screens**: M7.3. Both `needs_approval` and the two ticket
  states now point at a place that does not exist.
- **A ticket id in the API's answer**, so the page can link to it rather than mention it.
- **A browser-level check.** Everything here is one layer below what a person sees.
